# Grid Inline Editing — Feature Plan — 2026-07-08

What the `editable` feature is trying to be, what ships today, and the increments that take it the rest of the way. The [Grid roadmap](../../src/modules/grid/ROADMAP.md) retired editing from its tracker and named this doc the successor, so status lives here alongside the design.

## Thesis

`editable` is heading at **spreadsheet-grade inline editing without a form detour**: the user edits values where they read them, with the pointer and keyboard ergonomics of a spreadsheet (double-click or type to edit, Enter/Tab to commit and move, Escape to bail) and the data discipline of a form (typed editors, validation, batched commits the consumer applies). Everything layers on the one existing model — the controllable editable-row `Set<key>` plus the `CellChange[]` commit sink — rather than introducing a second editing state; each increment widens who drives that set (consumer → grid) and how narrowly a session scopes (row → cell), never how values commit.

## Current state (verified in tree, 2026-09-23)

- **Row-session model.** A row key in the `editable` set puts every editable cell of that row into edit mode at once (`use-grid-editing.ts`, `grid-editing-cell.tsx`). A column is editable when it has a `field` or an `editCell` slot and isn't `readOnly` (`isColumnEditable`).
- **Staged drafts, batched flush.** Edits stage into a session-owned draft store keyed by cell (no per-keystroke render); a row leaving the set flushes its changed, `validate`-passing cells as one `onCommit` batch, announced politely (WCAG 4.1.3). Escape reverts a single cell. A draft belongs to the session, not to the editor that shows it: an editor that unmounts keeps its draft, and one that mounts again shows it (see the draft cluster below).
- **Editors.** Inferred from the value's primitive type (text / number / yes-no listbox, `grid-edit-inputs.tsx`) or supplied per column via `editCell` — a render-prop slot over `onValueUpdate` / `commit` / `cancel`; no editor components are exported. No editor wires a session key of its own: under a grid-owned session every key lives on the table's key surface (`sessionKeys`), so a slot inherits them all.
- **Cursor.** An editable grid always carries the keyboard cursor (`useGridCursor`: `cursorEnabled = navigable || editing`) — a single tab stop with `aria-activedescendant`, arrows/Home/End/PageUp/Down movement, and Enter/Space activation.
- **Grid-owned sessions.** `editable.session: 'managed'` — entry on an editable data cell's double-click (through the grid's built-in cell double-click event, so `resolveCellContext`'s data-cell resolution and the interactive-content guard apply, and a consumer `onCellDoubleClick` still fires after) or on the cursor's Enter; the entered cell's editor takes focus once mounted. Enter and Escape from *any* editor — inferred, listbox, or `editCell` slot — are owned once on the table's key surface (`sessionKeys`, layered onto `navTableProps`): Enter commits unless the focused element owns Enter natively, as the listbox trigger does (see increment 3 for where it moves), Escape abandons the session's drafts, and both defer to an open floating surface (a consumed press, focus in a portaled panel, or an `aria-expanded="true"` trigger — that press closes the surface; the next abandons). Focus reseats on the grid's tab stop on exit; an `editCell` slot's `commit` also ends the session. Every transition flows through `rows`/`onRowsChange`, so a controlled binding can decline an entry. Default stays `'manual'` — no behavior change for existing consumers.
- **Cell-scoped sessions (shipped).** `editable.scope: 'cell'` narrows a grid-owned session to the entered cell: the row still enters the set, but `GridEditingCell` mounts an editor only for the cell the session names (`activeEdit`, held beside the set and derived against it, so a declined or withdrawn row drops the coord; the cells read it from an external store, one flag each, so a move along a row re-renders two cells). Entering another cell re-points the session — the cell it leaves commits, and a row the session acquired leaves the set — so a session that opened its own row commits one `CellChange` at a time. Narrowing a row the consumer had already opened is the exception: the editors that close with the narrowing commit together, which is why the sink's contract is the batch and never its first entry. One predicate carries the whole narrowing: `isCellEditing` (engine) answers which cell mounts an editor, which entry is the no-op of re-entering the cell already open, and which staged drafts the commit sweep must flush, so an editor's lifetime and its value's commit cannot disagree. The sweep reads that open state rather than diffing against the last render, which is why a consumer's save, a grid-owned exit, and a session moving on all travel one path. The session's surface names itself after the session rather than the row it used to be: `enterEdit(rowKey, columnId)` takes the cell in one address space and resolves the display coord where it is used, `endSession(rowKey, 'save' | 'discard')` is the one exit, and the context is `GridEditingSession`. `scope: 'cell'` without `session: 'managed'` is inert rather than wrong, so it warns in development like the module's other config mismatches. Escape drops the active cell's draft alone, because the cells before it already committed. The setting needs the grid-owned session; under `'manual'` the consumer names a row and never a cell, so the row's editors all mount as under `'row'`. Default stays `'row'`.
- **Commit-and-move keys (shipped).** On by default under `session: 'managed'`, in both scopes: Enter commits and moves down one row (re-entering under `scope: 'cell'`), Tab / Shift+Tab move along the row's editable cells with wrap, F2 toggles edit, and a printable key on the tab stop enters edit seeded with it. See increment 3's as-built note for the edge-case choices.
- **Active-cell binding (shipped).** Under `session: 'managed'` and `scope: 'cell'`, the session's cell is a controllable of its own: `cell` / `defaultCell` / `onCellChange`, typed by the one new export, `GridCellRef`. `rows` keeps its meaning — the rows open for editing — and the grid keeps the two consistent. A controlled binding decides every move, the grid's own and the consumer's; see the settled API question below for the as-built rules. The cells still read the cell from `GridActiveEditStore`, so a controlled move along a row renders two cells.
- **Commit on leave (shipped).** `editable.commitOn: 'explicit' | 'leaveEditor' | 'leaveGrid'` under `session: 'managed'`, default `'explicit'`. `'leaveGrid'` also commits the session when focus leaves the grid; `'leaveEditor'` when focus leaves the session's editors — the held cell under `scope: 'cell'`, the row's open editors under `'row'`. A leave commits through the same exit as Enter, minus the cursor move and the focus reseat. The settle-control policy moved into the hook (`settleControls` on the session): the held cell shows the pair, or discard alone under `'leaveEditor'`. See increment 4's as-built note.
- **Async commit (shipped).** `onCommit` may return a promise. The batch's cells stay in the draft store as `'pending'`: each shows the committed value with `aria-busy` and a pulse, and no entry opens it, while other cells and other batches carry on. Resolving with nothing or `[]` accepts; resolving with `GridCellRefusal[]` (the second export) refuses those cells; a rejection refuses the batch. A refused cell gets its draft back as `'staged'` with the error on the `validate` surface, back in the session without a focus move. See increment 5's as-built note.
- **New-row entry (shipped).** `editable.newRow: 'top' | 'bottom'` with a sibling sink, `onRowAdd(values)`, under `session: 'managed'`: one blank editor row pinned to the body and outside the row model, which only an explicit Enter or Add control adds. It ships as a slot the grid owns, not as public row pinning. See increment 8's as-built note.
- **Bindings that gate it.** Grouping and master-detail stand the cursor down but not editing; virtualization keeps editing (rows mount their editors when scrolled into the window, and keep their drafts while out of it).

## Design sketch — increments

Each increment is independently shippable, in dependency order. The `editable` binding grows options; the exports it gained are `GridCellRef`, the active-cell binding's type, and `GridCellRefusal`, the async sink's refusal type. Increment 8 added none.

**1. Edit triggers (shipped).** `session?: 'manual' | 'managed'` as described above. Foundation for everything below: the grid can now begin and end a session itself, with focus management in both directions (`enterEdit` + pending-focus effect into the editor; `restoreGridFocus` back to the tab stop).

**2. Cell-scoped sessions (shipped).** `scope?: 'row' | 'cell'` (default `'row'`, the current model). Under `'cell'` a session is one cell, not one row: the double-clicked/Enter-entered cell alone mounts its editor, and the session key (Enter) commits just that cell, so the sink contract is unchanged. Internally the editable set is joined by an active-edit coord; `GridEditingCell` renders an editor only when its cell is the active edit (row mode keeps the has-rowKey test). Two session rules fell out of the narrowing and are load-bearing for increment 3, which moves the session by key rather than by pointer: the cell a session leaves commits as it leaves, even when the next cell is in the same row, and Escape discards that active cell rather than the row (the cells before it are already committed, so they are not the session's to drop). Blur commit stays increment 4's. This is where the spreadsheet feel starts; `'row'` remains right for form-like "edit this record" grids.

**3. Commit-and-move keys (shipped).** Spreadsheet muscle memory, on by default wherever the grid owns the session: Enter commits and moves the cursor down one row (re-entering edit under `scope: 'cell'` when the next cell is editable — a column-wise fill flow); Tab / Shift+Tab commit and move right/left within the row's editable cells, wrapping at the edges; F2 toggles edit on the cursor's active cell (the keyboard-only entry that needs no activation semantics); typing a printable character on the active cell enters edit seeded with that character (replacing the value, as spreadsheets do). Movement rides the existing cursor `moveTo`; the keys extend `editorKeys` and the cursor's key handler.

Two things found in increment 2's review are this increment's real groundwork, and both want settling before the keys land. First, the session's key surface is split: increment 1 hoisted Escape onto the table (`sessionEscape`), where every editor inherits it, but Enter stayed inside each inferred editor through a `commitRow` prop, and an `editCell` slot commits only by calling `ctx.commit` itself. Commit-and-move needs `moveTo` and `enterEdit`, which no editor can reach — so hoist Enter and Tab to the table surface as Escape already is, rather than thread four callbacks through `GridEditInputProps` and still leave slots behind. Second, `activeEdit` rides the shared editing context, and every data cell consumes it, so a session move re-renders the whole mounted window to change two cells. Row scope flipped that context twice per row; cell scope flips it once per cell, and increment 3 makes a cell move a keystroke rather than a double-click. The fix is the pattern `GridNavCell` already uses — the coord in a small external store, each cell subscribing to its own flag through `useSyncExternalStore` — and the bench that would show it (`grid-editing.bench.tsx` measures only the at-rest mount) does not exist yet.

*As built.* Three commits, groundwork first. (1) Enter hoisted onto the table beside Escape as one `sessionKeys` handler, with one resolver (`sessionTarget`) mapping a press to the session — the row from the `<tr>` or the held row, the column only from an open editor's cell. `commitRow` is gone; an `editCell` slot inherits Enter. The surface leaves Enter to an element that acts on it natively (`button, a[href], textarea, select, [contenteditable]`), which is what keeps the listbox trigger's Enter-to-open. Tab needed no handler in this step, because native Tab was the behaviour to keep. (2) `activeEdit` moved into a small external store (`GridActiveEditStore`); each `GridEditingCell` subscribes to a numeric flag through `useSyncExternalStore`. The hook still keeps the coord as state for its commit sweep and focus effect, and writes both at event time so cells and effects see one render; a layout effect mirrors the render-time clear of a stranded coord. The new `Grid · cell-scoped session move` bench (two cells of one row, alternating) went from 61 / 152 / 359 ms per move at 100 / 500 / 1,000 rows to 29 / 40 / 29 ms in this container. Those figures were a bench artefact, not a result; see the active-cell as-built note below. A move across rows still changes the editable set, which rides context, so it still renders the window. (3) The keys. Editor-side keys (Enter, Tab, F2) live in `sessionKeys`; tab-stop entries (F2, printable) in `useGridCursor` beside the existing Enter entry. Pure seams in the engine: `stepEditableColumn`, `seedFromKey`, `readKeyPress`.

Edge cases, as decided:

- **Last row.** Enter commits and ends the session; the cursor stays on the cell, focus on the tab stop. No wrap, no re-entry of the cell just committed.
- **No other editable cell / no editable cell.** Editability is per column, so every row has the same editable cells. Tab and Shift+Tab walk only editable columns (`readOnly` and display-only columns are skipped). With one editable column, Tab has nowhere to go and commits in place, as F2 does — otherwise it would leave the grid with the draft staged. F2 and type-to-edit on a non-editable cell do nothing (`enterEditAtCell` refuses it).
- **`readOnly` / declined row.** `readOnly` is a column property here, so it falls under the rule above. A controlled binding that declines the entry below: Enter is two writes (`endSession` then `enterEdit`), so the commit stands, the cursor lands on the declined cell, and focus stays on the tab stop.
- **Row scope.** Enter saves the row and moves the cursor down without entering (a record grid, not a fill flow). Tab moves focus between the row's already-open editors and commits nothing; the row commits when it closes.
- **IME.** A press with `isComposing` or `keyCode` 229 belongs to the input method: it neither seeds nor reaches any session key (Enter confirms the composition, Escape cancels it). Type-to-edit therefore cannot start an IME composition; enter with F2 or Enter first.
- **Modifiers.** Ctrl, Cmd, or Alt with a letter does not seed; AltGr (which reports Ctrl+Alt on some platforms) does. The editor-side move keys also leave a modified press to the editor. Space never seeds — it stays the cursor's select/activate.
- **What seeds.** Only an editor the grid infers: text takes any single character, number takes a digit (it cannot hold a lone `-` or `.`). The yes/no listbox and an `editCell` slot take no seed — the grid does not know a slot's value type — and open with F2, Enter, or a double-click.
- **Floating surfaces.** Every key goes through the same `claimedBySurface` deferral `sessionEscape` used (consumed press, portaled panel, `aria-expanded="true"`), so an open DatePicker or listbox panel keeps Tab and Enter.
- **The settle pair and Tab.** Tab from an editor commits and moves, so it cannot also reach the pair. The pair is now `tabIndex={-1}`, a pointer affordance; the keyboard settles through Tab, Enter, F2, and Escape. That keeps the listbox's WCAG 2.1.1 closure: Tab is its keyboard commit (the browser test that walked Tab into the pair now proves the Tab commit instead).
- **A slot with several controls.** As first built, Tab from any editor committed and moved, so an `editCell` slot with several focusable controls lost keyboard access to all but its first (WCAG 2.1.1). Tab now moves to the next tabbable element in the same cell when there is one, and the browser moves focus there. Only Tab from the last tabbable element commits and moves; Shift+Tab mirrors this from the first. The cell's tabbable elements are the matches of the shared `FOCUSABLE_SELECTOR`, less `tabindex="-1"` and hidden inputs (`tabStaysInCell`). An inferred editor has one tabbable element, so it behaves as before, and the settle pair stays `tabIndex={-1}`, so Tab from the listbox still commits. The browser test [`grid-edit-commit-move.test.tsx`](../../src/__tests__/browser/grid-edit-commit-move.test.tsx) proves the real Tab order through a two-input slot.

Not done here: the settle-control policy still lives in the leaf (increment 4 moved it into the hook), and the two API questions below stay open — the keys ship under `session: 'managed'` and read no cell binding.

**4. Blur / click-outside commit policy (shipped).** As first sketched: `commitOn?: ('enter' | 'blur' | 'clickOutside')[]` (default `['enter']`). `'blur'` commits a cell-scoped session when its editor loses focus to elsewhere in the grid; `'clickOutside'` commits when focus leaves the grid entirely — the forgiving mode where wandering off doesn't discard work. Needs care against the floating-overlay cases the cursor's blur guard already handles (`[data-floating-ui-portal]`): a `DatePicker` slot opening its popover must not read as blur.

*As built.* The array became one value: `commitOn?: 'explicit' | 'leaveEditor' | 'leaveGrid'`, default `'explicit'`. The options nest — focus that leaves the grid has also left the editor — so an array could only spell redundant or contradictory sets (`['clickOutside']` without `'blur'` means the same as with it), and `'enter'` was never optional: the keys commit under every setting. The names say what is left rather than which event fires, because a keyboard Tab-out leaves as surely as a click, and a window blur fires `blur` without leaving anything. Like `scope`, it needs `session: 'managed'`; elsewhere it is inert and warns in development. Three commits, groundwork first. (1) `gridHasFocus` took the nearest-grid rule `restoreGridFocus` already used (`isInGrid`), so a value set from outside no longer pulls focus out of a grid nested in a detail row. (2) Under a controlled `cell`, Enter's exit and entry became two rows writes, as they are uncontrolled, so a `rows` binding that declines the entry below keeps the commit (see the active-cell rules below). (3) The policy.

The mechanism is one focus-loss handler (`sessionLeave`) layered onto the table's `onBlur` ahead of the cursor's, the way `sessionKeys` layers onto `onKeyDown`, and absent under `'explicit'` — the default path gains no handler. Run one scenario per process, the benches stayed level at 100 / 500 / 1,000 rows: the uncontrolled move 8.4 / 17.6 / 30.5 ms before and 8.3 / 17.5 / 32.1 after, the controlled move 9.3 / 17.1 / 32.8 and 9.5 / 17.3 / 30.0, the Tab move 21.7 / 40.7 / 61.4 and 21.8 / 40.5 / 57.7, every pair inside the runs' ±4–9% margins. It reads the move's `relatedTarget` against the policy (`readLeave`):

- **What counts as the editors.** Under `'leaveEditor'`, an element inside this grid that `sessionTarget` resolves to an open editor's cell on the committing row: the held cell under cell scope, any open editor of the row under row scope. The settle controls sit in the held cell, so a move onto them is not a leave, and a press on discard discards. They also cancel their own `mousedown`, so a browser that does not focus a button on click (and would focus the tab stop instead) reads the same.
- **What counts as the grid.** The `<table role="grid">` by the nearest-grid rule, so toolbar and pagination chrome outside the table are outside, and so is a grid nested in a detail row.
- **Not a leave.** A move into a floating surface that the grid renders. As first built this read the DOM — the `inFloatingSurface` rule the session keys defer by (any `[data-floating-ui-portal]`, any `aria-expanded="true"`) — so focus moving into an unrelated popover or onto an open combobox elsewhere on the page never committed. Ownership is a React-tree question, not a DOM one: a portal rendered from inside the grid delivers its `focusin` to the table's `onFocus`, and an unrelated element does not. So a move to an element outside the table's DOM is held as a pending leave; the table's `onFocus` marks it owned when its target is that element; and a one-time `focusin` listener on the document settles it. The browser fires `focusin` in the same task right after `focusout`, and React's own listener sits on the root or portal container, below the document, so the document listener always runs after `onFocus` — in jsdom and in Chromium alike. A microtask was the other candidate and is not reliable: after a real click the browser runs a microtask checkpoint between the two events. A move within the table's DOM keeps the nearest-grid rule. `inFloatingSurface` stays for the key deferral, where it is right, because a key reaches the table only from its own tree. A window blur: a focus loss with no `relatedTarget` while `document.hasFocus()` is false. The grid's own reseat onto the tab stop (Enter, F2, Escape, a Tab move), which runs under a guard flag — without it, Escape's reseat would commit the draft it is about to discard.
- **A leave from a surface.** A focus loss inside a portaled panel reaches the table through the React tree, so a `focusout` whose target is outside the table's DOM is from the grid's own surface; it counts as starting inside the editors (and the grid), so picking a date and then clicking away still commits.
- **A press in a surface.** The cursor's click-to-seat `mousedown` on a cell pulled focus onto the table for any press that reached the cell — including one in the cell's own portaled listbox options, through the React tree — which under `'leaveEditor'` ended the session before the pick staged. It now stands down for a press whose target is outside the cell's DOM. [`grid-edit-commit-on-listbox.test.tsx`](../../src/__tests__/browser/floating-ui/grid-edit-commit-on-listbox.test.tsx) proves the listbox pick and the unrelated-portal commit in the real engine.
- **The commit.** `exitSession(rowKey, 'save', reseat: false)`: Enter's exit without the focus reseat or the cursor move. Enter does not gate on `validate` — it ends the session and the sweep sends refused cells to `onReject` — so a leave does the same. Under a controlled `cell` the leave asks for `null` like any exit, without the blur flag, so a consumer can decline it. The committing row is the row the focus loss came from, else the session's held row.
- **The settle pair.** Whether a cell shows it is now `settleControls(rowKey, columnId)` on the session, decided in the hook and read by the cell with its store flag: `'both'` on the held cell, `'discard'` there under `'leaveEditor'` (a move away saves, so save is redundant), `'none'` elsewhere. That closes the open item below and leaves increment 8 a hook-side answer.

Chosen rather than specified: under `'leaveEditor'` a pointer move to another cell ends the session on `mousedown` (focus goes to the tab stop) and the double-click starts a new one, so a consumer sees `null` and a rows write between the two cells where `'explicit'` reports a direct move. Jsdom covers each option under both scopes, the exemptions, validation, window blur, a controlled cell, and the inert warning ([`grid-editing.test.tsx`](../../src/__tests__/modules/grid-editing.test.tsx)); the real focus moves — a click outside, Shift+Tab out from the tab stop, a click on another cell, a press of discard, and a `DatePicker` slot's calendar — are in [`grid-edit-commit-on.test.tsx`](../../src/__tests__/browser/grid-edit-commit-on.test.tsx) and [`grid-edit-commit-on-date-picker.test.tsx`](../../src/__tests__/browser/floating-ui/grid-edit-commit-on-date-picker.test.tsx). The date picker case proves the surface exemption only through Tab: its day cells keep focus on the input, so a pointer pick never moves focus at all.

**5. Async / optimistic commit (shipped).** `onCommit` may return a `Promise`: the grid renders the committed cells in a pending state (subtle shimmer + `aria-busy`), settles on resolve, and on reject restores the drafts and re-enters the row/cell in edit with a per-cell error — the `validate` error surface reused for server rejections. `CellChange` stays the unit, so partial acceptance (resolve with the rejected subset) is expressible. The seam is in place: each record of the session's draft store (`GridDraftStore`) carries a `status`, which is `'staged'` alone today. This increment adds `'pending'` and a settled state to the same records, so an in-flight draft keeps its cell address, and a rejected one is already where the editor that mounts again reads it.

*As built.* The sink is `(changes) => void | Promise<void | GridCellRefusal[]>`, with `GridCellRefusal = GridCellRef & { error?: string }` the one new export. A thenable return is async; anything else keeps the synchronous path, which is why the existing suite passes unchanged. Resolving with nothing or `[]` accepts the batch, a list refuses the cells it names (a name outside the batch is ignored), and a rejection refuses the batch with the reason's `message` when that is a non-empty string, else `Change not saved`. The settled state needed no status of its own: an accepted record leaves the store, and a refused one goes back to `'staged'` carrying `error`.

- **The records.** The sweep takes the closed records as before, and hands an async batch's changed-cell records back to the store as `'pending'` (`pend`), the same objects at the same address. `take` skips a pending record, `stage` ignores a write to one, and a discard (`unstage`, `unstageRow`) keeps it, because a batch in flight is not the session's to drop. `settle` acts only on the exact record it pended, so a late settle cannot touch a newer draft. A refused record keeps its value; the next `stage` clears its error, and the editor clears the message with it.
- **The pending cell.** `GridEditingCell` reads its draft ahead of the session flag: pending wins over editing, so a pending cell never mounts an editor, even in a row the consumer holds open. The active-edit store gained `notify`, so a status change reaches each cell through the flag it already subscribes to; a keystroke still notifies nothing. The cell shows the column's display over a copy of the row with the committed value in its `field` (a consumer that applied it optimistically needs no copy), writes `aria-busy` on the gridcell in a layout effect as `GridNavCell` writes `data-active`, and pulses through `k.edit.pending`, the `body.settling` pair (`motion-safe` pulse, `motion-reduce` 50% dim) at cell size.
- **No entry.** `enterEdit` refuses a pending cell, which covers the double-click, Enter, F2, and type-to-edit alike, so two batches for one cell cannot be in flight. Tab steps past a pending cell (`stepEditableColumn` takes a `blocked` predicate), and commits in place when nothing else is open to it. Enter onto a pending cell below commits and moves the cursor there, with focus on the tab stop, as a declined entry does.
- **The refusal.** Under row scope the refused row returns to the set through `onRowsChange`. Under cell scope the session holds one cell, and the user has usually moved on, so a refused cell is marked `reopened`: it mounts its editor beside the session, with no settle pair, and the sweep leaves it until the session holds the cell, when the mark goes. Focus into the held editor moves the session onto it (`resumeCell`, a `focusin` listener), so the keys and the pair then act on the cell that has focus; F2, Enter, or a typed key on the tab stop enter it too, and a typed seed replaces the draft there, because the editor is already mounted. Neither path moves focus by itself. A refused draft that closes unedited commits again: a save is a retry.
- **Announcements.** One polite message per settled batch (`describeSettle`): `2 cells updated`, `1 cell not saved`, or both joined. The synchronous path still announces at the sweep.
- **Unmount.** A mounted flag drops a settle that arrives after the grid unmounts; the rejection is handled, so nothing surfaces as an unhandled error.
- **`onReject`** stays the `validate` channel. A server refusal keeps its value and shows its own error, so it does not call it.

Chosen rather than specified: the held editor under cell scope, rather than moving the session onto a refused cell and unmounting the editor that has focus; the retry on an unedited close; Tab skipping pending cells; the wording above.

A refused draft drops, with a polite `N changes discarded` (`describeDiscard`), when nothing will reopen it. As first built, a controlled `rows` that declined the row-scope reopen left the refused drafts staged against a closed row, and the sweep of the next unrelated transition sent them again — the late-write hazard #1240 closed, back through another door. The decline is now read as the consumer's choice: the settle records the row it asks to reopen and forces a render, and an effect after it drops the refused drafts of a row that is still closed. A consumer that applies the write later than the event that reports it reads as a decline, the same rule the `cell` binding keeps. The held cell of a cell-scoped session drops the same way when the consumer closes its row, and when its row leaves the grid's `rows`, at the next sweep rather than at unmount. Only a consumer close counts: the grid records the rows it closes itself (a session exit, an acquired row left behind, a controlled transition), so an Enter or F2 that ends the session keeps the held cell. The deleted-row read cannot tell a deleted row from one on another server page, so a held cell paged away drops too, where #1240's commit-from-snapshot rule keeps an ordinary draft; a held editor cannot mount on another page, and a draft that waits for it would wait forever. No development warning: the module warns for a configuration that cannot work, and a decline is a valid consumer choice, which #1240 also chose not to warn for. The pending display's row copy keeps the row's prototype and own property descriptors, so a class row's methods and getters still render; a private class field does not copy. Jsdom covers the pending state and its entries, accept, partial and whole refusal with the fallback message, the re-open under both scopes without a focus move, the error clearing, discard, the held cell's resume and seed, concurrent batches in one cell-scoped session, and the late settle ([`grid-editing.test.tsx`](../../src/__tests__/modules/grid-editing.test.tsx)); the visible pulse is in [`grid-edit-async-commit.test.tsx`](../../src/__tests__/browser/grid-edit-async-commit.test.tsx). The bench gained `Grid · cell-scoped Tab commit`, which stages a value and commits it with Tab through a sync sink and through an async one that accepts at once, awaiting the settle. Run one scenario per process at 100 / 500 / 1,000 rows, it read 21.6 / 32.4 / 54.4 and 24.8 / 31.5 / 61.4 ms sync, and 17.8 / 34.2 / 58.9 and 20.8 / 30.3 / 63.0 ms async. **6. Undo / redo** (backlog). A value-based history of committed batches wrapping the sink: Ctrl/Cmd+Z re-emits the inverse batch (old values, captured at flush time from the live rows), Shift+Z / Y replays. Purely a layer over `onCommit` — the consumer still owns the data — bounded (e.g. 100 entries) and cleared when `rows` identity changes wholesale (a refetch).

**7. Range selection, fill handle, paste** (backlog, own plan when picked up). The cursor grows an anchored rectangular range; fill drags the active cell's value/series across it and paste maps a clipboard TSV block through the same per-column `validate` + `CellChange[]` path — the batch just spans rows. Depends on nothing above except the cursor; listed here because its commit semantics must stay the one sink.

**8. New-row entry (shipped).** A pinned blank editor row (top or bottom) whose commit emits an `onRowAdd(values)` rather than `CellChange[]` — the one place the sink doesn't fit, so it's a sibling callback. Furthest out; needs the pinned-row primitive from the row-model backlog.

*As built.* No pinned-row primitive existed, and none shipped: the row is a slot the grid owns, rendered for the new-row editor alone, with no public row-pinning API. A public primitive would have to answer what a pinned *data* row means to sort, filter, selection, export, aggregation, and the editable set, and nothing here needs those answers; a blank editor row needs only to sit outside all of them. Building the primitive first would have spent the increment on a row-model decision this feature does not exercise, and the slot does not foreclose one later — a primitive can take the slot over, since nothing outside the module names it.

`newRow` sets the position and `onRowAdd: (values) => void | Promise<void | GridCellRefusal[]>` takes the row, a sibling of `onCommit` because a new record has no row key yet. `values` maps each editable column's `field` (the column id where there is none) to its drafted value, and holds only the cells that hold one. No new export: `values` is a `Record<string, unknown>`, and the refusal type is #1242's.

- **Gating.** The slot needs `session: 'managed'` and `onRowAdd`. Under `'manual'` there is no key surface to add from, so the grid renders no slot and warns in development, as `scope` and `commitOn` do; `newRow` without `onRowAdd` warns and renders none too. A rule for `'manual'` was the other candidate and bought nothing: every key the slot answers to lives on `sessionKeys`, which `'manual'` does not mount.
- **The slot.** A `<tbody>` of its own beside the data body (`GridNewRow`), so no body branch — plain, virtualized, grouped, empty — has to carry it, and no transform reaches it: it is not in `rows`, the engine, the virtual window, selection, or export. Its cells stick to the scroll container's edge (`k.newRow`, one z-layer over a pinned data cell and under the sticky header, one more for a pinned column of the slot); at the top they stick below a sticky header, whose height the slot measures into `--grid-new-row-top`. It shows over the empty state, where adding the first row is the point, and not over the loading skeleton or an error. A sticky slot covers the rows that scroll under it, so the cursor's `scroll-margin` (`obscuringInsets`, WCAG 2.4.11) adds the slot's height at its edge, and a page move keeps the cursor cell in view. The slot is found through `table.tBodies`, because a selector over the table read every cell of the body on each cursor move and nearly tripled the Tab move at 1,000 rows; a margin is written only when it changes, because each write sets the `style` attribute again.
- **The key.** The drafts live in #1240's store under `NEW_ROW_KEY`, a `unique symbol`, so no `getKey` result can collide with it; the store's key type widened to `GridDraftKey`. The commit sweep skips the key, and it never reaches `rows`, `cell`, `onCommit`, or `onReject`. The cursor names the slot's row `NEW_ROW_INDEX` (`-2`, clear of the `-1` an unknown row reads as), a fixed index, so a cursor on the slot stays there as rows are added beneath it.
- **Always editors.** Each editable cell of the slot mounts its editor at all times, rather than entering through the managed session. Entering through the session would put the slot's key into the `rows` set and the `cell` binding, both keyed by the consumer's row keys and reported through `onRowsChange` / `onCellChange`; the reserved key would leak into both, and a slot entry would end the data session it sits beside. Always-mounted editors keep the slot out of both bindings, so a data session and a half-filled slot coexist. The editors are `GridCellEditor` itself, keyed by a generation counter that an add, an Escape, or a typed entry raises, so each mounts again and reads the store. The inferred editor kind reads the first source row with a value in the column, else text.
- **Keys.** The slot's keys run on the table's key surface ahead of the data session's (`useGridNewRow.keys`), after the same floating-surface and IME deferral. Enter adds, unless the focused element owns Enter natively; F2 puts focus back on the tab stop with the cursor on the cell; Escape clears the slot's drafts and does the same. Tab is native: the slot's editors and its Add control are in the tab order, and Tab past the last leaves the row, so there is no wrap and no trap. On the tab stop, Enter and F2 on a slot cell focus its editor, and a printable key seeds an inferred editor there as type-to-edit does.
- **Add control.** The #1238 settle controls host it: `GridSettleControls` gained an `'add'` answer, which the slot passes for its last editable cell, and the editor renders it as an Add button (`Add row`) where the pair would sit. Unlike the pair it is in the tab order, because Tab commits nothing in the slot, and it is the keyboard route to an add from a listbox or a slot that keeps its own Enter.
- **Commit.** An add with no value does nothing and announces nothing; an empty text, `null`, and no entry are no value. `validate(value, values)` runs per drafted cell, and a refusal blocks the add (`Row not added, 1 cell refused`); the slot's editors run `validate` live only once a cell holds a value, so an empty slot shows no errors. A sync return accepts: the drafts clear, focus goes to the first editable cell, and `Row added` announces. An async add reseats focus on the tab stop, holds the drafted records `'pending'` in the store, and renders every cell of the slot pending, with `aria-busy` and the Add control `aria-disabled`; a second add waits. A refusal (a resolved list, whose `rowKey`s are ignored, or a rejection) stages every drafted cell again, with the named errors, and focus does not move; a refusal that names an undrafted editable cell gives it an empty draft that carries the error, for a required field. An accepted async add moves focus only when focus is still in the grid (WCAG 3.2.1).
- **`commitOn`.** Leaving the slot never adds it, under any setting. A half-filled new row must not create a record, so an add is always explicit; the asymmetry with the data cells is deliberate and documented on `newRow`.
- **Accessibility.** The slot is a real row: `aria-label="New row"`, editors labelled `Edit Name, new row`. It counts in `aria-rowcount` where grid semantics set one. At the top it takes the first index after the header rows and the data rows shift down one; at the bottom it takes the index after the last data row, before a grand-total row, and none under an indeterminate count. The cursor's row order gains the slot first or last (`toPosition` / `fromPosition`), so the arrows, Home/End, PageUp/Down, and a Tab into the grid all reach it; `onActiveCellChange` reports `null` on it, as it is no data cell.

Chosen rather than specified: always-mounted editors over session entry; the column id as the key of a fieldless column; blank drafts as no value; refusals on undrafted cells; Escape reseating focus; the Add control in the tab order; the slot over the empty state; the null report on the slot. A pending cell of the slot shows its value as text, not through the column's `cell`, because the renderer reads a whole row and the slot holds only the drafted fields. Jsdom covers both positions, sort / filter / pagination exclusion, the values, the empty add, `validate`, the pending block, both refusals, Escape, each `commitOn`, the ARIA indexes, names, and labels, the cursor's arrows and entries, and the warnings ([`grid-editing.test.tsx`](../../src/__tests__/modules/grid-editing.test.tsx)); the sticky pinning in a scrolling virtualized body, the cursor's scroll margins, and the real Tab order are in [`grid-edit-new-row.test.tsx`](../../src/__tests__/browser/grid-edit-new-row.test.tsx).

The bench gained `Grid · editable new row`, the at-rest mount with the slot at the bottom. Run one scenario per process, base and change in turn, it read 182.0 / 790.1 / 1,688.2 ms at 100 / 500 / 1,000 rows on the base, where the slot is inert, and 180.2 / 812.1 / 1,677.0 with it, inside the runs' ±6–17% margins: one row of editors is lost in a thousand rows of cells. The same pairs held the rest level: the initial render 185.2 / 758.4 / 1,684.6 and 180.8 / 788.4 / 1,657.7 ms; the uncontrolled move 7.7 / 10.8 / 18.2 and 7.7 / 10.8 / 19.6; the sync Tab commit 22.1 / 25.2 / 39.0 and 21.1 / 25.4 / 42.6; the async 17.9 / 38.1 / 56.8 and 17.1 / 35.9 / 45.6; the keystroke 0.57 / 0.83 / 1.17 and 0.59 / 0.82 / 1.21. ## Accessibility cluster — cell scope removes row scope's compensations

A WCAG 2.2 AA review of increment 2 found five, ranked. The first two should gate shipping `scope: 'cell'`; the rest are older than it, but cell scope is where each stops being covered by something else.

**Closed: the listbox editor has a keyboard commit path.** The boolean editor deliberately leaves Enter to the listbox's own open/select, and row scope covered that by mounting a sibling text or number editor to save from. Cell scope mounts one editor, so that sibling is gone. The value commits only by moving the session to another editable cell, which from inside the editor takes several Shift+Tab hops out through the header's resize and menu controls, unannounced. When the boolean column is the only editable one, the value is uncommittable by any route: `enterEditAtCell` refuses a non-editable column, so no move exists to flush it. The same gap covers an `editCell` slot that does not call `ctx.commit`. Hoisting Enter onto the table's key surface — the fix this plan first named — does **not** close it. Enter on a closed listbox trigger is how the listbox opens, verified in [`grid-edit-listbox-enter.test.tsx`](../../src/__tests__/browser/floating-ui/grid-edit-listbox-enter.test.tsx), so a hoisted Enter would contend with the editor rather than serve it. The route to a keyboard commit for this editor is a control that owns no editor's keys, so that is what shipped: a save and a discard control beside the editor on the cell a cell-scoped session holds. Tab reached them in real tab order and Enter on the save committed, both proven in the browser project. Increment 3 moved the keyboard commit to Tab itself (commit and move, or commit in place with no other editable cell) and took the pair out of the tab order; the browser test now proves the Tab commit. Row scope shows no pair — its settle control is the consumer's row action, and a pair per cell would put two save targets on screen at different scopes.

**Retracted: one Escape does not abandon the cell while a listbox is open.** The review reported that `sessionEscape`'s deferral misses this library's own `Listbox`, because its panel appeared to render inline rather than portaled and its expanded trigger is the focused option's sibling. That was an artifact of the jsdom suite, whose `@floating-ui/react` mock renders `FloatingPortal` inline and stamps no `data-floating-ui-portal` — so the guard reads as missing under jsdom and only there. Against the real engine the panel is portaled, the guard fires, and the first press closes the panel with the session intact. Proven in [`grid-edit-listbox-escape.test.tsx`](../../src/__tests__/browser/floating-ui/grid-edit-listbox-escape.test.tsx), which lives in the browser project because jsdom structurally cannot assert it. The lesson generalizes: any claim about floating-surface behaviour taken from the jsdom suite is untrustworthy by construction.

**No focus indicator while an editor is open (2.4.7).** The editing branch bypasses `GridNavCell`, whose unmount strips `data-active`, so the editing cell carries no cursor ring. Harmless while focus is inside the editor. Not harmless after Tab: focus leaves the grid with the editor still mounted and its draft uncommitted, and tabbing back seats the cursor on a cell with no visible indicator anywhere in the grid. Row scope hid this because Tab moved to the next editor in the row; under cell scope Tab is the first exit a user reaches for.

**A display-only column advertises as editable (1.3.1, 4.1.2).** `aria-readonly` is written only for an explicit `readOnly`, so a column with no `field` and no `editCell` — not editable by `isColumnEditable` — carries nothing. Under row scope a screen-reader user learned the editable set by opening a row and reading which cells became editors. Cell scope mounts one, so trial and error on each cell is the only discovery channel left. Gating the attribute on `!isColumnEditable(col)` states it.

**The commit announcement does not say what saved (4.1.3).** `1 cell updated` was written for a row save. Under cell scope it fires on every cell-to-cell move, queued behind the focus change into the next editor, naming neither column nor row — so the user hears it while already somewhere else. Increment 3 makes that move a single keystroke.

The a11y corpus holds one editable grid, row-scoped and at rest, so axe never sees a narrowed row or a mounted editor. A `scope: 'cell'` case with a session open is cheap and would cover the fourth finding.

## Carried into increment 3

Three things the settle pair leaves for the increment that adds commit-and-move keys, all cheaper to decide there than to retrofit. Increment 3 settled the first two and the bench note; increment 4 settled the third.

**Settled: increment 3 claims Tab, and Tab is how the settle pair is reached.** The table surface owns it: Tab commits and moves, and the pair left the tab order (see increment 3's as-built note). The pair closes the listbox's WCAG 2.1.1 gap on the strength of native tab order, asserted in the browser project. Increment 3 gives Tab and Shift+Tab to commit-and-move across a row's editable cells, hoisted to the table's key surface and prevented in the same shape as `sessionEscape` — which would take the only keyboard route to the one control the listbox editor has. Decide there which surface owns reaching the pair, rather than letting tab order decide by default, or the increment reopens the finding this one closed and the guarding test reads as stale rather than broken.

**Settled: the session is two records, and the keys will want one.** The resolver is written once (`sessionTarget`); the two records stay. `activeEdit` names the held cell under cell scope; `sessionRowRef` names the held row and how the session came by it, under both. That split is honest — provenance belongs to the row, identity to the cell — but every key increment 3 adds asks the same question `sessionEscape` already asks, resolving an event to the live session through a DOM walk with a ref fallback. Write that resolver once when the second caller arrives.

**Settled: whether a session shows a settle control is decided in the hook.** `GridEditingCell` derived it from `isSameCell(activeEdit, cell)`, which was that day's only policy rather than the policy itself. Increment 4's `commitOn` made the pair conditional (a blur-committing session needs discard, not save), and increment 8's pinned new-row editor wants a pair while holding no `activeEdit` coord at all — `isSameCell` can never say yes for it. The session now carries `settleControls(rowKey, columnId)`, which the hook answers (`'both'`, `'discard'`, or `'none'`) and the cell renders; the cell's store flag is that answer, so a session move still renders two cells.

Also open: the settle pair is grid chrome the consumer can neither replace nor suppress, and for a cell-scoped `editCell` column it renders beside a slot whose `ctx.commit` and `ctx.cancel` are the designed settle route — so a slot that renders its own save shows two at the same scope. And the editing benches could not see any of this: `grid-editing.bench.tsx` set no `session`, no `scope`, and no editing row. Increment 3 added the session-move scenario. A scenario that opens a session and moves it is what would catch a regression in the pair's mount cost, measured at about +0.8 ms against a session move already dominated by whole-grid context fanout.

## Correctness cluster — a draft can outlive its editor (fixed)

Found by an adversarial state-machine sweep during increment 2 and reproduced, but **not** introduced by it: each predates the trigger increment. The first three share one cause. A cell's draft is staged against `rowKey` and `columnId`, and the commit sweep asks whether the session still holds that cell — but an editor also unmounts for reasons the session knows nothing about.

**Fixed: a draft survived its editor and re-committed behind the next one.** Page away from an editing row and back, or let a consumer drop the row from `rows` and re-add it, and the editor re-seeded from the row while the draft was still staged. Saving then wrote the old draft over a cell the user last saw holding the original value. The editor now reads the staged draft as it mounts, so the user sees the value that commits.

**Fixed: a draft was dropped when its row left the render.** `flushRow` resolved the row through `rowKeys.indexOf`, and the sweep had already taken the draft out of staging. #1230 moved the commit path onto the grid's own inputs (`GridEditSource`), so a paged-away row commits; this change adds the grid-owned session cases and the virtualized case, in the browser project.

**Fixed: a draft was dropped when its column left the render.** The column axis of the row case, fixed by the same #1230 change: `flushRow` walks the drafts and resolves each column against all columns, not the visible ones.

**Fixed: a declined entry kept its pending focus.** The focus intent cleared inside an effect keyed on the session, so a controlled binding that refused a grid entry left the intent to steal focus at the next unrelated open. #1230 moved the drop into an effect that runs after each render, and #1236 added the guard test.

*As built.* The decision the first three needed: the sweep treated a closed editor as a commit, which is right when the session closed it and wrong when the render did. The rule is now that a draft belongs to the session. It lives exactly as long as its cell is open — under `scope: 'row'` its row is in the set, under `scope: 'cell'` it is the held cell — and an editor's mount or unmount, whether from virtualization, pagination, column hiding, grouping, or a re-key, never commits and never drops it. The drafts live in one session-owned store keyed by cell (`GridDraftStore`, engine), each record `{ value, status }`. The store has no subscribers, so increment 2's property holds: a keystroke renders the editor that took it and nothing else, which a render-count test guards. The sweep takes the closed records, resolves each row by key against the grid's `rows` and each column against all columns, and hands the result to `validate`, `onReject`, and `onCommit` as before. Each record also keeps the row object its first write staged against. A row that is no longer in `rows` when its session closes commits against that snapshot, for `validate(value, row)` and for the unchanged check, in the same batch and under its key. Under server-side pagination a row on another page is absent from `rows`, and the grid cannot tell it from a deleted row, so it never drops the edit: a consumer that deleted the row ignores the change. A first build discarded such drafts with an announcement and a warning; both are gone, because the commit is the normal case under server pagination rather than a mistake to report. A re-key resolves the same way: the drafts commit under the old key, from their snapshots. The store also ignores a write to a cell the session does not hold open — a NumberInput blur after a consumer's `rows` save, say — which would otherwise commit on the next unrelated sweep. A cell the last sweep still saw open counts as open, so a controlled move's layout-effect blur still stages before the sweep commits the cell it leaves. Escape and the settle discard drop the drafts the session closes, mounted or not, because the discard reads the store rather than the editors. The `status` field is increment 5's seam; see there. The new `Grid · row session keystroke` bench (one row-scoped session, one editor typed into) guards the keystroke path. Run one scenario per process, the benches stayed level at 100 / 500 / 1,000 rows. The uncontrolled move measured 6.8 / 12.1 / 28.1 ms and 8.4 / 15.3 / 27.6 on two base runs, against 8.4 / 17.2 / 27.7 and 8.3 / 14.0 / 35.1 after; the controlled move 8.5 / 13.5 / 26.4 before and 8.9 / 12.8 / 29.8 after; the Tab move 19.4 / 31.3 / 59.5 and 19.0 / 32.5 / 52.4. The keystroke read 0.57–0.64 / 0.88–0.92 / 1.16–1.44 ms over four base runs and 0.61–0.65 / 0.87–0.94 / 1.39–1.41 after. A first build that allocated a fresh record on each keystroke read 0.69–0.76 ms at 100 rows, outside that spread, so a keystroke now rewrites its cell's record in place. With the row snapshot and the open-cell check on each write, the keystroke read 0.63 / 0.95 / 1.22 and 0.54 / 0.94 / 1.44 ms.

## Open API questions — settled

Two shapes on the public surface were worth settling before increment 4, and both were a maintainer's call rather than a refactor. Both are now settled.

**Settled: the setting names the session's owner.** It shipped as `trigger: 'manual' | 'doubleClick'`, which named a gesture while it gated who owns the session: cursor-Enter entry, the table-level Escape, an `editCell` slot's `commit`, the whole of `scope`, and after increment 3 the commit-and-move keys, F2, and type-to-edit. It is now `session: 'manual' | 'managed'`, with `'manual'` still the default. The package is private and nothing outside it wrote the old name, so the rename carries no alias. Internally the flag is `managed`, read once from `session === 'managed'`.

**Settled: a cell-scoped session binds its cell.** The question as surfaced: `rows` stays the only controllable, and under `scope: 'cell'` it becomes a forced-singleton row set while the session's real identity — the active cell — is internal state a consumer can neither read nor decline. A move between cells of one row emits nothing, which is why `session`'s TSDoc now scopes its source-of-truth claim to which rows edit. Increments 3, 4, and 5 all need to name a cell from outside. Adding `activeCell` / `defaultActiveCell` / `onActiveCellChange` later leaves `rows` as a permanent second binding for one session; adding it with increment 3 does not.

*As built.* The three props landed on `GridEditableConfig` as `cell` / `defaultCell` / `onCellChange`, not under the names above: `GridDataProps.onActiveCellChange` already reports the keyboard cursor's cell, and `cell` pairs with `rows` inside `editable`. They go through `useControllable`, as `rows` does, with `GridCellRef = { rowKey, columnId }` as the value (no exported type had that shape; `GridCellChange` stays as written, because an intersection would change its emitted `.d.ts`). Outside `managed` + `cell` the binding is inert and warns once in development. The rules:

- **One order of writes.** The cell reports first, then the rows. An entry into a closed row emits `onCellChange(cell)` and then `onRowsChange`; an exit emits `onCellChange(null)` and then `onRowsChange`. Enter is an exit and an entry, so it reports `null` and then the cell below. Under a controlled `cell` the rows write waits until the consumer applies the cell, which is what makes a decline clean: a declined move writes neither binding, the held cell stays open, and nothing commits. Enter is the exception, because it means "commit, then move": declining the move must not decline the commit. As first built, a controlled `cell` folded Enter's exit and entry into one rows write, so a `rows` binding that declined the row below declined the exit with it and nothing committed — while the uncontrolled path, two writes, kept the commit. The transition now writes an exit that comes with an entry into a closed row as two rows writes, exit first (`writeRowsPlan`), so both modes agree: Enter commits the held cell and reports `null`, and a declined entry leaves the cursor on the declined cell with focus on the tab stop.
- **One transition path.** A controlled value is acted on by a layout effect, whether the grid asked for it or the consumer set it. A value the grid asked for keeps its focus and seed intents and carries out the exits and discard recorded with the request; any other value is a set from outside. The rows follow a grid entry's rules — the new cell's row opens, an acquired row closes as the session leaves it, and `null` closes the held row, as a save does. A request forces one render (a counter), so a decline is seen in the same event rather than lingering as an intent that a later, unrelated set would honour.
- **No row widens for a render.** While a controlled value waits for its row, the render reads the settled cell, not `null`, so the held row never flashes row-shaped between the cell write and the rows write.
- **Focus.** The entered editor now claims focus itself as it mounts or comes to be held (`claimFocus` on the session), because a controlled move along a row mounts its editor one pass after the hook's effects run. A set from outside moves focus only when focus is already in the grid (WCAG 3.2.1); a grid-asked move blurs the leaving editor where the uncontrolled path does — on a key move or an exit — and not on a double-click, which kept the controlled bench level with the uncontrolled one.
- **Not editable.** A cell of an unknown row, or of a `readOnly` or display-only column, reads as `null`, mounts nothing, and warns once. Editability is checked when a consumer value arrives, not continuously, so a column that locks mid-session behaves as it did.
- **Stranding.** A controlled cell whose row the consumer closes reads as `null` and reports nothing; it reads again if the row reopens, because the value is the consumer's. An uncontrolled coord that strands stays dropped, as before — now through a mask rather than a render-time state write, since clearing a controllable would emit from render.
- **Mount.** An initial cell (controlled or default) seeds `defaultRows` with its row, so the mount reports nothing; under a controlled `rows` that lacks the row the cell stays closed.

The bench gained a controlled variant of the session move. Run one scenario per process, the uncontrolled move measured 7.8 / 16.7 / 34.1 ms at 100 / 500 / 1,000 rows before and 7.5 / 14.6 / 34.3 after; the controlled move 8.3 / 13.9 / 33.5. Increment 3's "flat 29 / 40 / 29 ms" was an artefact of the file: every scenario's persistent tree mounts at collection time into one document, so each scenario's figure depends on what else the file mounts.
