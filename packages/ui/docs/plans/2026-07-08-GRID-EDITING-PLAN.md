# Grid Inline Editing — Feature Plan — 2026-07-08

What the `editable` feature is trying to be, what ships today, and the increments that take it the rest of the way. The [Grid roadmap](../../src/modules/grid/ROADMAP.md) retired editing from its tracker and named this doc the successor, so status lives here alongside the design.

## Thesis

`editable` is heading at **spreadsheet-grade inline editing without a form detour**: the user edits values where they read them, with the pointer and keyboard ergonomics of a spreadsheet (double-click or type to edit, Enter/Tab to commit and move, Escape to bail) and the data discipline of a form (typed editors, validation, batched commits the consumer applies). Everything layers on the one existing model — the controllable editable-row `Set<key>` plus the `CellChange[]` commit sink — rather than introducing a second editing state; each increment widens who drives that set (consumer → grid) and how narrowly a session scopes (row → cell), never how values commit.

## Current state (verified in tree, 2026-09-23)

- **Row-session model.** A row key in the `editable` set puts every editable cell of that row into edit mode at once (`use-grid-editing.ts`, `grid-editing-cell.tsx`). A column is editable when it has a `field` or an `editCell` slot and isn't `readOnly` (`isColumnEditable`).
- **Staged drafts, batched flush.** Edits stage into a grid-held ref (no per-keystroke render); a row leaving the set flushes its changed, `validate`-passing cells as one `onCommit` batch, announced politely (WCAG 4.1.3). Escape reverts a single cell.
- **Editors.** Inferred from the value's primitive type (text / number / yes-no listbox, `grid-edit-inputs.tsx`) or supplied per column via `editCell` — a render-prop slot over `onValueUpdate` / `commit` / `cancel`; no editor components are exported. No editor wires a session key of its own: under a grid-owned session every key lives on the table's key surface (`sessionKeys`), so a slot inherits them all.
- **Cursor.** An editable grid always carries the keyboard cursor (`useGridCursor`: `cursorEnabled = navigable || editing`) — a single tab stop with `aria-activedescendant`, arrows/Home/End/PageUp/Down movement, and Enter/Space activation.
- **Grid-owned sessions.** `editable.session: 'managed'` — entry on an editable data cell's double-click (through the grid's built-in cell double-click event, so `resolveCellContext`'s data-cell resolution and the interactive-content guard apply, and a consumer `onCellDoubleClick` still fires after) or on the cursor's Enter; the entered cell's editor takes focus once mounted. Enter and Escape from *any* editor — inferred, listbox, or `editCell` slot — are owned once on the table's key surface (`sessionKeys`, layered onto `navTableProps`): Enter commits unless the focused element owns Enter natively, as the listbox trigger does (see increment 3 for where it moves), Escape abandons the session's drafts, and both defer to an open floating surface (a consumed press, focus in a portaled panel, or an `aria-expanded="true"` trigger — that press closes the surface; the next abandons). Focus reseats on the grid's tab stop on exit; an `editCell` slot's `commit` also ends the session. Every transition flows through `rows`/`onRowsChange`, so a controlled binding can decline an entry. Default stays `'manual'` — no behavior change for existing consumers.
- **Cell-scoped sessions (shipped).** `editable.scope: 'cell'` narrows a grid-owned session to the entered cell: the row still enters the set, but `GridEditingCell` mounts an editor only for the cell the session names (`activeEdit`, held beside the set and derived against it, so a declined or withdrawn row drops the coord; the cells read it from an external store, one flag each, so a move along a row re-renders two cells). Entering another cell re-points the session — the cell it leaves commits, and a row the session acquired leaves the set — so a session that opened its own row commits one `CellChange` at a time. Narrowing a row the consumer had already opened is the exception: the editors that close with the narrowing commit together, which is why the sink's contract is the batch and never its first entry. One predicate carries the whole narrowing: `isCellEditing` (engine) answers which cell mounts an editor, which entry is the no-op of re-entering the cell already open, and which staged drafts the commit sweep must flush, so an editor's lifetime and its value's commit cannot disagree. The sweep reads that open state rather than diffing against the last render, which is why a consumer's save, a grid-owned exit, and a session moving on all travel one path. The session's surface names itself after the session rather than the row it used to be: `enterEdit(rowKey, columnId)` takes the cell in one address space and resolves the display coord where it is used, `endSession(rowKey, 'save' | 'discard')` is the one exit, and the context is `GridEditingSession`. `scope: 'cell'` without `session: 'managed'` is inert rather than wrong, so it warns in development like the module's other config mismatches. Escape drops the active cell's draft alone, because the cells before it already committed. The setting needs the grid-owned session; under `'manual'` the consumer names a row and never a cell, so the row's editors all mount as under `'row'`. Default stays `'row'`.
- **Commit-and-move keys (shipped).** On by default under `session: 'managed'`, in both scopes: Enter commits and moves down one row (re-entering under `scope: 'cell'`), Tab / Shift+Tab move along the row's editable cells with wrap, F2 toggles edit, and a printable key on the tab stop enters edit seeded with it. See increment 3's as-built note for the edge-case choices.
- **Active-cell binding (shipped with this change).** Under `session: 'managed'` and `scope: 'cell'`, the session's cell is a controllable of its own: `cell` / `defaultCell` / `onCellChange`, typed by the one new export, `GridCellRef`. `rows` keeps its meaning — the rows open for editing — and the grid keeps the two consistent. A controlled binding decides every move, the grid's own and the consumer's; see the settled API question below for the as-built rules. The cells still read the cell from `GridActiveEditStore`, so a controlled move along a row renders two cells.
- **Bindings that gate it.** Grouping and master-detail stand the cursor down but not editing; virtualization keeps editing (rows mount their editors when scrolled into the window).

## Design sketch — increments

Each increment is independently shippable, in dependency order. The `editable` binding grows options; the one export it gained is `GridCellRef`, the active-cell binding's type.

**1. Edit triggers (shipped).** `session?: 'manual' | 'managed'` as described above. Foundation for everything below: the grid can now begin and end a session itself, with focus management in both directions (`enterEdit` + pending-focus effect into the editor; `restoreGridFocus` back to the tab stop).

**2. Cell-scoped sessions (shipped).** `scope?: 'row' | 'cell'` (default `'row'`, the current model). Under `'cell'` a session is one cell, not one row: the double-clicked/Enter-entered cell alone mounts its editor, and the session key (Enter) commits just that cell, so the sink contract is unchanged. Internally the editable set is joined by an active-edit coord; `GridEditingCell` renders an editor only when its cell is the active edit (row mode keeps the has-rowKey test). Two session rules fell out of the narrowing and are load-bearing for increment 3, which moves the session by key rather than by pointer: the cell a session leaves commits as it leaves, even when the next cell is in the same row, and Escape discards that active cell rather than the row (the cells before it are already committed, so they are not the session's to drop). Blur commit stays increment 4's. This is where the spreadsheet feel starts; `'row'` remains right for form-like "edit this record" grids.

**3. Commit-and-move keys (shipped, this change).** Spreadsheet muscle memory, on by default wherever the grid owns the session: Enter commits and moves the cursor down one row (re-entering edit under `scope: 'cell'` when the next cell is editable — a column-wise fill flow); Tab / Shift+Tab commit and move right/left within the row's editable cells, wrapping at the edges; F2 toggles edit on the cursor's active cell (the keyboard-only entry that needs no activation semantics); typing a printable character on the active cell enters edit seeded with that character (replacing the value, as spreadsheets do). Movement rides the existing cursor `moveTo`; the keys extend `editorKeys` and the cursor's key handler.

Two things found in increment 2's review are this increment's real groundwork, and both want settling before the keys land. First, the session's key surface is split: increment 1 hoisted Escape onto the table (`sessionEscape`), where every editor inherits it, but Enter stayed inside each inferred editor through a `commitRow` prop, and an `editCell` slot commits only by calling `ctx.commit` itself. Commit-and-move needs `moveTo` and `enterEdit`, which no editor can reach — so hoist Enter and Tab to the table surface as Escape already is, rather than thread four callbacks through `GridEditInputProps` and still leave slots behind. Second, `activeEdit` rides the shared editing context, and every data cell consumes it, so a session move re-renders the whole mounted window to change two cells. Row scope flipped that context twice per row; cell scope flips it once per cell, and increment 3 makes a cell move a keystroke rather than a double-click. The fix is the pattern `GridNavCell` already uses — the coord in a small external store, each cell subscribing to its own flag through `useSyncExternalStore` — and the bench that would show it (`grid-editing.bench.tsx` measures only the at-rest mount) does not exist yet.

*As built.* Three commits, groundwork first. (1) Enter hoisted onto the table beside Escape as one `sessionKeys` handler, with one resolver (`sessionTarget`) mapping a press to the session — the row from the `<tr>` or the held row, the column only from an open editor's cell. `commitRow` is gone; an `editCell` slot inherits Enter. The surface leaves Enter to an element that acts on it natively (`button, a[href], textarea, select, [contenteditable]`), which is what keeps the listbox trigger's Enter-to-open. Tab needed no handler in this step, because native Tab was the behaviour to keep. (2) `activeEdit` moved into a small external store (`GridActiveEditStore`); each `GridEditingCell` subscribes to a numeric flag through `useSyncExternalStore`. The hook still keeps the coord as state for its commit sweep and focus effect, and writes both at event time so cells and effects see one render; a layout effect mirrors the render-time clear of a stranded coord. The new `Grid · cell-scoped session move` bench (two cells of one row, alternating) went from 61 / 152 / 359 ms per move at 100 / 500 / 1,000 rows to 29 / 40 / 29 ms in this container. Those figures were a bench artefact, not a result; see the active-cell as-built note below. A move across rows still changes the editable set, which rides context, so it still renders the window. (3) The keys. Editor-side keys (Enter, Tab, F2) live in `sessionKeys`; tab-stop entries (F2, printable) in `useGridCursor` beside the existing Enter entry. Pure seams in the engine: `stepEditableColumn`, `seedFromKey`, `readKeyPress`.

Edge cases, as decided:

- **Last row.** Enter commits and ends the session; the cursor stays on the cell, focus on the tab stop. No wrap, no re-entry of the cell just committed.
- **No other editable cell / no editable cell.** Editability is per column, so every row has the same editable cells. Tab and Shift+Tab walk only editable columns (`readOnly` and display-only columns are skipped). With one editable column, Tab has nowhere to go and commits in place, as F2 does — otherwise it would leave the grid with the draft staged. F2 and type-to-edit on a non-editable cell do nothing (`enterEditAtCell` refuses it).
- **`readOnly` / declined row.** `readOnly` is a column property here, so it falls under the rule above. A controlled binding that declines the entry below: Enter is two writes (`endSession` then `enterEdit`), so the commit stands, the cursor lands on the declined cell, and focus stays on the tab stop.
- **Row scope.** Enter saves the row and moves the cursor down without entering (a record grid, not a fill flow). Tab moves focus between the row's already-open editors and commits nothing; the row commits when it closes.
- **IME.** A press with `isComposing` or `keyCode` 229 belongs to the input method: it neither seeds nor reaches any session key (Enter confirms the composition, Escape cancels it). Type-to-edit therefore cannot start an IME composition; enter with F2 or Enter first.
- **Modifiers.** Ctrl, Cmd, or Alt with a letter does not seed; AltGr (which reports Ctrl+Alt on some platforms) does. The editor-side move keys also leave a modified press to the editor. Space never seeds — it stays the cursor's select/activate.
- **What seeds.** Only an editor the grid infers: text takes any single character, number takes a digit (it cannot hold a lone `-` or `.`). The yes/no listbox and an `editCell` slot take no seed — the grid does not know a slot's value type — and open with F2, Enter, or a double-click.
- **Floating surfaces.** Every key goes through the same `claimedBySurface` deferral `sessionEscape` used (consumed press, portaled panel, `aria-expanded="true"`), so an open DatePicker or listbox panel keeps Tab and Enter.
- **The settle pair and Tab.** Tab from an editor commits and moves, so it cannot also reach the pair. The pair is now `tabIndex={-1}`, a pointer affordance; the keyboard settles through Tab, Enter, F2, and Escape. That keeps the listbox's WCAG 2.1.1 closure: Tab is its keyboard commit (the browser test that walked Tab into the pair now proves the Tab commit instead).
- **A slot with several controls.** As first built, Tab from any editor committed and moved, so an `editCell` slot with several focusable controls lost keyboard access to all but its first (WCAG 2.1.1). Tab now moves to the next tabbable element in the same cell when there is one, and the browser moves focus there. Only Tab from the last tabbable element commits and moves; Shift+Tab mirrors this from the first. The cell's tabbable elements are the matches of the shared `FOCUSABLE_SELECTOR`, less `tabindex="-1"` and hidden inputs (`tabStaysInCell`). An inferred editor has one tabbable element, so it behaves as before, and the settle pair stays `tabIndex={-1}`, so Tab from the listbox still commits. The browser test [`grid-edit-commit-move.test.tsx`](../../src/__tests__/browser/grid-edit-commit-move.test.tsx) proves the real Tab order through a two-input slot.

Not done here: the settle-control policy still lives in the leaf, and the two API questions below stay open — the keys ship under `session: 'managed'` and read no cell binding.

**4. Blur / click-outside commit policy.** `commitOn?: ('enter' | 'blur' | 'clickOutside')[]` (default `['enter']`). `'blur'` commits a cell-scoped session when its editor loses focus to elsewhere in the grid; `'clickOutside'` commits when focus leaves the grid entirely — the forgiving mode where wandering off doesn't discard work. Needs care against the floating-overlay cases the cursor's blur guard already handles (`[data-floating-ui-portal]`): a `DatePicker` slot opening its popover must not read as blur.

**5. Async / optimistic commit** (roadmap backlog). `onCommit` may return a `Promise`: the grid renders the committed cells in a pending state (subtle shimmer + `aria-busy`), settles on resolve, and on reject restores the drafts and re-enters the row/cell in edit with a per-cell error — the `validate` error surface reused for server rejections. `CellChange` stays the unit, so partial acceptance (resolve with the rejected subset) is expressible.

**6. Undo / redo** (backlog). A value-based history of committed batches wrapping the sink: Ctrl/Cmd+Z re-emits the inverse batch (old values, captured at flush time from the live rows), Shift+Z / Y replays. Purely a layer over `onCommit` — the consumer still owns the data — bounded (e.g. 100 entries) and cleared when `rows` identity changes wholesale (a refetch).

**7. Range selection, fill handle, paste** (backlog, own plan when picked up). The cursor grows an anchored rectangular range; fill drags the active cell's value/series across it and paste maps a clipboard TSV block through the same per-column `validate` + `CellChange[]` path — the batch just spans rows. Depends on nothing above except the cursor; listed here because its commit semantics must stay the one sink.

**8. New-row entry.** A pinned blank editor row (top or bottom) whose commit emits an `onRowAdd(values)` rather than `CellChange[]` — the one place the sink doesn't fit, so it's a sibling callback. Furthest out; needs the pinned-row primitive from the row-model backlog.

## Non-goals

- **Exported editor components** — the `editCell` slot plus staging callbacks stay the whole override surface.
- **A form state model** — no dirty-tracking API, no submit lifecycle; the editable set and the batch sink remain the entire contract.
- **Editing under manual (server) grouping's header rows** — group headers are not data rows.

## Accessibility

Every increment keeps the established invariants: editors carry `aria-label` ("Edit Status, row 2") and `aria-required`; validation errors link via `aria-describedby` and `role="alert"`; commits announce politely (WCAG 4.1.3); the cursor's tab stop owns focus between sessions, and session transitions move focus deliberately (into the entered editor, back to the grid on exit — WCAG 2.4.3). New keys must not shadow editor-internal keys: Enter is claimed only by editors that don't need it (the listbox keeps it for open/select); Escape lives once on the table's key surface and defers to any open floating surface, so a panel closes on its own press and the next abandons; increment 3's typing-starts-edit fires only from the table tab stop, never from within a control. Increment 5's pending state needs `aria-busy` plus an announced settle.

## Accessibility cluster — cell scope removes row scope's compensations

A WCAG 2.2 AA review of increment 2 found five, ranked. The first two should gate shipping `scope: 'cell'`; the rest are older than it, but cell scope is where each stops being covered by something else.

**Closed: the listbox editor has a keyboard commit path.** The boolean editor deliberately leaves Enter to the listbox's own open/select, and row scope covered that by mounting a sibling text or number editor to save from. Cell scope mounts one editor, so that sibling is gone. The value commits only by moving the session to another editable cell, which from inside the editor takes several Shift+Tab hops out through the header's resize and menu controls, unannounced. When the boolean column is the only editable one, the value is uncommittable by any route: `enterEditAtCell` refuses a non-editable column, so no move exists to flush it. The same gap covers an `editCell` slot that does not call `ctx.commit`. Hoisting Enter onto the table's key surface — the fix this plan first named — does **not** close it. Enter on a closed listbox trigger is how the listbox opens, verified in [`grid-edit-listbox-enter.test.tsx`](../../src/__tests__/browser/floating-ui/grid-edit-listbox-enter.test.tsx), so a hoisted Enter would contend with the editor rather than serve it. The route to a keyboard commit for this editor is a control that owns no editor's keys, so that is what shipped: a save and a discard control beside the editor on the cell a cell-scoped session holds. Tab reached them in real tab order and Enter on the save committed, both proven in the browser project. Increment 3 moved the keyboard commit to Tab itself (commit and move, or commit in place with no other editable cell) and took the pair out of the tab order; the browser test now proves the Tab commit. Row scope shows no pair — its settle control is the consumer's row action, and a pair per cell would put two save targets on screen at different scopes.

**Retracted: one Escape does not abandon the cell while a listbox is open.** The review reported that `sessionEscape`'s deferral misses this library's own `Listbox`, because its panel appeared to render inline rather than portaled and its expanded trigger is the focused option's sibling. That was an artifact of the jsdom suite, whose `@floating-ui/react` mock renders `FloatingPortal` inline and stamps no `data-floating-ui-portal` — so the guard reads as missing under jsdom and only there. Against the real engine the panel is portaled, the guard fires, and the first press closes the panel with the session intact. Proven in [`grid-edit-listbox-escape.test.tsx`](../../src/__tests__/browser/floating-ui/grid-edit-listbox-escape.test.tsx), which lives in the browser project because jsdom structurally cannot assert it. The lesson generalizes: any claim about floating-surface behaviour taken from the jsdom suite is untrustworthy by construction.

**No focus indicator while an editor is open (2.4.7).** The editing branch bypasses `GridNavCell`, whose unmount strips `data-active`, so the editing cell carries no cursor ring. Harmless while focus is inside the editor. Not harmless after Tab: focus leaves the grid with the editor still mounted and its draft uncommitted, and tabbing back seats the cursor on a cell with no visible indicator anywhere in the grid. Row scope hid this because Tab moved to the next editor in the row; under cell scope Tab is the first exit a user reaches for.

**A display-only column advertises as editable (1.3.1, 4.1.2).** `aria-readonly` is written only for an explicit `readOnly`, so a column with no `field` and no `editCell` — not editable by `isColumnEditable` — carries nothing. Under row scope a screen-reader user learned the editable set by opening a row and reading which cells became editors. Cell scope mounts one, so trial and error on each cell is the only discovery channel left. Gating the attribute on `!isColumnEditable(col)` states it.

**The commit announcement does not say what saved (4.1.3).** `1 cell updated` was written for a row save. Under cell scope it fires on every cell-to-cell move, queued behind the focus change into the next editor, naming neither column nor row — so the user hears it while already somewhere else. Increment 3 makes that move a single keystroke.

The a11y corpus holds one editable grid, row-scoped and at rest, so axe never sees a narrowed row or a mounted editor. A `scope: 'cell'` case with a session open is cheap and would cover the fourth finding.

## Carried into increment 3

Three things the settle pair leaves for the increment that adds commit-and-move keys, all cheaper to decide there than to retrofit. Increment 3 settled the first two and the bench note; the third is still open.

**Settled: increment 3 claims Tab, and Tab is how the settle pair is reached.** The table surface owns it: Tab commits and moves, and the pair left the tab order (see increment 3's as-built note). The pair closes the listbox's WCAG 2.1.1 gap on the strength of native tab order, asserted in the browser project. Increment 3 gives Tab and Shift+Tab to commit-and-move across a row's editable cells, hoisted to the table's key surface and prevented in the same shape as `sessionEscape` — which would take the only keyboard route to the one control the listbox editor has. Decide there which surface owns reaching the pair, rather than letting tab order decide by default, or the increment reopens the finding this one closed and the guarding test reads as stale rather than broken.

**Settled: the session is two records, and the keys will want one.** The resolver is written once (`sessionTarget`); the two records stay. `activeEdit` names the held cell under cell scope; `sessionRowRef` names the held row and how the session came by it, under both. That split is honest — provenance belongs to the row, identity to the cell — but every key increment 3 adds asks the same question `sessionEscape` already asks, resolving an event to the live session through a DOM walk with a ref fallback. Write that resolver once when the second caller arrives.

**Open: whether a session shows a settle control is decided in the leaf.** `GridEditingCell` derives it from `isSameCell(activeEdit, cell)`, which is today's only policy rather than the policy itself. Increment 4's `commitOn` makes the pair conditional (a blur-committing session needs discard, not save), and increment 8's pinned new-row editor wants a pair while holding no `activeEdit` coord at all — `isSameCell` can never say yes for it. A session field naming the cell that shows the control keeps both edits in the hook.

Also open: the settle pair is grid chrome the consumer can neither replace nor suppress, and for a cell-scoped `editCell` column it renders beside a slot whose `ctx.commit` and `ctx.cancel` are the designed settle route — so a slot that renders its own save shows two at the same scope. And the editing benches could not see any of this: `grid-editing.bench.tsx` set no `session`, no `scope`, and no editing row. Increment 3 added the session-move scenario. A scenario that opens a session and moves it is what would catch a regression in the pair's mount cost, measured at about +0.8 ms against a session move already dominated by whole-grid context fanout.

## Open correctness cluster — a draft can outlive its editor

Found by an adversarial state-machine sweep during increment 2 and reproduced, but **not** introduced by it: each predates the trigger increment, and each needs a decision rather than an edit. They share one cause. A cell's draft is staged against `rowKey` and `columnId`, and the commit sweep asks whether the session still holds that cell — but an editor also unmounts for reasons the session knows nothing about.

**A draft survives its editor and re-commits behind the next one.** Page away from an editing row and back, or let a consumer drop the row from `rows` and re-add it, and the editor re-seeds from the row while the draft is still staged. Saving then writes the old draft over a cell the user last saw holding the original value. This is the sharpest of the four, because the user reads one value and commits another.

**A draft is dropped when its row leaves the render.** `flushRow` resolves the row through `rowKeys.indexOf` and returns nothing when it cannot, but the sweep has already taken the draft out of staging, so the value is consumed and discarded on the same pass. Paginate away from an editing row and save, and the edit is gone with no commit and no announcement.

**A draft is dropped when its column leaves the render.** `flushRow` walks the visible data columns, so hiding a column mid-edit sweeps its draft without emitting it. The column axis of the row case above.

**A declined entry keeps its pending focus.** The focus intent clears inside an effect keyed on the session, so a controlled binding that refuses a grid entry — a permission or dirty guard — changes neither dep, the effect never runs, and the intent survives to steal focus at the next unrelated open. The comment at that effect promises the opposite.

The decision the first three need: the sweep treats a closed editor as a commit, which is right when the session closed it and wrong when the render did. Virtualization already relies on the current behaviour — a row scrolled out of the window unmounts its editors and must *not* commit — so "editor unmounted" cannot become the trigger. What is missing is a way to tell the two apart, and where a draft belongs when its cell is no longer on screen. That question wants settling before increment 5's async commit, which adds a third state (in flight) over the same drafts.

## Open API questions — settled

Two shapes on the public surface were worth settling before increment 4, and both were a maintainer's call rather than a refactor. Both are now settled.

**Settled: the setting names the session's owner.** It shipped as `trigger: 'manual' | 'doubleClick'`, which named a gesture while it gated who owns the session: cursor-Enter entry, the table-level Escape, an `editCell` slot's `commit`, the whole of `scope`, and after increment 3 the commit-and-move keys, F2, and type-to-edit. It is now `session: 'manual' | 'managed'`, with `'manual'` still the default. The package is private and nothing outside it wrote the old name, so the rename carries no alias. Internally the flag is `managed`, read once from `session === 'managed'`.

**Settled: a cell-scoped session binds its cell.** The question as surfaced: `rows` stays the only controllable, and under `scope: 'cell'` it becomes a forced-singleton row set while the session's real identity — the active cell — is internal state a consumer can neither read nor decline. A move between cells of one row emits nothing, which is why `session`'s TSDoc now scopes its source-of-truth claim to which rows edit. Increments 3, 4, and 5 all need to name a cell from outside. Adding `activeCell` / `defaultActiveCell` / `onActiveCellChange` later leaves `rows` as a permanent second binding for one session; adding it with increment 3 does not.

*As built.* The three props landed on `GridEditableConfig` as `cell` / `defaultCell` / `onCellChange`, not under the names above: `GridDataProps.onActiveCellChange` already reports the keyboard cursor's cell, and `cell` pairs with `rows` inside `editable`. They go through `useControllable`, as `rows` does, with `GridCellRef = { rowKey, columnId }` as the value (no exported type had that shape; `GridCellChange` stays as written, because an intersection would change its emitted `.d.ts`). Outside `managed` + `cell` the binding is inert and warns once in development. The rules:

- **One order of writes.** The cell reports first, then the rows. An entry into a closed row emits `onCellChange(cell)` and then `onRowsChange`; an exit emits `onCellChange(null)` and then `onRowsChange`. Enter is an exit and an entry, so it reports `null` and then the cell below. Under a controlled `cell` the rows write waits until the consumer applies the cell, which is what makes a decline clean: a declined move writes neither binding, the held cell stays open, and nothing commits. Enter is the exception, because it means "commit, then move": declining the move must not decline the commit. As first built, a controlled `cell` folded Enter's exit and entry into one rows write, so a `rows` binding that declined the row below declined the exit with it and nothing committed — while the uncontrolled path, two writes, kept the commit. The transition now writes an exit that comes with an entry into a closed row as two rows writes, exit first (`writeRowsPlan`), so both modes agree: Enter commits the held cell and reports `null`, and a declined entry leaves the cursor on the declined cell with focus on the tab stop.
- **One transition path.** A controlled value is acted on by a layout effect, whether the grid asked for it or the consumer set it. A value the grid asked for keeps its focus and seed intents and carries out the exits and discard recorded with the request; any other value is a set from outside. The rows follow a grid entry's rules — the new cell's row opens, an acquired row closes as the session leaves it, and `null` closes the held row, as a save does. A request forces one render (a counter), so a decline is seen in the same event rather than lingering as an intent that a later, unrelated set would honour.
- **No row widens for a render.** While a controlled value waits for its row, the render reads the settled cell, not `null`, so the held row never flashes row-shaped between the cell write and the rows write.
- **Focus.** The entered editor now claims focus itself as it mounts or comes to be held (`claimFocus` on the session), because a controlled move along a row mounts its editor one pass after the hook's effects run. A set from outside moves focus only when focus is already in the grid (WCAG 3.2.1); a grid-asked move blurs the leaving editor where the uncontrolled path does — on a key move or an exit — and not on a double-click, which kept the controlled bench level with the uncontrolled one.
- **Not editable.** A cell of an unknown row, or of a `readOnly` or display-only column, reads as `null`, mounts nothing, and warns once. Editability is checked when a consumer value arrives, not continuously, so a column that locks mid-session behaves as it did.
- **Stranding.** A controlled cell whose row the consumer closes reads as `null` and reports nothing; it reads again if the row reopens, because the value is the consumer's. An uncontrolled coord that strands stays dropped, as before — now through a mask rather than a render-time state write, since clearing a controllable would emit from render.
- **Mount.** An initial cell (controlled or default) seeds `defaultRows` with its row, so the mount reports nothing; under a controlled `rows` that lacks the row the cell stays closed.

The bench gained a controlled variant of the session move. Run one scenario per process, the uncontrolled move measured 7.8 / 16.7 / 34.1 ms at 100 / 500 / 1,000 rows before and 7.5 / 14.6 / 34.3 after; the controlled move 8.3 / 13.9 / 33.5. Increment 3's "flat 29 / 40 / 29 ms" was an artefact of the file: every scenario's persistent tree mounts at collection time into one document, so each scenario's figure depends on what else the file mounts.
