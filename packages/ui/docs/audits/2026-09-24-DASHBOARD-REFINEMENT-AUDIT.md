# Dashboard Refinement Audit

Survey of `modules/dashboard` (2026-09-24, at `c2cfcb5`) after its roadmap closed, for redundancy, performance, and stability. Ten single-lens sweeps read all 37 module files. Three lenses looked for redundancy: inside the module, against the rest of `packages/ui`, and in the public API and its docs. Two measured the cost of React renders and of the engine. Two looked for stability defects, in the shell and in the engine. The last three read the recipe and its CSS, the test suites, and the mechanical measures.

The sweeps raised 156 findings. A merge pass joined the findings that name one mechanism, which left 113 groups. For each batch of four to six groups, one verifier read each cited site again and tried to refute each claim. Where the setup was short, it ran a throwaway probe: a jsdom test, a benchmark, or a Chromium run. It then judged each group against the plan, `ROADMAP.md`, the TSDoc, and `CONVENTIONS.md`, and it set a priority. A completeness critic read the verdicts and the 84 sweep leads, and four targeted sweeps added nine findings under the same verification.

Each probe is deleted, and the tree is clean. The verifiers refuted one claim and ruled out twelve more on merit; Ruled out holds them. Many rows carry a correction, because the verifier narrowed a trigger, fixed a number, or replaced a proposal. Each row states the result of the verifier. One confirmed defect is in `modules/chat`, so it is a lead and not a row.

P1 is a defect that an app or a user meets in normal use, or a cost that fills a frame at about 50 tiles. P2 is real, but it needs an edge case, or it is a change with a clear gain. P3 is a small change for the next edit of the file. The ids are stable: S is stability, P is performance, R is redundancy, and T is the test suites. Resolve each row in place against the pull request that closes it (`CONVENTIONS.md` §12.4).

The result is 4 rows at P1, 44 at P2, and 60 at P3. The value is in the stability rows. The module has no exact duplicate block, and the largest semantic duplicate (R01) saves 15 to 20 lines. Only P01 costs a frame at a realistic board size; the other performance rows matter only on deep boards, or they save microseconds.

[#1301](https://github.com/charliebeckstrand/midgard/pull/1301) applied the four P1 rows. Main then carried 35 more commits from `c2cfcb5` to `7f5ffed`, and a check of each commit found that none closes a row. Seven rows changed, because main moved their mechanism or built a part of their proposal: S21, S23, S40, R18, R30, R33, and T01. Each of these rows carries a note. A row whose sites only moved keeps its `c2cfcb5` cites.

## Measured

The module is 5,068 lines in 37 files: the engine has 2,079 lines in 11 files, and the shell has 2,989 in 26. The tests are 3,872 lines in 23 files, a ratio of 0.76 to the source. The 19 jsdom suites pass 183 tests in 4.5 s, and the 9 engine suites take less than 70 ms of that. The 4 browser suites pass 11 tests in Chromium in about 10 s.

Line coverage of the module is 91.7 percent, and the engine is at 99.0 percent. Three shell files hold the gaps. `use-dashboard-resize.ts` has 33 percent line coverage, and `use-dashboard-flip.ts` has 69 percent. `use-dashboard-drag.ts` has 54 percent branch coverage. The suites print no warning, and four shuffle seeds show no order dependence.

The mechanical checks are clean. `knip` reports nothing, `biome check` reports no diagnostic in 37 files, and `tsc --noEmit` reports no error. `knip` misses four exports with no importer, because `knip.json` sets `ignoreExportsUsedInFile` (R13). A duplicate-block scan finds no exact block of eight or more lines; the semantic duplicates below come from the hand trace.

The dashboard entry bundles to 96.7 kB minified and 32.0 kB gzip, with its dependencies external. The module's own code is 34.1 kB of that, and the recipes are 36.0 kB.

Engine cost, in Node on a 2.1 GHz Xeon. A mid-range laptop or phone is about two to five times slower.

The three render claims of the plan hold for a preview. A preview frame renders only the tiles that it moves, the root does not render, and a commit renders no unchanged spec tile. ## Fix first

**S01 · `parseDashboardSpec` drops the saved entries of the JSX tiles on a mixed board, so each JSX tile loses its place on each load.** `parseLayout` drops each entry whose id is not a spec tile (`engine/dashboard-spec-parse.ts:220-228`), and its only set of ids comes from `tiles` (`:279`). But `mergeLayout` appends an entry for each mounted tile, JSX tiles included (`engine/dashboard-layout.ts:452-454`). Plan §9.2 binds `layout` to `spec.layout` and lets JSX tiles share the board with `DashboardTiles`, so a saved mixed spec holds JSX entries. Each load through `parseDashboardSpec` or `startFromPreset` reports these sound entries as `orphan-entry` and drops them. Each JSX tile then takes a new row under the lowest tile at its `defaultSize`, and the next commit saves that place. A JSX tile on a mixed board therefore never keeps a saved place.

A jsdom probe of the plan §9.2 pattern showed that a `tidy()` commit writes the JSX entry `notes` into `spec.layout`. With `notes` saved at `x: 12, y: 0`, a direct load rendered it at `1 / 13 / span 10 / span 12`, and a load through the parse at `11 / 1 / span 18 / span 8`. The verifier narrowed the finding: a board of JSX tiles only has no contract with the parse, so that half is a feature gap. The `nextSpecTileId` collision with a JSX id is real, but it also occurs before a JSX tile commits, so this fix does not close it.

Add an optional second argument, `parseDashboardSpec(input, { tileIds })`, whose ids join the set at `engine/dashboard-spec-parse.ts:279`. With no option the result does not change, so the orphan rule of `ROADMAP.md:29` holds; `startFromPreset` (`engine/dashboard-preset.ts:51-53`) takes the option and passes it through. The TSDoc must say that a mixed board passes its JSX ids, and a test in `__tests__/modules/dashboard-spec-parse.test.ts` must pin a kept JSX entry. Estimate: about +8 lines in `engine/dashboard-spec-parse.ts` and +2 in `engine/dashboard-preset.ts`, about 6 lines of TSDoc, and a test of about 15 lines.

*Applied in [#1301](https://github.com/charliebeckstrand/midgard/pull/1301). `parseDashboardSpec` and `startFromPreset` take a `tileIds` list or set, so the parse keeps the entries of the JSX tiles.*

**S02 · A spec renderer that throws escapes every tile boundary and unmounts the whole board.** `DashboardSpecTileView` calls `render(tile)` in its own render body (`dashboard-tiles.tsx:177`), so the call runs in the parent of `DashboardTile`. `DashboardTileBoundary` sits lower, inside `DashboardTileContent` (`dashboard-tile-content.tsx:48`), and `Dashboard` has no boundary of its own. A throw from the renderer function therefore passes every tile boundary to the nearest boundary above the board. `parseDashboardSpec` does not check `options`, so a saved spec whose `options` are absent or of an old shape reaches a renderer that reads them. The repo's own test widget has this shape (`__tests__/modules/dashboard-registry.test.tsx:37`). The whole board goes away, JSX tiles included, and `onTileError` never fires, so the tile boundary of plan §4, item 4, is void for spec tiles.

A jsdom probe with the spec tiles `a` (no `options`) and `b`, and one JSX tile, gave `{ crashed: true, siblingAlive: false, jsxAlive: false, onTileErrorCalls: 0 }`. The control, with the same read inside a component that the renderer returns, kept the sibling and called `onTileError` once. At SSR, `renderToString` threw for the page; with the fixed shape, it rendered the sibling, because the tile Suspense sends the error to a client render. The verifier added that under `lazy` or `active` mount the renderer runs for held content, so an offscreen tile crashes the board.

The fix is an internal `DashboardSpecTileBody` in `dashboard-tiles.tsx` that returns `render(tile)`, and it replaces `{render(tile)}` at line 177. The renderer and the registry fallback then run under the tile boundary and its Suspense, in the card and in the expand dialog (`dashboard-tile-expand.tsx:86`). A test in `__tests__/modules/dashboard-registry.test.tsx` pins it: a renderer that reads absent `options` fails in its own tile, the sibling stays, and `onTileError` gets the id. Estimate: about +10/−1 lines in `dashboard-tiles.tsx` with the `@internal` TSDoc, and about +25 lines of test.

*Applied in [#1301](https://github.com/charliebeckstrand/midgard/pull/1301). The renderer runs in `DashboardSpecTileBody`, under the boundaries of its tile. `DashboardWidgetRenderer` also excludes a promise, because the renderer runs again on each Suspense retry.*

**S03 · On a touch screen, the spark veil stays hidden at rest, so the title never shows and the controls are live but invisible.** Tailwind compiles `not-hover:` in the two `veil.fade` literals (`recipes/kata/dashboard.ts:115-116`) to `&:not(*:hover)` and to a `@media not (hover: hover)` branch. On a device whose primary pointer cannot hover, the second branch sets `opacity: 0%` and `pointer-events: none` on the header while the card holds no focus. A spark chart is pointer-inert and holds no focusable element, so a tap on the card focuses the board `<section>` outside the card. The trigger is normal use of a spark tile on a phone or a tablet, as in the demo tiles `units-trend` and `revenue-trend` (`docs/demos/modules/dashboard/index.tsx:202-209`). The title and each action that is not a `Button` never show, and each `Button` control takes a tap while invisible. This fails the stated goal of `ROADMAP.md:35`: at rest the veil shows on hover or focus, so the title and the controls stay reachable.

A Chromium probe under the CDP call `Emulation.setTouchEmulationEnabled` gave `(hover: hover)` false, and after a hover the header stayed at opacity 0. The verifier corrected the tap claim: the touch-target span of `Button` has `pointer-events-auto`, so a blind tap on the hidden Expand opened the dialog. The finder's test recipe fails, because `Emulation.setEmulatedMedia` with a `hover` feature left `matchMedia('(hover: hover)')` true in this Chromium. The Clear case is narrower than the finding says, because a spark chart is pointer-inert and cannot make the selection itself.

The fix prefixes the two `veil.fade` literals with `[@media(hover:hover)]:`, so the nested `@media not (hover: hover)` branch cannot match and touch screens keep the veil in view. Update the fade comment (`recipes/kata/dashboard.ts:109-113`), the `DashboardTile` remark (`dashboard-tile.tsx:145-148`), and `ROADMAP.md:35` to match. Add one case to `__tests__/browser/dashboard-spark.test.tsx` that turns on touch emulation through `cdp()` and resets it in `afterEach`. Estimate: two class literals, about 3 doc lines, and one browser case of about 15 lines.

*Applied in [#1301](https://github.com/charliebeckstrand/midgard/pull/1301). The fade applies only under `@media (hover: hover)`. A jsdom case pins the class, because the shared browser suite cannot turn touch emulation off again.*

**P01 · `DashboardTile` builds its whole card inline under the dnd-kit consumer, so each lift and each drop render the chrome of every tile again.** Each tile calls `useDraggable` through `useDashboardTileDrag` (`use-dashboard-tile-drag.ts:70-71`), which reads the dnd-kit `InternalContext`, a memo over `active`, `activatorEvent`, and `activeNodeRect`. A lift changes that value twice, because `useRect` measures the active node in a layout effect, and a drop or a cancel changes it again. `DashboardTile` builds the card, the header, the Clear control, the edit controls, the content box, and the edges inline, with no memo (`dashboard-tile.tsx:234-313`). Each change therefore renders the full chrome of every tile, which contradicts the tile TSDoc at `dashboard-tile.tsx:135`. The dragged tile also renders its chrome on each carry move, through `ActiveDraggableContext`, but that cost is below the measurement noise. The cost falls once at each lift and once at each drop or cancel, and it grows linearly with the tile count.

A Profiler probe on a 48-tile edit board counted 98 tile renders at a keyboard lift, and 49 at a drop or a cancel. In Chromium with production React, an A/B copy with a memo boundary cut the median lift from about 14 ms to about 5 ms. The median cancel fell from 12 ms to 5 ms, and the p90 lift from 21-23 ms, past a 16 ms frame, to 7-9 ms. The verifier corrected the finding: a drop renders each tile once, not twice, and its jsdom-dev times overstate the shipped cost 2 to 9 times.

The fix splits `DashboardTile` into a thin shell, which calls the hooks and positions the div, and a memoized card body in `dashboard-tile-card.tsx`. Because `grip` and `surface` keep their identity (`use-dashboard-tile-drag.ts:86-102`), the memo holds on each tile but the dragged one, given a memoized placeholder (`dashboard-tile.tsx:221`). A regression test pins it: a keyboard lift on a 3-tile board renders no card body of a tile that is not dragged. Estimate: +35 to +45 lines, with the body props type, its TSDoc, and a `memo` on `DashboardTileEdges`.

*Applied in [#1301](https://github.com/charliebeckstrand/midgard/pull/1301). The card renders in a memoized `DashboardTileCard`, and `DashboardTileEdges` is memoized. At 48 tiles in Chromium (development build), a lift fell from about 31 ms to 16 ms.*

## Stability

### Gestures

**S04 · Escape during a tile drag also closes the Dialog, Sheet, or Drawer around the board, because the drag joins no dismiss layer.** `useEscapeLayer` skips an Escape only when the press is default-prevented or its layer is not on top of the dismiss stack (`hooks/use-escape-layer.ts:43-58`). An Overlay registers a layer through `useDismissable` (`primitives/overlay/overlay.tsx:138`), and its shared document listener attaches when the Dialog opens, before dnd-kit attaches. The drag registers no layer, and the dnd-kit 6.3.1 PointerSensor cancels on Escape with no `preventDefault` (`core.esm.js:1595-1598`). The KeyboardSensor calls `preventDefault` from a listener that it adds on a timer after the lift (`core.esm.js:1158`, `1328-1332`), so the Dialog sees the press first. One Escape therefore cancels the drag and closes the surface around the board. The resize already consumes Escape in window capture (`use-dashboard-resize.ts:201-221`), so only the drag has the defect.

The verifier held a board in edit mode inside `<Dialog open onOpenChange={spy}>`. An Escape during a keyboard drag and during a pointer drag each gave `spy.calls=[[false]]`. A pointer resize with Escape gave `[]`, and both proposed fixes also gave `[]` and still canceled the drag. The verifier rejected the finder's optional move of the resize Escape onto `useEscapeLayer`, because the resize `stopPropagation` also blocks raw app listeners.

Call `useEscapeLayer({ open: isDragging, onDismiss: noop })` in `useDashboardTileDrag` (`use-dashboard-tile-drag.ts:70-71`), with `noop` from `utilities`. The live drag is then the top layer, so the surface around the board ignores the press, and dnd-kit still cancels the drag. Pin it in `__tests__/modules/dashboard.test.tsx` with a keyboard drag in a Dialog, then Escape, and no `onOpenChange` call. Estimate: +3 lines (two imports and one call), plus a test of about 20 lines.

*Applied in [#1337](https://github.com/charliebeckstrand/midgard/pull/1337). P2; severity medium; verified by probe.*

**S05 · The dragged card shows the closed hand only under the pointer, and `useGrabbingCursor` exists for this case.** The card takes the scoped `cursor-grab` and `data-[dragging]:cursor-grabbing` pair (`recipes/kiso/hannou/cursor.ts:15`, through `recipes/kata/dashboard.ts:62`). dnd-kit sets no cursor and captures no pointer, so the element under the pointer decides the cursor. `carriedOffset` clamps the tile to its travel range (`use-dashboard-tile-drag.ts:51-54`), so at an edge of that range the tile stops and the pointer goes on. The cursor then shows the default arrow over the page, the open hand over another movable card, or a resize cursor over a splitter. `useGrabbingCursor` documents this failure (`hooks/use-grabbing-cursor.ts:49-59`), and `modules/grid/grid-group-manager.tsx:171` and `modules/grid/grid-row-manager.tsx:65` use it.

The verifier pressed the pointer on tile `a` at `x=0, y=0` and moved it by −300 px and −40 px. The shell and the card both carried `data-dragging`, the shell transform stayed `translate3d(0px, 0px, 0)`, and `document.head` held no `style[data-grabbing-cursor]`. jsdom draws no cursor, so the verifier derived the visual result from the CSS rules and did not see it. The verifier did not show the finder's second trigger, a pointer that outruns the transform by one frame near the card edge.

Call `useGrabbingCursor(drag.dragging)` in `DashboardTile` after `useDashboardTileDrag` (`dashboard-tile.tsx:194`), with the import from `'../../hooks'`. The global rule then holds for the whole drag, a keyboard drag included, as in the grid managers. Pin it with a case in `__tests__/modules/dashboard.test.tsx` that lifts a tile and expects `style[data-grabbing-cursor]` in `document.head`. Estimate: +2 lines (the import and the call).

*Applied in [#1337](https://github.com/charliebeckstrand/midgard/pull/1337). P2; severity low; verified by probe.*

**S06 · A gesture commit writes the whole snapshot from the gesture start, so it reverts outside layout changes and restores the entry of a removed tile.** `handleDragEnd` (`use-dashboard-drag.ts:171`) and `settleResize` (`use-dashboard-resize.ts:109`) commit the full preview, which is the start snapshot with one change. `mergeLayout` (`engine/dashboard-layout.ts:440-454`) writes each preview cell over the current saved entry, and it appends each cell with no entry without a check of `demands`. The sync effect (`dashboard.tsx:239-242`) updates `state.layout` during the gesture, but `paintedCells` reads only the snapshot or the preview (`engine/dashboard-store.ts:151`). So when the app moves a tile during a drag or a pointer resize, the commit writes the old cell back. When the app removes a tile during the gesture, the commit appends its entry again, and `nextSpecTileId` then skips that id. The trigger is an outside change during a live gesture: a remote sync, or a mouse Remove during a keyboard pickup.

In the verifier's probe, a keyboard drop reverted an app move of `c` to y 40, and it wrote `c{x16,y0,w8,h10}` back after an app remove. A pointer resize reverted an app move of `a` to y 30, and a keyboard resize, the control, kept it. The finder's delta commit is not safe, because the preview comes from the stale snapshot and can persist an overlap. A check at the drop costs less than a cancel on input, and `sameGeometry` compares content, so an equal new array cancels nothing.

In `handleDragEnd` and `settleResize`, end as canceled, with no commit, when `!sameGeometry(store.getView().canonical, gesture.snapshot)`. The snapshot equals `canonical` at the start, because a gesture needs projection identity (`engine/dashboard-responsive.ts:90`, `109`). In `mergeLayout`, append a cell only when `demands.has(cell.id)`, as its TSDoc states (`engine/dashboard-layout.ts:425-430`). Estimate: about +5 lines, plus about 30 lines of tests for an app move and an app remove during a drag.

*Applied in [#1337](https://github.com/charliebeckstrand/midgard/pull/1337). P2; severity medium; verified by probe.*

**S07 · Gestures do not exclude each other, so a resize during a keyboard drag commits two tiles on one cell, and the drag gets no `onDragEnd`.** `handleDragStart` (`use-dashboard-drag.ts:78-107`) and `resizeContext` (`use-dashboard-resize.ts:47-83`), which serves `beginResize` and `resizeBy`, do not check `state.gesture`. A resize takes its snapshot from `view.cells` (`use-dashboard-resize.ts:73`). During a drag, `paintedCells` pins the dragged tile to its start cell, and a shift partner already paints at that cell (`engine/dashboard-store.ts:151-163`). The dnd-kit KeyboardSensor listens only for keydown, resize, and visibilitychange (`core.esm.js:1154-1158`), so a mouse resize or a Tab to a splitter leaves the drag live. The resize start overwrites the drag gesture, and its commit writes both tiles on one cell into the saved layout. `handleDragEnd` then finds no drag gesture and returns (`use-dashboard-drag.ts:155`), so `onDragEnd` never fires, against `types.ts:66-69`.

The verifier lifted `a` with Space, pressed ArrowRight four times into a shift with `b`, and resized `c` by −1 column with the pointer. The commit was `[a{x0,y0}, b{x0,y0}, c{w7}]`, and after Space `onDragStart` had 1 call and `onDragEnd` had 0. An ArrowLeft on the east splitter of `c` during the drag gave the same result, and two concurrent pointer resizes lost the change to `a`. dnd-kit still ends its own drag on Space, so the board does not stick, and the finder's `isPrimary` and id checks are not necessary.

In `handleDragStart`, return before the `setState` when `store.getState().gesture !== null`. At the top of `resizeContext`, return `null` on the same check, as `tidy` does at `use-dashboard-handle.ts:33`. A refused dnd-kit drag then stays active and does nothing until release, as the `!view.editable` path does now. Estimate: about +4 lines, plus a 25-line test in which a keyboard drag, a splitter arrow, and Space give no overlap and one `onDragEnd`.

*Applied in [#1337](https://github.com/charliebeckstrand/midgard/pull/1337). P2; severity high; verified by probe.*

**S08 · Nothing ends a live gesture when edit mode ends or the board unmounts, so a stranded resize leaks its listeners and a drag still commits.** `beginResize` puts pointer listeners on the splitter and a capture keydown listener on `window` (`use-dashboard-resize.ts:188-221`), and only those listeners end the gesture. When `movable` turns false (`dashboard-tile.tsx:192`, `302-311`), the splitter unmounts, and a browser sends `lostpointercapture` to the document, not to the splitter. The store keeps the `resize` gesture, so the board paints the unsaved preview, ignores new layout values, and refuses `tidy` (`use-dashboard-handle.ts:33`). `handleDragMove` and `handleDragEnd` never read `editable` (`use-dashboard-drag.ts:111-174`), and the dnd-kit KeyboardSensor stays on the document until an end key (`core.esm.js:1147-1158`). So after a keyboard pickup, a click on the app's Done control or an unmount leaves a drag that the next Space commits. A mouse alone cannot strand a gesture, because pointer capture sends its release to the splitter.

In the verifier's jsdom probe, `editing=false` during a resize of `a` to span 14 left the shell at `span 14` with z-30. The leaked listener swallowed the next Escape, and later a keyboard move of `b` committed the unsaved `h 14` of `a`. A keyboard pickup, then `editing=false`, let Space commit `a` to y 2 in view mode, and after an unmount `onValueChange` still fired. Any later commit clears a stranded gesture, and once the gesture is null, dnd-kit prevents only the first end key, not the arrows.

Give `useDashboardResize` a `cancelResize` over the `finish` in a ref, and `useDashboardDrag` a `cancelDrag` that ends a drag as canceled. In `Dashboard`, add a layout effect on `editable` that calls both when `editable` is false and on cleanup. Pin it with jsdom cases for an edit exit and an unmount during a resize and during a keyboard drag. Estimate: about +20 lines across `use-dashboard-resize.ts`, `use-dashboard-drag.ts`, and `dashboard.tsx`, plus about 50 lines of jsdom test.

*Applied in [#1337](https://github.com/charliebeckstrand/midgard/pull/1337). P2; severity high; verified by probe.*

## Leads

These leads are outside the three lenses, or outside the module. They are not verified unless the line says so.

Outside the module, for the owner of each file:

- `modules/chat/chat-embed.tsx:67` looks up a renderer on a plain object. An embed named `constructor`, `hasOwnProperty`, or `__proto__` throws during render, and `toString` renders `[object Undefined]`. The chat module has no error boundary, so one message part takes down the transcript subtree. The dashboard lookup uses `Object.hasOwn` (`dashboard-tiles.tsx:108`); use the same guard in the chat. A shared registry helper saves no code, because only the three-line merge is common. Verified by probe.
- The S04 defect is on every dnd-kit surface: `hooks/use-sortable-list.ts`, `components/kanban/kanban.tsx`, and `modules/grid/grid-group-manager.tsx`. None registers a dismiss layer while a drag is live. The query builder with `reorder` ([#1276](https://github.com/charliebeckstrand/midgard/pull/1276)) is one more surface, and `useSortableList` covers it; verified by probe.

Inside the module, but outside the three lenses or not ranked:

- A move and a resize have keyboard paths, but no single-pointer path without a drag (WCAG 2.2 SC 2.5.7). An accessibility audit decides this.
- The board speaks through two live regions: the region of dnd-kit for a drag, and `announce()` for a remove, a duplicate, and a tidy.
- Tab ends a keyboard drag and commits the move, but `describeDragStart` names only Space and Escape.
