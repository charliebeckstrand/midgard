## Mechanisms

### G1-01 — the inferred number editor rounds a fraction on blur, and the rounded value commits

- **File:** `packages/ui/src/modules/grid/grid-edit-inputs.tsx`
- **Mechanism:** `grid-edit-inputs.tsx:107` `<NumberInput` passes no `step`, and `:115` `onValueChange={(next) => onValueUpdate(next ?? undefined)}`. `number-input.tsx:66` `step = 1,`, then `:91` `const precision = stepPrecision(step)` and `:93` `const round = (n: number) => Number(n.toFixed(precision))`. On blur, `:145` `const next = clampValue(round(current))` and `:147` `if (next !== current) setCurrent(next)`. The commit drops only an equal value: `grid-edit-commit.ts:106` `if (Object.is(cell.value, original)) return 'drop'`. So 2.5 becomes 3, is staged, and commits.
- **Trigger:** an editable grid with a number column whose cells hold fractions (a price of 19.99, a rate of 0.25), edited through the inferred number editor. The user opens the cell, types a fraction or types nothing, and leaves it with Enter, Tab, F2, a settle control, a commit on leave, or a press of the consumer's own save button. The new-row slot is hit the same way when Tab leaves its number editor before the add. Under row scope, a Tab that only passes through the editor is enough (focus then blur), because all of the row's editors mount.
- **Documented intent:** `number-input.tsx:35` "Stepper increment; also sets the rounding precision applied on blur." This is deliberate for NumberInput only. The grid's editor says nothing about rounding: `grid-edit-inputs.tsx:95` "Number editor for numeric cells, backed by `NumberInput`." `grid-editing-types.ts:393` "Three kinds of cell are dropped: unchanged ones". See Q23.
- **Reach:** test-only. NONE in the roots: searched `editable=` and the number fields of the editable docs pages, and `editable` in apps (only `place-form.ts`, which is not a grid). The one number column, `editor-types.tsx:101-105` (budget), uses the `CellCurrency` slot, not the inferred editor. Test-only: `__tests__/modules/grid-editing.test.tsx:370`, `:918`.
- **Severity:** low (bug). The cost is high (a silent change to committed data), but no shipped surface builds the trigger.
- **Prior art:** none (digest NONE).

### G1-02 — a frozen row throws as its cell goes pending

- **File:** `packages/ui/src/modules/grid/grid-editing-cell.tsx`
- **Mechanism:** `grid-editing-cell.tsx:72` `Object.create(Object.getPrototypeOf(row), Object.getOwnPropertyDescriptors(row))` copies the non-configurable descriptors of a frozen or sealed row. `:74-78` `Object.defineProperty(copy, field, { value, writable: true, enumerable: true, configurable: true })` then redefines a non-configurable property, which throws TypeError. The only guard is `:70` `if (field == null || Object.is(row[field], value)) return row`, so it bypasses only a consumer that already applied the change. It is reached from `:160` `render?.(pendingRow(row, column, value))` while the draft is `pending` (`:141`).
- **Trigger:** rows that are frozen or sealed objects, as Immer and Redux Toolkit state is, and an async `onCommit` that applies the change when its promise resolves rather than at once. The user commits an edit, a paste, a fill, or an undo.
- **Documented intent:** `:61-65` covers prototypes, getters, and private fields only. Frozen rows are not mentioned. `grid-editing-types.ts:404` "Each shows the committed value with `aria-busy`".
- **Reach:** none. Searched for `Object.freeze`, `immer`, `produce(`, and `@reduxjs` in apps, docs pages, layouts, and grid. Nothing found. `async-commit.tsx:23` uses plain `useState` rows. No test covers it.
- **Severity:** low (bug). A throw would be high, but no shipped surface builds the trigger.
- **Prior art:** none (digest NONE).

### G1-03 — Enter, F2, or a typed key on a cell whose editor is already open does nothing

- **File:** `packages/ui/src/modules/grid/use-grid-editing.ts`
- **Mechanism:** `use-grid-editing.ts:914` `const here = entering ? isSameCell(active, entering) : editableRows.has(rowKey)`, then `:918` `if (here || isPending(rowKey, columnId)) return`. This runs before `:920` sets `pendingFocusRef`, so no focus intent is recorded. From the tab stop, `sessionTarget` finds no `td`, so `:1223` gives `columnId: null` and `:1361` `if (session.columnId === null) return`. The cursor path calls `use-grid-cursor.tsx:326` (Enter) and `:552-554` `event.preventDefault()` then `enterEditAt(...)`. So a printable key is also swallowed.
- **Trigger:** `session: 'managed'`. Focus is on the grid's tab stop while the cell under the cursor already has an open editor. Under row scope that is a row that is open: a refused async save opened it again (focus stays on the grid by design), the consumer opened it through `rows`, or focus went to a header control and came back. Under `scope: 'cell'` it is the cell that the session holds. The user presses Enter, F2, or a printable key on that cell. The concrete route: with the default `commitOn: 'explicit'` (`grid-editing-types.ts:320`), leave the grid with the editor open, then Tab back onto the table's tab stop.

## Open questions

The verifiers' questions, renumbered in the order of the steps they gate. Each names its source sheet and question. Q1 is moot after #2646, and Q2, Q3, and Q4 are settled. None of the others is settled.

### Q1 — how does Form block a second submit without disabling the focused control? Gates S1. (V5 Q1)

- **(a) Keep the disable.** Save `document.activeElement` at submit and restore it after settle. This keeps the public `disabled` TSDoc, but focus stays lost while the submit runs.
- **(b) Disable every control except the focused or submitting one,** and block re-entry with `submitting`. This changes the public contract "submitting disables it regardless" (`form.tsx:55`), so it needs assent under CLAUDE.md §3.1 and a TSDoc and docs-index update.
- The outcome sets the S1 file set.

**Answer:** moot. #2646 settled it on `main` with a third shape: a submitting Form locks its controls instead of disabling them, so focus stays.

### Q2 — prewarm the live regions or delay the first write? Gates S2. (V7 Q2)

- **Prewarm:** `UIProvider` mounts both regions. This adds a provider dependency, and a caller with no provider keeps the bug.
- **Delay** the first write after creation by one task: `setTimeout` or rAF. This changes the timing that `expectAnnouncement` relies on.

**Answer:** "Delay the first write after the live region is created by one task. Do not prewarm in UIProvider."

**Amended by the reader:** delay the first write until after the next paint (a frame callback, then one task). One task alone can run before the next rendering update, and the browser adds the region to the accessibility tree in that update. In Chromium, the one-task delay wrote the text in the same frame as the region in 10 of 10 runs. #2659 uses the amended shape.

**Amended by the reader again:** after the next paint, wait 100ms more before the first write. React Aria's `LiveAnnouncer` waits 100ms before its first message, because VoiceOver in Safari did not speak a message that came sooner. This record did not measure that delay, because no Safari or VoiceOver was available.

### Q3 — should a non-sortable truncated title become focusable? Gates S4. (V2 Q4)

- **Focusable:** that adds Tab stops, against the cursor's single stop.
- **Pointer-only:** it stays as it is.
- The choice decides whether S4 touches the non-sortable branch.

**Answer:** "Open the truncated title's tooltip when the sort button takes focus. A non-sortable title stays pointer-only; add no Tab stop."

### Q4 — should an `aria-current` move also override a stop the user has roved to? Gates S5. (V6 Q-A)

- **Axis 1:** always follow `aria-current` when focus is outside, or only when the hook seated the current stop. The second needs a seated-vs-roved marker.
- **Axis 2:** whether the `activeSelector` TSDoc wording "applies only until the user roves" stays true.

**Answer:** "Always re-seat the stop on the aria-current item when focus is outside the container."

### Q5 — what should Debug off do to the pin? Gates S6. (V6 Q-B)

- **Debug off also clears the pin.** Then `setEventsOn` changes.
- **The pin persists and the aside gates on the on-state.** Then the aside needs an on-state subscription.

**Answer:** "Keep the pin; mount and load the panel only while Debug is on."

### Q6 — what does an arrow do on an empty stop list? Gates S11. (V4 Q2)

- **`handled: false`:** the page scrolls, and the engine test changes.
- **Handled with no move:** the key is claimed and the page does not scroll. This keeps `handled: true` but needs a third outcome beside "clear".

**Answer:** "Handled with no move: claim the key, do not scroll, keep focus on the map."

### Q7 — how does a dot near an inset edge get its query box? Gates S12. (V4 Q1)

- **(a) A round-trip guard in `unprojectPoint`,** so a corner that maps into a different inset returns null. The TSDoc then holds, but the dot still gets no claim, and every reader of `unproject` changes.
- **(b) Clamp the corners to the dot's own inset box before the invert.** Only `spare.ts` changes, and the claim is kept.
- **(c) Invert the centre alone and widen by the local scale.** This avoids the corner problem but loses the per-latitude accuracy that `spare.ts:72-74` asks for.

**Answer:** "(b) Clamp the corners to the dot's own inset box before the invert; change only spare.ts."

### Q8 — which callbacks does Enter or Space fire, and what does Space do? Gates S13. (V3 Q2)

- **Scope:** `onCategoryClick` only, or also `onCellClick`, `onMarkClick` and the pie.

**Answer:** "Enter and Space fire the click callbacks of the focused point: onCategoryClick, onCellClick, and onMarkClick. Space claims the key only when one of those callbacks is set; otherwise the page scrolls."

### Q9 — where does the touch menu button go on a chart that draws no header? Gates S14. (V3 Q1)

- **(a) A corner button over the plot.** No tier reserve change, but it may cover a mark.
- **(b) A header row that holds only the button.** This changes `chartChromeReserve` and the plot height.

## Ruled out

- **G2-07** (REFUTED) — a pointer-opened grid context menu restores no focus on close. The guard: `use-menu-root.ts:241-242` "A keyboard open restores focus to it on close, as the grid does. A pointer open restores nothing, so focus stays where the user put it", pinned by the test `context-menu.test.tsx:423-433` "leaves focus alone after a menu that the pointer opened closes … `expect(field).not.toHaveFocus()`". The grid menu runs on the same `useMenuRoot` context mode. Mechanism traced: a pointer open leaves `returnFocus` null (`grid-context-menu.tsx:174`), the context panel takes focus (`menu-content.tsx:192` `autoFocus={!isDropdown}`), and a close blurs it to `<body>` (`floating-surface.tsx:132-134`).
- **Q1-02** (REFUTED) — an empty assistant bubble stays after Stop. `use-chat-send.ts:200-201` "A stop-induced rejection isn't a failure: no rollback, no onError." and `if (signal.aborted) return`. The rollback it skips is the one on `:73` "Throwing (or rejecting) rolls back the empty assistant placeholder". So the empty bubble that stays after a stop is by design.
