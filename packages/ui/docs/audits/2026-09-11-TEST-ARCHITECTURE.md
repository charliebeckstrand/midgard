# Test Architecture Proposal

Proposal for the `packages/ui` test suite (2026-09-11): the browser suite for the DOM that jsdom fakes with the full migration held behind one measurement, a node environment for the pure layer, a disk module cache, one component registry that feeds every sweep gate, and lint rules in place of the import-layering boundary tests. The measured speed wins are the browser suite without isolation (190s to 44s) and the module cache (60s to 51s on the unit project); the browser convergence is a simplification at wall-clock parity, and the rest is structure. [#1039](https://github.com/charliebeckstrand/midgard/pull/1039) banked the runner wins: pool, isolation, and sequencer took the jsdom suite from 143s to about 47s. This document starts where that work stopped. [#1125](https://github.com/charliebeckstrand/midgard/pull/1125) landed this document and the first three steps of its Order together, so read the Order table for the state of each step. Every number below comes from a run on this machine; the method is the one the audits set, so a claim is a finding only after a run showed it.

The suite holds 592 test files and about 115,000 lines. 492 files and 6,743 tests run under `pnpm test`; 100 files and 539 tests run in the browser suite. The test infrastructure is 2,223 lines across 44 files, and about half of those lines are comments that explain a jsdom workaround.

## Measured

All numbers come from a shared 4-core container. Compare them only against each other; the 143s and 47s figures above come from an idle machine that was about twice as fast.

The jsdom suite (`pnpm test`) runs 492 files in 91.4s of wall clock. The phases sum across workers: tests 196.6s, import 76.2s, transform 41.7s, setup 18.3s. Test bodies are now the largest phase, and the per-file fixed cost is gone. The per-test profile is flat: the slowest test is a 1.9s TSDoc walk, only 73 tests exceed 200ms, and 54 percent of the test time sits in the 1,016 tests over 50ms. There is no fat tail to cut.

Per-test cost follows the interaction style, not the component:

| style | files | tests | ms per test |
|---|---|---|---|
| no DOM at all | 162 | 2,078 | 13.9 |
| render, assert only | 195 | 1,666 | 18.7 |
| `fireEvent` | 76 | 1,483 | 42.0 |
| `userEvent` | 59 | 1,516 | 48.5 |

The browser suite (`pnpm test:browser`) runs 100 files in 190.3s. Its import phase sums to 565.7s and its setup phase to 98.6s: each file re-imports the module graph, because the browser config leaves `isolate` at its default. Test bodies take 120.1s.

**The same jsdom tests run in Chromium at wall-clock parity, with cheaper test bodies.** A trial config pointed the `components/`, `hooks/`, and `primitives/` directories (215 files, 3,016 tests) at the browser provider with `isolate: false`, the browser setup files, and the browser module mocks. The jsdom run of the same three directories, on four workers, took 20.9s of wall clock with test bodies at 35.7s summed. The Chromium run took 32.3s cold and 27.6s warm, on one page, with test bodies at 25.0s summed; the files themselves ran in a 19.0s span, and the rest was fixed startup (the Vite server, the dependency optimizer, and the browser launch). A four-instance variant, one page per quarter of the file list, took 39.3s warm: each instance re-imports the whole graph, and four pages saturate four cores. So on this machine the browser is not a wall-clock win. It is a 30 percent cut in test-body cost behind a fixed startup, and that startup does not grow with the suite.

The trial failed 48 of 3,016 tests in 16 files, and every failure is test infrastructure, not component behaviour:

| cause | tests | fix |
|---|---|---|
| `fireEvent.drop` with a fake `dataTransfer` object | 15 | build a real `DataTransfer` in `makeFileList` |
| `motion` and `shiki` not in the browser mocks | 11 | add both to `browser/setup/module-mocks.ts` |
| `el.focus = vi.fn()` after `userEvent` patched the getter | 7 | `vi.spyOn(el, 'focus')` |
| `vi.spyOn` on an ESM namespace export (`announce`) | 6 | mock `core/announcer` in setup, or assert on the live region |
| live-region assertions with no `__resetAnnouncer` | 4 | port the `afterEach` from the jsdom setup |
| real layout and real CSS serialization | 3 | assert the behaviour, not the pixel or the shorthand |
| timezone and locale not pinned in the page | 2 | `timezoneId` and `locale` on the Playwright context |

**`modules/` runs in Chromium too, and beats jsdom on wall clock.** The trial the paragraph above left open ran on 2026-09-19. A trial config pointed the 96 DOM files under `src/__tests__/modules/` at the browser provider with `isolate: false`, the browser setup files, and all four `unit` doubles (`@floating-ui/react`, `motion`, `motion/react`, `shiki`). The 47 node-docblock files in that directory stayed out, because part 2 keeps them in `pure`. jsdom runs the same 96 files and 1,398 tests in 26.2s of duration and 33s of wall clock on four workers. Chromium runs them in 34.1s cold and 28.1s warm, and 36s then 30s of wall clock, on one page. So the browser takes the directory in less wall clock than jsdom while using a quarter of the parallelism, and the reason is the phase jsdom cannot avoid: `environment` sums to 207.1s there and to zero in the browser. Test bodies fall to 0.59 of their jsdom cost, 38.2s against 65.2s, which is better than the 0.70 the components trial measured.

The trial failed 52 of 1,398 tests in 18 of 96 files. That is 3.7 percent of tests and 19 percent of files, against 1.6 percent and 7.4 percent for the components trial, so the prediction above holds: this directory costs more per file to move. Two failures differed between the cold and the warm run, which is an order dependency under `isolate: false` and wants `VITEST_SEED` replay before anyone calls it fixed. Every failure is test infrastructure again, and the causes are not the components' causes. A tilde marks a bucket whose edges overlap another's, because a chart tooltip can miss on the pointer or on the geometry; the 52 and the 18 are exact:

| cause | tests | fix |
|---|---|---|
| synthetic pointer coordinates against real geometry (chart tooltips and band clicks) | ~13 | drive the pointer from the rendered geometry, or assert through the keyboard path |
| deferred content is really deferred: the jsdom `IntersectionObserver` stub reports every target intersecting at `observe()` | ~11 | scroll the target into view, or give the deferral a test seam |
| CSS number serialization and computed style (`aspect-ratio: 1.77778`, `default` against `pointer`) | ~9 | assert the behaviour, not the serialized shorthand |
| real layout geometry (`viewBox`, measured heights) | ~6 | assert the behaviour, not the pixel |
| live-region residue: `browser/setup/index.ts` never calls `__resetAnnouncer`, which `setup/index.ts:24` does | ~6 | port that one line into the browser setup |
| real transitions not yet settled | 2 | await the settled state |
| the remainder, one case each (a revoked object URL, a visibility assertion, a stray click) | 5 | per case |

Two of those rows are new. The `IntersectionObserver` stub is named in the Findings below as a jsdom workaround, but not as a migration cost, and it is the second largest cause here. The pointer rows are the `mockDomGeometry` dependency surfacing exactly where the paragraph above predicted it. The live-region row is the components trial's row again, unchanged and still one line.

One failure argues part 5 on its own. `bar-chart.test.tsx:90` reads `expect(tooltip?.textContent).toContain('Q3')` after `bySlot(container, 'tooltip-content')` returned `null`, so the run reports "the given combination of arguments (undefined and string) is invalid for this assertion" rather than naming the missing element. Ten of the 52 failures report that way. `getBySlot` through `buildQueries` would have thrown with a DOM dump at the query.

**The whole movable suite runs in one browser config, and the merge costs wall clock rather than saving it.** The second open trial ran on 2026-09-19. One config took every file the migration would move, the `unit` and `integration` projects plus the existing `browser/` files, into a `dom` instance and a `floating-ui` instance, both `isolate: false`. `pure` and `boundary` stayed in node, because the boundary rules walk source text through `node:fs` and no page can serve them. The run took 445 files and 5,448 tests in 109.1s of duration and 113s of wall clock, and the node remainder took 154 files and 1,964 tests in 11s. Today the same ground costs 73s for `pnpm test` and 35s for `pnpm test:browser`, so the suite goes from 108s across two runs to 124s across two runs. The `environment` phase that paid for the `modules/` win, 703.3s summed over the `unit` and `integration` projects, falls to zero here too; at this scale the single page gives it all back, because 445 files on two pages cannot use four cores.

That also settles what "one runner in place of two" means. `boundary` reads the filesystem and `pure` wants no DOM, so the end state is a browser config and a node config, not one runner. What the migration retires is jsdom and its workaround layer, which is the simplification part 1 claims; the runner count does not change.

The run failed 243 of 5,448 tests in 52 of 445 files, and 112 of those failures are one file. `browser/geometry-invariants.test.tsx` checks page-level horizontal overflow across the baseline corpus, and on a page shared with 400 other files it measures 414px of overflow that belongs to residue rather than to the case under test, so all 112 tests fail together. Discount that file and the rate is 131 failures in 51 files, 2.4 percent of tests, which sits between the components trial's 1.6 percent and the `modules/` trial's 3.7 percent.

Two findings change part 1 rather than costing it.

**Seven files declare a per-file `vi.mock`, not five.** Part 1 names `map-centroid-deferral`, `map-path-deferral`, `map-points-render`, `query-builder`, and `use-pdf-viewer-document` for the `isolated` instance. `use-pdf-viewer-report.test.ts` and `chart-export-report.test.tsx` declare one too. Leave either on a shared page and the run dies: the browser mocker registers a Playwright route for each mocked module and re-registration races its own `unroute`, so the provider throws an unhandled `route.fulfill: Route is already handled!` from `@vitest/browser-playwright/dist/index.js:1001` and the run reports no summary at all. That reproduced three times, once with the `dom` instance split across two pages, so it is the mock registration and not the page size. Holding all seven out clears it. The list is a scan, not a memory: `grep -l 'vi\.mock'` over the `integration` set is what keeps it right, and `test-isolation-boundary.test.ts` should own the rule once the instance exists.

**A page-scoped gate cannot share a page at this scale.** `geometry-invariants` is the proof above. The existing browser suite runs it beside about 70 files that keep the residue rules; part 1 moves roughly 350 more onto that page. Either the page-scoped gates take their own instance, or the residue rules stop being convention and start being enforced. The `test-isolation-boundary` rule guards the module registry only, which the Risks section already says.

**The disk module cache pays for itself on the second run.** Vitest 4.1 ships `experimental.fsModuleCache`. With it on, the `unit` project ran in 60.0s cold and 50.7s warm; transform fell from 40.0s to 8.9s and import from 57.1s to 24.2s. The cache is 29 MB on disk.

**The CI runner is the same four cores, so the full migration stays off the table.** Measured on 2026-09-20 from the green run on this branch. The node suite takes 498 files and 6,882 tests in 160.6s, and the browser suite 108 files and 583 tests in 43.8s. The two runs cost 204.4s of suite duration between them. The phase split is the finding. `environment` sums to 1,489.4s in the node suite and to zero in the browser, where `tests` sums to 299.7s against 76.1s. So jsdom construction, not test work, is the node suite's largest cost. The step's condition is not met even so. `ci.yml` runs both jobs on `ubuntu-latest`, which has four vCPUs, the same count as the container the full-suite trial ran on. That trial measured 124s across two runs against 108s, so the merged suite loses wall clock here as well. Revisit on a larger runner, where the `environment` figure says what there is to win.

## Findings

**The workaround layer exists because jsdom has no layout.** `setup/jsdom-stubs.ts` (135 lines) stubs `matchMedia`, `ResizeObserver`, an `IntersectionObserver` that reports every target visible at once, `scrollIntoView`, `scrollBy`, canvas `getContext`, `window.print`, an `<iframe>` `contentWindow` getter, and object URLs. `setup/restore-prototype-focus.ts` undoes a `userEvent` patch that jsdom cannot undo itself. `helpers/with-fake-time.ts` installs a fake `jest` global so RTL's `waitFor` advances the clock. `vitest.config.ts` swallows one `window is not defined` error from a virtualizer timer that outlives its file. `helpers/mock-dom-geometry.ts` and `helpers/stub-resize-observer.ts` fake the geometry that nine and seven files need. The `virtual-options` tests assert only that the row count is bounded, because react-virtual renders zero rows in a zero-size viewport. None of this exists in the browser suite, whose setup is 61 lines.

**The split in `CONVENTIONS.md` §10.5 costs a second file per component.** Eight components carry a jsdom file and a browser twin (`grid-pinning`, `grid-width-settle`, `grid-row-reorder`, `grid-infinite-scroll`, `grid-resize`, `chart-aspect-legend`, `chart-resize-tracking`, `use-is-truncated`), and each twin's header explains what jsdom could not see. The a11y gate disables `color-contrast`, `target-size`, and `region` under jsdom and re-enables the first two in three browser files. The corpus in `a11y/cases` already feeds both suites, so the case list has one home and two runners.

**A third of the jsdom suite touches no DOM.** 142 of 411 files in the unit tree import nothing from Testing Library and reference no `document`, `window`, or `render`. `utilities/` (18 of 18), `recipes/` (9 of 9), and the module engines (`map-geometry`, `chart-scale`, `query-evaluate`, `grid-sort-state`, and 41 more `.test.ts` files under `modules/`) are pure. Each of them pays jsdom, three setup files, and four `vi.mock` doubles for nothing, and each can leak DOM state into the shared window by accident. The `.test.ts` extension is not a clean proxy: 37 of the 52 `.test.ts` files under `components/` are hook tests on `renderHook`.

**Five test shapes repeat across the component tree.** The counts are the density triad (28 tests, 10 files), "passes through HTML attributes" (30 tests, 27 files), 22 skeleton-pairing tests across 21 files, the text-input legs across 13 components, and "renders as a link when href is provided" (9 files). `a11y/cases` is already the registry that the axe, focus, trap, and roved gates read; the other five shapes have no registry, so a new component gets them by copy or not at all.

**Half of the DOM assertions read structure, not behaviour.** `bySlot` and `allBySlot` appear at 1,994 sites in 150 files, more than `getByRole` (857 sites, 91 files). Tailwind class strings are asserted at 637 sites in 112 files, counted over `src/__tests__` and `src/docs`. Three forms hold 454 of them in 99 files: `toHaveClass` (122), a `className` string matcher (316), and `classList.contains` (16), and 107 of the `toHaveClass` sites sit inside the jsdom `unit` project, which is the figure a `toHaveClass` scan alone returns. Two further forms hold the rest. `getAttribute('class')` holds 124 sites in 24 files, almost all of them SVG in the chart and map tests, where `className` is an `SVGAnimatedString` and not a string. Another 55 bind the class list to a local first, named `cls`, `paint`, `row`, or `plain`, so a pattern that reads the `expect` line alone misses them. `tagName` is asserted at 113 sites in 60 files. A class assertion fails on a cosmetic recipe edit and passes when the recipe row is wrong but the class is present. Where the equivalent recipe test sits is a separate question, and the census under Order answers it. `bySlot` returns `null`, so 62 files pair it with `present()` to get what a Testing Library query gives for free: a thrown error with a DOM dump, and a `findBy` variant.

**The boundary project holds two kinds of rule.** Ten of the nineteen `*-boundary` tests are import-layering rules over source text (`hook-purity`, `primitive-purity`, `kiso`, `katakana-purity`, `kata`, `recipe-import`, `create-context`, `component-ma`, the sibling-import half of `component-boundary`, the import half of `engine-purity`). Biome 2.5 expresses five of them in full, and one in half, as `noRestrictedImports` with gitignore-style `patterns` under a per-glob `overrides` entry. The four that do not move, and the two banned-token scans (`spacing`, `data-slot`) that its GritQL plugins cannot take either, are recorded under Order and Ruled out below. The other rules are semantic and stay as tests: `tsdoc-coverage` walks alias chains with the compiler API, the two filename rules check symbol-to-filename parity, `static-component` holds a curated contract, `test-isolation` re-parses `vitest.config.ts`, and `component-boundary` ties a Context render to `'use client'`.

**Helpers duplicate what one generic factory or the runner already does.** This paragraph read, at the document's own commit: `makeChangeEvent`, `makeFocusEvent`, `makePointerEvent`, and `makeKeyEvent` share one shape; `matchMedia` and `ResizeObserver` are stubbed twice each; `noop` is declared five times; `stubWindowScrollBy` has no test importer; 12 files carry an `afterEach(vi.unstubAllGlobals)` that `unstubGlobals: true` already runs; 13 files hand-roll fake timers beside the `withFakeTime` helper that 9 files use; `userEvent.setup({ delay: null })` appears 327 times with no fixture; three files define the same `makeWrapper`. A census against a later commit disproves five of the eight, and the entry under Order below holds the corrected figures and the two items it did find.

**Seven modules hold process-global state that no seam resets.** `src/hooks/use-scroll-lock.ts:6`, `src/hooks/use-grabbing-cursor.ts:6`, and `src/utilities/dismiss-layers.ts:8` balance a counter or an array on mount and unmount; `src/utilities/media-query.ts:7`, `src/utilities/document-listener.ts:6`, `src/components/time-ago/time-ago-ticker.ts:13`, and `src/hooks/use-truncation.ts:79` keep module-scope state and touch `document` or `window`. `use-truncation` is the worst: `:96` assigns `sharedResizeObserver`, `:106` only unobserves, and nothing clears the reference, so the module caches a global a test installed and keeps it after the test restores it. `src/core/announcer.ts:67` ships the only `__reset*` export in the package and `setup/index.ts:24` is the only call to one; `utilities/dismiss-layers.test.ts:21` drains its own array in an `afterEach` instead, and no test file references `subscribeMediaQuery`, `matchesMediaQuery`, or `subscribeTimeAgoTick` at all. Every one of these outlives its file under `isolate: false`, and part 1 keeps that setting. Measure each before you add a reset: a proposed seam for the media-query registries turned out to guard nothing, because a registry drops itself when its last subscriber unsubscribes and RTL's `cleanup` unmounts every subscriber.

## Architecture

The proposal has six parts. The first three change where tests run; the last three change how tests are written. Each part stands alone, and the Order section gives the sequence that keeps every step measurable.

### 1. The browser for what jsdom fakes, the rest behind one number

Move into the browser suite the tests jsdom cannot answer honestly. The file list was the nine `mockDomGeometry` files and the seven ResizeObserver-stub files, and doing the work proved that list wrong: a file is not the unit, a case is. Both helpers serve two purposes, and only one of them is a workaround.

A case that writes a box onto an element and then asserts the engine agreed with it moves, and gains a real box. A case whose subject is the notification itself stays, because a browser cannot stage it: a real `ResizeObserver` never fires for a box that did not change, so an equality guard has no browser expression; a morph interrupt needs a height-only frame followed by a width-coupled one on demand; a detached-node measurement needs a notification from a node already gone. Counting how many observers a hook constructs, or that it disconnected one, is the same category. So is arithmetic at a boundary, where a case needs two widths set exactly equal and a browser gives what the font produces.

A third group leaves the DOM entirely. `computeThumb` and `resolveFrameSizing` take numbers and return numbers; they were under jsdom only because each shared a file with something that reads elements. Those are part 2's work, found by doing part 1's.

Retire each jsdom twin as its browser file takes the behaviour, and where a twin already covers a case, drop it rather than move it. Nothing in this step has to be undone if the full move lands later.

The full move, every rendering test in a browser with jsdom and its workaround layer deleted, stays the destination and waits on one number. The trials agree on what it is worth: the DOM is accurate, test bodies run at 0.59 to 0.70 of their jsdom cost, the eight twins collapse into one file each, and the workaround layer goes. They agree on its price too. `components/`, `hooks/`, and `primitives/` reached wall-clock parity for 48 test edits across five seams; `modules/` beat jsdom by 3s for 52; the whole movable suite lost, 124s against today's 108s, because 445 files on two pages cannot use four cores while jsdom uses all of them. The `environment` phase the browser deletes is real and large, 703.3s summed across `unit` and `integration`, and at full scale the lost parallelism gives it back.

So the decision rests on core count, not on the migration's merits, and one measurement settles it: the full suite on the CI runner. More cores mean more pages, and that is the only lever that puts 124s under 108s. Take that number before the jsdom project goes. If it does not move, keep both runners; this step is then the whole of part 1, and jsdom keeps the files a stub serves adequately. Either way this is the simplification move of the proposal, not the speed move; parts 2 and 3 and the `isolate` fix under Ruled out were the speed moves, and they landed first in [#1125](https://github.com/charliebeckstrand/midgard/pull/1125).

When the full move lands, keep three instances, split by what a setup-file `vi.mock` must toggle:

- `dom`: `@floating-ui/react`, `motion`, `motion/react`, and `shiki` mocked, as the `unit` project mocks them today. This instance absorbs `components/`, `modules/`, `hooks/`, `primitives/`, `providers/`, `layouts/`, `a11y/`, `docs/`, the integration files now under `boundary/`, and the current `browser/` files.
- `floating-ui`: `@floating-ui/react` real, as today.
- `isolated`: `isolate: true`, for the seven files that `vi.mock` a source module (`map-centroid-deferral`, `map-path-deferral`, `map-points-render`, `query-builder`, `use-pdf-viewer-document`, `use-pdf-viewer-report`, `chart-export-report`). The first five were the list this document shipped with; the Measured section holds the run that found the other two, and what happens when one is missed. The rest of today's `integration` project moves to `dom`: the virtualizer timer that forced process isolation fires into a real window, where `window` is defined.

What the full move deletes: `setup/jsdom-stubs.ts`, `setup/restore-prototype-focus.ts`, the fake `jest` global in `with-fake-time.ts`, `mock-dom-geometry.ts`, `stub-resize-observer.ts`, `stub-match-media.ts`, the `onUnhandledError` filter, the `LANG` guard and the `TZ` pin (the Playwright context pins both), the axe rule exclusions in `helpers/axe.ts` and the three browser files that re-enable them, the eight jsdom twins whose browser file already owns the behaviour, and the `jsdom` dependency. `CONVENTIONS.md` §10.5 loses its jsdom-or-browser split, because every DOM test then has one home; its node sentence stays, for `pure`. The runner count does not change, as the Measured section records: `boundary` walks source text through `node:fs` and `pure` wants no DOM, so a node config outlives jsdom either way.

What the full move keeps: `renderUI`, `bySlot`, the module mocks, the corpus, `sequence.shuffle`, the timeout policy, and the reporter setup. `IS_REACT_ACT_ENVIRONMENT` stays `true`: the trial ran with RTL's default and the synchronous tests passed. The current browser files that set it to `false` for real `ResizeObserver` callbacks keep their `waitFor` form.

Every number above comes from a four-core container, and the Measured section holds the three runs. Read the failure tables there as the edit budget: the rate climbed from 1.6 percent of tests in `components/` to 3.7 percent in `modules/` to 2.4 percent across the whole movable suite once a single page-scoped gate is discounted, and no trial found a component defect.

### 2. A node environment for the pure layer

Open every no-DOM test file with `// @vitest-environment node`, and let the config build a `pure` project from that docblock: a scan at config time collects the files that declare `node`, the `pure` project includes exactly those, and `unit` excludes them. The 126 pure files then run on one shared node worker with no jsdom, no DOM stubs, no module doubles, and no RTL cleanup, and the runner groups them by project so they never interleave with the jsdom files. One boundary rule holds the pair in step both ways: a file with the docblock reads no DOM, and a file that reads no DOM declares its environment. The rare file that reads no DOM itself but imports a module that needs a window at load declares `jsdom` instead, with the reason beside it.

Two earlier cuts of this part are recorded because each failed for a reason the next one needs. The first selected the project's files by directory, with an exception table for the DOM files inside the pure directories; the docblock replaced both, so the decision lives at the top of the file it governs. The second kept the docblock files inside the jsdom `unit` project and relied on Vitest's per-file environment switch; under `isolate: false` a shuffled queue then rebuilt jsdom and its module graph at every crossing, measured at twice the suite's wall clock, and needed a custom sequencer and window guards in the setup files to recover. The project is the grouping primitive the runner already has, so the docblock feeds it.

The speed gain is small: about 37ms of setup per file, or six seconds of worker time. The accuracy gain is the point. A pure test cannot reach the shared window, cannot depend on a mock it did not ask for, and runs anywhere Node runs, with no browser.

*Applied in [#1125](https://github.com/charliebeckstrand/midgard/pull/1125). 144 files carry the docblock, `vitest.config.ts` builds the `pure` project from it, `node-environment-boundary.test.ts` holds both directions of the rule, and `CONVENTIONS.md` §10.5 states the placement.*

### 3. The disk module cache, on every machine

Set `experimental.fsModuleCache: true` in both configs and add its directory to the CI cache beside `.turbo`, keyed on the lockfile with a restore prefix. The warm path took 9.3s off the unit project on this machine and 31s off its transform phase; on CI the restore turns every run into a warm run. The option is experimental, so pin the Vitest version and drop the flag if a release note changes its semantics.

*Applied in [#1125](https://github.com/charliebeckstrand/midgard/pull/1125) for `vitest.config.ts` and the CI cache. "Both configs" is wrong: the browser suite cannot use the cache, and the Ruled out entry below holds the measurement.*

### 4. One component registry, every sweep derived

Grow `a11y/cases` into the registry it already is. Each entry keeps its canonical `element` and gains optional columns: `slots` (the `data-slot` anchors the component publishes), `open` (the interaction that reveals an overlay), and capability flags for `density`, `passthrough`, `skeleton`, `href`, and `textInput`. The sweep gates read the columns: the axe baseline, focus, trap, and roved gates as today, plus a sweep for each shape the corpus can express. Three are taken and two are not, and the entry under Order below says why. A new component writes one entry and receives every gate; a component that lacks a capability omits the column and no test is skipped by hand.

The registry removes about 130 hand-written tests and, with them, the drift the audit found: two of thirty skeleton components with no render test, and 21 identical tests that differ only in the import line.

### 5. Queries and assertions that read like the contract

Build `getBySlot`, `queryBySlot`, `findBySlot`, and their `All` forms with Testing Library's `buildQueries`, bind them into `screen` and `within` through `configure`, and retire `bySlot` and `present`. The change is mechanical over 1,994 sites, and a codemod does it in one commit. Each query then throws with a DOM dump on a miss, and `findBySlot` replaces the `waitFor(() => bySlot(...))` form.

Remove the class assertions in three passes, each behind the coverage that replaces it. About half read a behaviour the class stands in for (a drawer that fits its content, a menu that scrolls at its cap), and those move to the browser as computed style or geometry. About a sixth read a recipe row, and those move to `recipes/`, which does not own them today: the per-kata recipe test comes first and the deletion follows it. The remaining third read neither, and they stay, because a merge result, a forwarded `className`, the element a class was projected onto, the selector that drives a state, and a hook's return value have no expression except the class list. Leave `tagName` assertions where the element type is the contract (a `<fieldset>` for a menu section) and drop them where it is not.

Introduce property-based tests for the engines through `@fast-check/vitest`. The pure layer holds the invariants that tables under-sample: CSV quoting per RFC 4180, ring winding and spherical area in `map-geometry`, tick placement in `chart-scale`, sort stability and group nesting in the grid engine, evaluation in `query-evaluate`, and number formatting. A property replaces a table of five rows with a generator over the domain, and it shrinks a failure to the smallest input. Keep the tables for the documented examples and add a property beside each.

Consolidate the helpers: one `makeEvent<T>` factory for the four event builders, one `matchMedia` stub, one `ResizeObserver` stub, one `noop`, a `user` fixture through `test.extend` so `userEvent.setup({ delay: null })` is written once, and `withFakeTime` as the only fake-timer path. Give the grid cluster one fixture module (`fixtures/grid.ts`) with `Row`, the columns, the rows, and `getKey`, so a change to `GridColumn` is one edit and not 37.

### 6. Import rules in Biome, semantic rules in tests

Move the ten import-layering rules into `biome.json`: one `overrides` entry per source layer, each with `noRestrictedImports` and the `patterns` that the test's regex encodes today. Move the two banned-token scans into GritQL plugins scoped by `includes`. Each rule then runs in `biome check`, on staged files at pre-commit, and inline in the editor, and the `boundary` project keeps the nine semantic rules and the two recipe-arithmetic invariants.

The speed gain here is small, because the boundary rules take 72ms at the median. The gain is that a violation surfaces at the keystroke, and that about 600 lines of `walkSource` regex become declarative configuration.

## Risks

**Browser mode changes what `act` sees.** Real `ResizeObserver`, `IntersectionObserver`, and scroll events land outside React's act scope. The current browser files handle this with `waitFor`; the migrated jsdom files that stub those observers today will need the same form where they asserted synchronously after a resize. The trial found three such assertions in 215 files.

**Chromium in the gate job.** The gate today runs without a browser, and the browser job exists so the download does not serialize into it. With one suite there is one job, and it pays the cached download (about 170 MB, keyed on the lockfile) on every cache miss. Measure the cold-cache cost before the merge; the alternative is to keep two jobs and split the instances across them.

**`isolate: false` in a browser shares one window across files.** The jsdom suite has run that way since August and its residue rules apply unchanged: remove appended nodes in `onTestFinished`, never `vi.mock` per file, and keep `sequence.shuffle` on so an order dependency fails early. The `test-isolation-boundary` rule extends to the new instances by adding them to its project list, but it guards the module registry only; the module-scope singletons in the Findings section are the other half of this risk, and no rule covers them. Two of those residue rules are unenforced in the browser suite as it stands. `vitest.browser.config.ts` sets no `sequence`, so its files run in a stable order and an order dependency never surfaces there; that stable order is why `browser/setup/index.ts` could go without the `__resetAnnouncer` call that `setup/index.ts` has always made, until the trials below hit the leak.

**Turning the shuffle on is a project, not a switch.** It was tried on 2026-09-19 and backed out. Ten seeds: eight green, two red, three distinct tests. `pdf-viewer-highlight-layer` fails its rotation case under seed 2 and its zoom case under seed 10, and `current-rest` fails its fade case under seed 10. Both pdf-viewer cases have one symptom: after the page takes its initial fit, the toolbar controls stop moving it. Zoom leaves the image at 666px and rotation leaves the frame at the upright 861.875px, so the assertions read a size that never changed. The file passes alone, and it passes when run straight after the two files that preceded it in seed 2's order, so the trigger is cumulative page state rather than one neighbour. Three mechanisms were ruled out: RTL's wait budget (a 5s local budget does not help), a leaked dismiss layer (`dismiss-layers.ts` answers Escape, never a click), and the shared truncation observer (`use-pdf-viewer-viewport-size.ts:53` constructs its own `ResizeObserver`). The cause is unidentified. Until it is, the shuffle cannot land: it would redden about one CI run in five.

Two nearby facts belong with it. Seventeen browser files set the shared page's viewport and none restore it, which this document reads as a file inheriting whatever ran last — a probe disproves that half, and the entry under Order below holds it. And the browser config carries no timeout policy at all, where `vitest.config.ts:74` injects a scaled `asyncUtilTimeout` and states the rule that machine speed must change when a test passes and never whether it passes; RTL's 1s default governs the suite that does real layout on the most loaded page. Raising it is not free, and that is its own finding: lifting the budget to 4s turned eight green seeds red, because tests have grown to depend on a wait that expires quickly, and a wait meant to expire now runs four times as long and exhausts `testTimeout`. The budget and those tests have to move together.

**The fs module cache is experimental.** Vitest documents it as such. If a release changes its invalidation, a stale module serves a test. [#1125](https://github.com/charliebeckstrand/midgard/pull/1125) keys the CI cache on the commit SHA with a restore prefix, and the prefix carries an entry across commits, so the key bounds nothing on its own. Vitest's own invalidation is the only guard, which is why `vitest.config.ts` states beside the flag that each Vitest bump needs its release note read. `VITEST_SEED` replay does not depend on it.

**Snapshot tests.** The suite has none, and the proposal adds none. A snapshot pins structure, which is the class of assertion this proposal reduces.

**The disk module cache for the browser suite.** Measured. With `experimental.fsModuleCache: true` added to `vitest.browser.config.ts`, a cleared cache, and a warm Vite optimizer, the 102-file suite took 33.9s cold and 34.4s warm against a 32.8s baseline with the flag off, and every run reported `transform 0ms`. **GritQL plugins for the banned-token scans.** Measured on Biome 2.5.3. A plugin loads and reports, and `` `createContext` `` as a bare pattern fires on every occurrence of the identifier, which is too wide: it reads the call site as well as the import. Scoping it to the import is where it stops. `` `import $clause from 'react'` `` matches `import { createContext } from 'react'` and does not match `import { createContext, useState } from 'react'`, and none of a `contains` clause, a `within` clause, or a `$...` list pattern reached the second form. **Accumulation on the shared page.** Measured on 2026-09-20 with an instrument that counted live observers, live animations, DOM size, and frame cadence across a full 583-test run. Nothing accumulates. The DOM after teardown holds 17 elements and 14 head children at every sample, from the first file to the last. Live animations are zero at every sample. `requestAnimationFrame` delivers at 16.6ms to 16.8ms throughout, which is a clean sixty frames a second. Live IntersectionObservers are zero, MutationObservers reach five, and live ResizeObservers settle between four and twelve per page and do not climb. Two cautions belong with that. The samples are taken after teardown on an idle page, so they bound the degradation a run carries forward; they do not describe the page during a failing test. And the first instrument measured nothing at all, because Vitest re-executes a setup file for each test file: state declared in one restarts on every file. Only a module in the shared source graph persists across a page's files, which is where the second instrument put its counters. Any later probe of page-level state must do the same.

A handful of ResizeObservers outlive their own test, four to twelve of them. The count is bounded and steady rather than growing, so it is not a leak. `browser/setup/residue.ts` does not look for them.

**Running the current browser suite in isolation.** With `--no-isolate` on the existing browser config, the 100-file suite ran in 43.8s against 190.3s, and all 539 tests passed. That result is a free win to take now, ahead of part 1, and it is the same lever the migrated suite depends on.

**Three guards landed against the intermittent failure, a fourth was withdrawn, and none of them moved it.** The residue gate, the failure forensics and the singleton reset registry are defensible on their own terms, and together they left the rate where they found it: seven failures in the forty-five runs after the first guard, against three in the twenty-three before.

The withdrawn one is worth recording, because it was a plausible change that made the suite worse. A restore of the viewport after each file was meant to stop the seventeen files that resize the shared page from leaking a size forward. It restored to `window.innerWidth` read at setup load, which is Vitest's own default of 414x896 (`resolved.browser.viewport.width ??= 414`) rather than a size this repo ever chose. So it did not remove the inheritance; it moved roughly eighty files that declare no viewport off a predecessor's width, often 1280, onto a phone width most of them were never verified at. Five failures in the eighteen runs after it landed, against three in the twenty-three before, so it is at best not a fix. It is reverted.

The invisible coupling it aimed at is real and still open, and the fix is an arrival contract rather than a departure hook: declare `browser.viewport` in `vitest.browser.config.ts` so the default is a decision, then have each file that needs another size declare it once at file scope. A file's size would then be owned by the file, and a mid-file setter would stop crossing the boundary. Until that lands, a file whose geometry depends on a size must set it in a `beforeAll` at file scope. One block in `chart-aspect-legend` did not, and passed only because a sibling block above it had set 960x700. Twelve consecutive clean runs in the middle of that looked like a fix and were luck, which is the trap this rate sets for anyone measuring in short batches.

What the guards did buy is evidence. Five victims are now known rather than three, and they have nothing structural in common: `map-zoom-pick` and `list-item-hit-area` click, `grid-pagination-focus` reads an attribute after focus moves, `pdf-viewer-highlight-layer` takes a zoom step, and `grid-column-fit` auto-sizes a column. Every one passes alone, repeatedly, at the same viewport it fails at in the suite: `grid-column-fit`, `list-item-hit-area` and `grid-pagination-focus` each ran six times in isolation without failing. At the moment of failure the page is clean. The forensics report no residue on the body, no page scroll, a normal `activeElement`, and `document.hasFocus()` true.

**What they share is shape, not structure: every failure reads a value that had not finished settling.** `grid-column-fit` is the clearest, because its numbers name the mechanism. It waits for `scrollWidth <= clientWidth + 1`, meaning the content is no longer truncated, and then asserts the column is wider than 600. It failed at 480, so the wait was satisfied by a state where the content fitted a narrower column than the case expects. The wait is a proxy, and the proxy admits the wrong state; under load the wrong state lasts long enough to be read. A `waitFor` whose condition can be met before the thing the next line asserts has happened is a class of defect rather than one bug, and it would explain victims that share no component, no helper and no assertion style.

**The lead is confirmed for one victim, by reading the implementation rather than the rate.** `measureColumnIntrinsics` returns a `cells` count, and its own TSDoc names the state: a pass that reads no body cells measured no content, so every profile falls back to its header floor. `use-grid-column-auto-size` treats such a pass as provisional and re-measures, and it flips `settled` only once a pass reads real body cells. So the component already publishes the distinction the case needs. The case did not use it. It waited for `scrollWidth <= clientWidth + 1`, which a provisional floor-only fit satisfies, because at the header floor the content genuinely fits. It then asserted the column is wider than 600 and read the 480 the floor left. Two cases in `grid-column-fit` carried that shape, both for a user-invoked fit, and both now wait on the width and the fit together so a provisional pass cannot end the wait.

A scan of the browser suite finds 78 places where a wait reads one quantity and the next line asserts another. Most are sound: waiting for a dialog to close and then asserting focus returned is a real ordering, not a proxy. The dangerous subset is where both sides read a measurement, since only a measurement has a half-settled value to return. That subset wants a per-case reading rather than a sweep, and no rule should be written until more than one file has been confirmed.

That also reopens the wait budget, which was ruled out too quickly. Raising `asyncUtilTimeout` to 4s turned eight green seeds red, and that was taken as evidence the budget is not the problem. It is evidence of something narrower: the budget cannot be raised while tests depend on a short one to express that nothing happens. Fix those first, by giving each an explicit short window of its own, and the global budget becomes raisable. Whether it then helps is a separate measurement.

**The shuffle does not detect an order dependency here, because a seed does not reproduce.** Nine shuffled runs on 2026-09-20, after step 4 and the guards: five red, four green. A seed fixes the file order and nothing else. Seed 3 gave two failures on one run and one on the next. Seed 10 gave one failure and then none. Seed 2, which this document records as a reproduction, passes now, and it cannot be compared anyway: step 4 changed the file list, so the same seed is a different permutation. Four victims appeared across those runs, and no two runs agreed. So the shuffle raises the failure rate, from about one run in eight to about one in two, by changing which files sit beside a heavy neighbour, not by exposing a file that depends on its predecessor.

**The wait budget is not the mechanism, and it is also not the trap this document called it.** Measured with `asyncUtilTimeout` at 4s and `testTimeout` at 15s together, which the earlier trial did not do. The three red seeds stayed red, each on the same victim, so four times the budget buys nothing. The five green seeds stayed green, which is the correction: the eight seeds that reddened at 4s reddened because a wait meant to expire exhausted a 5s `testTimeout`, not because tests depend on a short budget to express that nothing happens. The budget is raisable as soon as `testTimeout` rises with it. It is simply not the lever.

**One victim is root-caused, and the cause is the component rather than the test.** `grid-pagination-focus` clicks Next twice and asserts that focus lands on the current-page marker. `GridPagination` wires each control as `goToPage(pageIndex + 1)`, an absolute target computed from the rendered `pageIndex`, and `await user.click()` resolves on dispatch rather than on React's commit. Two clicks against one render therefore both target page 2, which a probe reproduced deterministically: clicking Next twice with no commit between lands on page 2 of 3, never page 3. The focus symptom follows from the same fact. `goToPage` sets a `restoreFocus` latch that a `useLayoutEffect` keyed on `[pageIndex]` consumes, so a `setPageIndex` to the page already current runs no effect: the latch stays armed, focus stays on the still-enabled Next control, and the assertion reads an element with no `aria-current`. A double-click on Next advances one page in production for the same reason.

The fix is taken, and it is smaller than the proposal made it sound. `@tanstack/table-core` declares `setPageIndex` as `(updater: Updater<number>) => void`, and it clamps the result to the page count. The view's resolver forwards straight through, so only the view's narrowed `(index: number) => void` declaration blocked an updater. The change un-narrows that declaration, makes Previous and Next relative, and replaces the `restoreFocus` latch with a navigation count. A navigation onto the page already current then runs the restore, rather than arming it for a later change the consumer drove. The regression test is in jsdom, not the browser: two clicks inside one `act` reproduce the defect with no focus engine.

**The victim set is larger than this document says, and it grows as you sample.** Ten shuffled runs on 2026-09-20, after the pagination fix, added four names to the five recorded below: `current-morph` on two cases, `scroll-overflow`, and `drawer-fit-travel`. That makes eleven across the sampling so far, and no run agrees with another. So the set is not a list to work through. It is what a sample of one rate looks like.

**With `grid-pagination-focus` fixed, every remaining victim reads a geometry or an animation.** `grid-column-fit` takes a column width, `current-morph` a panel height tween, `scroll-overflow` a re-measure after content grows, `drawer-fit-travel` a drawer height, `pdf-viewer-highlight-layer` a zoom and a rotation, `current-rest` a fade completion, and `map-zoom-pick` and `list-item-hit-area` a coordinate under the pointer. The one victim that was not a measurement is the one that turned out to be a component defect. That is a shape worth weighing: the rest stall on a measurement that the budget measurement above says is not merely slow.

**`current-rest` was read for a defect of the confirmed shape and holds none.** It waits for panel B to hide, clicks the tab, and waits for it to wake. The first wait is a proxy: `useMountHold` starts a panel that mounts inactive already rested, so `display: none` is true from B's first commit and says nothing about the container being ready. But the wake path does not race. `useMountHold` clears its latch during render, in React's adjust-state-during-render form, so a panel that becomes current wakes in the same pass that reveals it. Two forcing functions confirm it: a click with no await after the render, and three clicks landing on one render, both wake B. The file also did not fail in ten runs on the branch that read it. The lead is spent; the timeout is not a defect in this component.

**The six unread victims were read against the confirmed shape, and it does not explain them.** Twenty cases across `current-morph`, `drawer-fit-travel`, `list-item-hit-area`, `map-zoom-pick`, `pdf-viewer-highlight-layer`, and `scroll-overflow`. Eighteen are sound, each for a reason in the component rather than in the case. `map-zoom-pick` renders at an explicit `width`, which turns off both measurement axes in `usePlotFrame`, so there is no canonical-to-measured swap for a click to land inside. Every assertion in `pdf-viewer-highlight-layer` is relational: the page image and the highlight layer read one `useMemo` through one context value and write it in the same commit, so a provisional scale moves both boxes together and the equality still holds. `useScrollOverflow` measures from live layout on every trigger and publishes only the answer, so it holds no provisional pass to catch. `list-item-hit-area` contains no wait at all.

**One case is confirmed, and its wait turned out to order nothing.** The drag case in `drawer-fit-travel` waited for `panel.style.height` to go non-empty, then read the panel's box. Three writers set that property, and `travelHeight` is one of them: it pins the panel at the height it is leaving, so a stray measurement that overrules the drag satisfies the wait as readily as the gesture does. Measured in the browser, the gesture writes the property in the same task as the keydown, while `aria-valuenow` holds its previous value into the next microtask. So the wait passed on its first poll. The case waits on `aria-valuenow` now, which moves on the commit that takes the size into state and which the travel cannot touch.

**A second hypothesis was sharper and died under measurement.** `use-current-contents-morph` compares box readings with `!==`, seeding from `getBoundingClientRect` and comparing against the observer's `borderBoxSize`, where the sibling `use-panel-fit` declares `SUBPIXEL = 1` and states the rule outright: read exactly, a fraction of a pixel answers yes. A spurious `discrete` would pin the container for the 250ms travel at mount, which the rest case in `current-morph` would catch intermittently. Instrumented against the real reflow probe, the two sources agree to the digit on every delivery — 600x48, 560x48, 520x72 — so nothing fires. The inconsistency with the sibling hook is real and stays recorded as latent fragility. It does not bite in this layout.

**The shape's population is the argument against it.** The dangerous form needs two things together: a wait that a half-settled state satisfies, and an assertion on an absolute value rather than on a relation between two quantities that settle together. The 78 sites counted above use the wider test, and the `pdf-viewer` zoom case shows why that is too wide — its wait is a genuine proxy over a two-pass settle, and it is harmless because the assertion never reads the width as a value. Under the narrower test, where the assertion sits outside the wait callback and compares a measurement against a literal or a pre-captured scalar, the browser suite holds 53 assertions in 45 cases, with 27 more cleared as relational. Almost none of those 45 cases are victims. If the shape were the mechanism, the eleven would concentrate there.

**Reading the victims still paid, in defects that are not wait defects.** `use-panel-resize` sets `resizing` in `onPointerDown` and never in `onKeyDown`, so the drawer publishes a "the gesture owns this height" attribute that the keyboard gesture leaves unset — which is why the drawer fix orders the commit and not the fit hook's stand-down. `list-item-hit-area` probed `(5, 5)` from the border box and clicked `(5, 5)` from the padding box, a border width apart, because Playwright measures `position` from the padding box. Playwright's own hit-target check does not cover the difference: it walks up from the element under the pointer to the click target, and the content area is a descendant of the row, so a press that lands on the bare row passes the check and reports a successful click. That is why the most-reproduced victim in the suite has three reproductions and no evidence. The case names the slot under the pointer beside the call count now, and a staged mis-hit reads `calls: 0, under: 'list-item'`. `scroll-overflow` held three assertions that could not fail, one of them dispatching a scroll at a node already removed from the document, where every quantity reads zero.

Three findings are left open rather than taken. Filling the `data-resizing` gap on the keyboard path changes what that attribute means, which is a decision about the component. `browser/setup/residue.ts` whitelists `STYLE`, `LINK`, and `SCRIPT` on `document.body`, and a leaked stylesheet is the one residue that changes every later file's computed layout while leaving the body clean by every other measure the forensics print. And `useScrollOverflow`'s `childList` branch has no browser coverage, because the growth case changes a child in place and the mutation observer never fires.

**The browser suite's intermittent failure, measured and still undiagnosed.** Twenty-three full runs with the shuffle off produced three failures, so about one run in eight rather than the one in four an earlier six-run sample suggested. Three victims so far, and they have less in common than they first appear: `map-zoom-pick` clicking a mark, `list-item-hit-area` clicking a row at (5, 5) and reading `elementFromPoint`, and `grid-pagination-focus` finding `aria-current` null after focus moves. The first two are coordinate-driven and the third is not, so "the click lands somewhere else" does not cover it. Every victim passes alone: `list-item-hit-area` ran ten times on its own without failing.

Six mechanisms are ruled out, and they are recorded because each cost a measurement. The wait budget: raising `asyncUtilTimeout` to 4s turned eight green seeds red instead, and a 5s local budget on the case that wanted one did not help. Predecessor residue: running the two files that preceded a failure straight before it reproduces nothing. A leaked dismiss layer: `dismiss-layers.ts` answers Escape and never a click. The shared truncation observer: `use-pdf-viewer-viewport-size.ts:53` builds its own. Body residue: the guard in `browser/setup/residue.ts` fails any test that leaves a node on `document.body`, and it stayed silent through a failing run. The shared viewport: the failing case passes at 600x600, 800x600 and 1280x800, which spans what the seventeen viewport-setting files leave behind.

What that leaves is state shared across a page that is neither the DOM under `body` nor the viewport. Document focus and the input pipeline are the obvious next places to look, since all three victims drive `userEvent`. Measure before believing it; six hypotheses have already failed here.

The residue guard lands anyway, as prevention rather than a cure. No file in this suite used `onTestFinished` to clear appended nodes, so the residue rule this document has stated since August had nothing enforcing it and nothing practising it, and part 1 would move roughly 350 more files onto that page.

**Step 6's instrument does not survive its census, so the step takes the part a measurement supports.** The codemod rests on `bySlot` having a Testing Library equivalent, and it has none. `data-slot` is not unique: 71 sites in eight files provably match more than one element, proved by the same file asserting a length above one on the same literal, and 394 sites query a literal that `allBySlot` reads somewhere. In `@testing-library/dom` 10.4.1 `makeSingleQuery` throws on multiple matches, so `queryBy*` throws exactly where `getBy*` does. Neither is a drop-in for a helper whose contract is the first match or null; only `queryAllBySlot(…)[0] ?? null` is, and that buys no error message. The rest of the step's arithmetic moved too: `findBySlot` replaces 3 sites in 2 files rather than the form this document assumed, the site count is 2,101 `bySlot` and 349 `allBySlot` across 195 files, 400 of them strip an optional chain and 554 a cast, 83 take a container that is not the render result, and `renderUI` has to go generic in two copies, because `src/docs/engine/__tests__/helpers.tsx` carries a second one for a separate TypeScript program.

What a measurement does support is narrower and was found by a failure rather than a count. 75 bindings in the browser suite carried a nullable query through an `as HTMLElement` cast, and a cast that lies puts the miss somewhere downstream: at a `getBoundingClientRect` on null, or at a `fireEvent` that reports only that it got no element. Each takes `present` now, or `getSlot`, a new helper that states the slot name once and reports a miss at the query. No non-null cast over a query remains in the browser suite. That is the whole of the step; the per-kata recipe tests and the three class-assertion passes stay as this document already re-scoped them.

**One victim of the intermittent failure is root-caused, and it is a test defect of exactly the shape above.** `grid-edit-validation-visible` is not among the eleven this document lists, and it failed twice in twelve full runs, which made it the most frequent victim in the sample. It clicked the edit trigger, read the editor with a bare `querySelector`, and passed the result straight to `fireEvent.change`. `browser/setup/act-environment.ts` lowers `IS_REACT_ACT_ENVIRONMENT` on purpose, so the click's commit lands on React's own schedule and not inside the dispatch, and the read can precede the editor. The cast carried the null and Testing Library reported `Unable to fire a "change" event - please provide a DOM element`, which has one origin in that library: a falsy element. The case waits for the editor now. A scan finds no second instance: every other query that follows an interaction is that interaction's own argument, taken after an act-wrapped render.

**The browser suite's dependency scan was broken, and nothing said so.** `vitest.browser.config.ts` carried no resolver for `virtual:component-modules`, so esbuild stopped at the first import of it and Vite reported "Failed to run dependency scan. Skipping dependency pre-bundling." The optimizer then served only the hand-written `optimizeDeps.include` list. Measured cold on a 4-core container: eight packages arrived one request at a time, two of them after the first test started, and each arrival re-runs the optimizer and reloads the page. `@vitest/browser` names that cost in its own warning — "Vite unexpectedly reloaded a test. This may cause tests to fail, lead to flaky behaviour or duplicated test runs." A five-line plugin in the config resolves the module to an empty map, which completes the scan and takes lazy arrivals to zero; the warm run falls from 30.3s to 26.3s. An empty map is exact here: a crawl of every relative import from `src/__tests__/browser/` reaches 1,492 files and none under `src/docs/`, so nothing this suite runs reads it. `docsPlugin` resolves the module too, and was the first fix taken, but it imports ts-morph and typescript at module scope, walks every barrel and demo to build the real map, and rewrites each barrel it serves to carry `__module` and `__name` — which would put the suite on docs-tagged barrels rather than the ones the package ships. None of that is what the scan needs. It is not a cure for the intermittent failure either, which reproduces with the scan whole and never fired that warning across twelve runs.

**The browser config declared no hygiene and no budget.** `restoreMocks`, `clearMocks`, `unstubGlobals`, and `unstubEnvs` are the four settings `vitest.config.ts` carries because a project shares a registry, and the browser config had none of them while running two instances at `isolate: false`. `testTimeout` and `hookTimeout` were Vitest's own browser defaults, 15s and 30s, which a version bump can move. RTL's `asyncUtilTimeout` had no policy at all, so the one suite that does real layout ran at the library's 1s default on every machine while the jsdom projects took 4s on CI. All six are declared now, and `browser/setup/index.ts` injects the budget as `setup/index.ts` does. Read back through `getConfig()`: 1000 locally and 4000 under CI. `restore-prototype-focus.ts` joins the browser setup too, as prevention — no browser file assigns `el.focus` today.

**26 wall-clock literals obeyed no policy, and ten of them could pass for the wrong reason.** Nineteen were real-time holds between 20ms and 400ms and seven were per-call `waitFor` budgets of 3s and 5s. The holds are the reason to act: ten wait past a delay and then assert that nothing happened, so too short a hold does not flake — it asserts nothing, because the thing the case denies had not had its chance. The tooltip cases hold 400ms against a 250ms hover delay. `browser/helpers/wall-clock.ts` gives both shapes a home, `pause(ms)` and `budget(ms)`, and a scale to the one that can take it. `budget` reads a `budgetFactor` provided beside `asyncUtilTimeout`, 1 locally and 2 on CI. `pause` does not scale, and the arithmetic says why: the 19 holds sum to 4.1s, so a factor of 2 would add that again to every green CI run, and the delay a hold outlasts is a `setTimeout` in the component, which fires on wall clock and does not stretch with CPU load. Two of the holds were a wait for a delivered measurement and take `frames()` instead, which returns as soon as the frame lands. About ten of the rest have an observable in their own file — a `data-testid` flag, the mount decision a tooltip publishes — and converting those is the deeper change this leaves open.

**The viewport does not cross a file boundary, so the coupling this document calls invisible is within a file only.** A probe on every file of a full run reports that all 108 arrive at one size and sixteen depart at a size of their own: Vitest resets the page to `browser.viewport` before each file. No departure hook is needed, and the restore this document records as withdrawn could not have worked for the reason it gives. What the probe does show is that the arrival size was never a decision — it is 414x896, Vitest's own default, and the suite has always run there. `vitest.browser.config.ts` declares it now, which changes nothing and stops a bump from moving it; the whole suite passes at 1280x800 as well, so gating wide later costs no edits. 414 is also the end of the range worth gating at, because `geometry-invariants` states its contract as no page-level horizontal overflow at the default viewport. The four `page.viewport` calls that sat inside an `it` — two files, every case in each — become one `beforeAll` apiece, and `test-isolation-boundary` holds that placement. `CONVENTIONS.md` §10.6 states the contract.

**The residue guard failed the files that obeyed the rule it enforces.** Its message and this document both say to reclaim an appended node in `onTestFinished`, and it ran from the setup's `afterEach`. Measured, the order is that `afterEach`, then each test's own `onTestFinished` in reverse, then anything an `onTestFinished` registered from a `beforeEach`. Only the last reads what every other teardown left. Wired into the jsdom projects from `afterEach` the guard failed eleven cases in six files at once, and not one was a leak: every one reclaims its node through `captureAppended`, which uses `onTestFinished` exactly as instructed. No browser file clears a node that way, which is why the browser suite never showed the trap. The check moves to the later placement, `residue.ts` moves to `helpers/`, and both setups serve it — `unit` shares one jsdom window across a worker's files on the terms a browser instance shares a page. A staged leak in each suite proves it still fails the culprit and names the node.

**The helper census corrects five of this document's eight redundancies and finds two it does not name.** `noop` is declared three times and not five, `afterEach(vi.unstubAllGlobals)` appears nowhere rather than in twelve files, `makeWrapper` does not exist under that name, `make-event.ts` already routes its four builders through one private factory, and the two ResizeObserver stubs differ in kind rather than repeat — one is the inert default, the other collects instances so a case can fire a resize by hand. `stubWindowScrollBy` has one importer, the global jsdom setup, so it is load-bearing rather than dead. What the census did find: `use-offcanvas.test.ts` declared a file-local `stubMatchMedia` that shadowed the barrel helper of that name and installed it by raw assignment, which `unstubGlobals` cannot revert, so the file carried a hand-written restore hook; and three files restored a fake clock in a `finally` alone, which a `testTimeout` abort skips. Both are closed.

**Four items are measured and not taken, each because the measurement says the work would cost more than it returns.** A shared grid fixture would collapse little: the tree holds 111 distinct `GridColumn` arrays across 151 declarations, the widest repeat covers six files, and the column set is usually the thing under test, so a fixture would carry more exceptions than users. A `user` fixture would have to absorb two shapes that differ in behaviour, `delay: null` at 278 sites and the library default at 102, and only 32 files use each. The four `new Date()` sites read the clock on both sides of their own assertion, microseconds apart, so the failure window is sub-millisecond at a month or year boundary and a pinned clock would add a leak to guard against. The two runtime `ctx.skip()` calls probe for a sub-pixel rounding dead zone and skip where the font produces none; forcing them to fail would redden the suite on a Chromium build rather than report a defect, and Vitest reports the skip in its summary.

**The intermittent failure is unchanged, and the sample is now larger.** Twelve full runs before this work: four red, on `grid-edit-validation-visible` twice, `scroll-within`, `pdf-viewer-highlight-layer`, and `list-item-hit-area`. That is a third of runs on this container, against the one in eight this document records on another. Of those victims one is now root-caused and fixed, and `scroll-within` is a new name: all four of its scrolling cases failed together while the case that scrolls by hand passed, so `scrollWithin` did nothing at all — which points at `findScrollAncestor` returning null rather than at a measurement that had not settled. That is a lead, not a finding; it wants an instrumented reproduction before anyone calls it a mechanism.

**Ten runs after the work put the rate at one in ten, and the fixed victim accounts for the difference.** Four of the twelve runs before were red, and two of those four were `grid-edit-validation-visible`. Discount it and the remainder is two in twelve against one in ten, which is the same rate at this sample size. Nothing else here was aimed at the failure, and nothing else moved it.

**The one red run carries new evidence, and it retires a theory.** `list-item-hit-area` failed on the diagnostic this document records adding — the slot under the pointer, printed beside the call count. It reads `calls: 0, under: 'list-item-content'`. So the pointer was on the right node and the handler did not run, which is not the mis-hit the padding-box reading predicted and not a staged miss either. The case holds no wait at all, and it clicks through a real CDP event in a suite that lowers the act environment, so the shape it shares with the one root-caused victim is an event arriving before React is ready for it. That is a lead and not a finding: it wants an instrumented reproduction that reads when the listener attached.

**`grid-pagination-focus` recurred after the fix this document records as taken.** One red run in seven, on the same case — two clicks on Next, then `aria-current` null on `document.activeElement`. The file passes three times out of three alone. So the absolute-target defect the fix closed was real and was not the whole of it. The case is worth reading again against what the fix left: the controls are relative now and a navigation count replaces the latch, and neither is what this run contradicts. A staged miss reads `current: 'none (button "Next page")'` beside `marker: 'present'`, which is the first of the two.

**Five negative tooltip cases cannot fail, and the shape of the fix is measured but not taken.** Each hovers an element whose content fits, holds past the 250ms delay, and asserts `queryByRole('tooltip')` is null. If the tooltip machinery were broken, or mounted nothing at all, every one of them still passes. `grid-cell-content.tsx:71` publishes the decision the case means to assert — the reveal wrap mounts only for a cell that is contacted and truncated, so a fitting cell stays a bare span — and a probe confirms the trigger count is the discriminator, rising from one to two as each cell is contacted and found clipped.

The other three do not take it, each for a reason the probe found.
