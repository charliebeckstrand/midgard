### B01-C01 — an inline `onReset` breaks the identity of `actions`

- **File:** `packages/ui/src/components/form/use-form-reducer.ts`
- **Mechanism:** `reset` lists the prop, so each new `onReset` makes a new `reset`, a new `actions`, and a new context value. `use-form-reducer.ts:258` `onReset?.()`; `:260` `[onReset],`; `:395` `[getValue, setValue, setErrorsExternal, setTouched, reset],`; `form.tsx:109` `onReset,`; `context.tsx:95` `<FormActionsContext value={actions}>`. - **Trigger:** `<Form onReset={() => …}>` under a parent that re-renders.
- **Documented intent:** `context.tsx:18` "Imperative form mutators. Stable across renders, so reading them never forces a re-render."; `context.tsx:53-54` "The actions object is referentially stable, so subscribing to it never triggers a re-render"; `use-form-value.ts:44` "`setValue` and `setTouched` keep their identity across renders."; `CONVENTIONS.md:182` "Use `useStableEvent` also for each other handler that keeps one identity for the mount and calls the newest props." - **Reach:** none. No root passes `onReset` to a Form; the only site is `form.test.tsx:102`, with a stable `vi.fn()`.
- **Severity:** low. Extra renders and identity churn, no wrong state, and no root passes the prop.
- **Prior art:** none. `2026-08-08-EFFECT-EVENT-PLAN.md:64` moved "`use-form-reducer.ts`'s two callback refs" (`reportSettled`, `reportInvalid`); `onReset` was never a ref. CLEANUP C8 records the compiler `Todo` skip, so no compiler memo hides the churn.

## Open questions

### Q1 (B01) — does a `{ fieldErrors }` return with no issues count as success? Gates B01-S3.

- **(a) Yes.** B01-S3 runs: apply the clears, then settle `ok: true`.
- **(b) No.** Every `fieldErrors` return is mid-flow, as `use-form-reducer.ts:41-42` reads literally; B01-C03 closes as by design and B01-S3 drops.

### Q2 (B01) — does `helpers.reset` inside `onSubmit` keep its own attempt live? Gates the B01-C02 part of B01-S2.

- **(a) Yes.** `onSettled` fires, and a throw after the reset reports. An outside `actions.reset` still supersedes, as `form.test.tsx:299-350` requires.
- **(b) No.** "Supersede any in-flight submit" (`use-form-reducer.ts:248`, `form.tsx:76-77`) includes the handler's own attempt; B01-C02 closes as by design and B01-S2 keeps C04 and C09.

### Q3 (B01) — how does the reducer keep an external issue apart from a client result? Gates B01-S4.

- **(a) Track the external keys in `FormState`,** cleared when that field's own value changes, on reset, or on submit. Changes the state shape and the `formReducer` tests. The only axis that runs into neither problem below.
- **(b) Re-validate a sibling only when its current result came from the client.** Needs the same tracking as (a).
- **(c) In `'touched'` mode, validate only the changed field and `changeValidationFields`.** Changes the documented client behavior (`form-reducer.ts:213-214` "The `'touched'` mode validates the touched fields."), and leaves `'change'` mode open.
- **Sub-question:** does an edit to the field that carries the server issue still clear it? `docs/pages/components/form/server-errors.tsx:13-18` ships that path, and today the message clears.

### Q4 (B01) — does the `preventDefault` in `handleReset` carry load? Gates B01-S6.
