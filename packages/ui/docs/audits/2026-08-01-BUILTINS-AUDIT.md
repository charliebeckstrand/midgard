# Built-in Adoption Audit

Survey of `packages/ui` (2026-08-01) for hand-rolled code that a library or platform built-in already provides, across React 19, Floating UI, dnd-kit, TanStack Table/Virtual, the remaining declared dependencies, and the web platform. The companion to the `<Activity>` adoption audit (landed in `eb4d128`, retired in `a1cbec4` once its findings closed out); this one covers everything else, and keeps its method — a claim is not a finding until something was read, probed, or run. Six claims did not survive that and are recorded under Corrections. Line numbers are as of this commit and will drift.

The headline is that adoption was already close to complete. Every survey came back with a long ruled-out list and a short findings list, and the ruled-out entries are the more useful half — several name a gap that looks like an oversight and is not. What the sweep did turn up was mostly **defects hiding behind hand-rolled code**, not idiom: an export that dropped rows, a date field that mis-read typed dates, a panel that would not dismiss, a menu that could not be opened from the keyboard.

## Landed

- [x] **`useIsomorphicLayoutEffect` retired** — the hook, its 24 call sites across 21 files, its boundary test, and its `useExhaustiveDependencies` registration in [`biome.json`](../../../../biome.json). It resolved to `useEffect` off the browser to silence React's "useLayoutEffect does nothing on the server" warning, which React 19 does not emit. Probed three ways: a `renderToString` of a `useLayoutEffect` component recorded no warning against the installed `react@19.2.7`; the string is absent from `react` and `react-dom`; and the same development build carries 132 other `console.error` sites, so the search would have found it. React's server renderer no-ops `useEffect` and `useLayoutEffect` alike and the module-scope ternary always resolved to `useLayoutEffect` on the client, so the hook had been a no-op wrapper since React 19. Behaviour-neutral.

- [x] **`arrayMove` — landed, then reversed in the grid engine** — `engine/grid-zone/map.ts` carried a private `moveItem` documented as "the dnd-kit `arrayMove` contract, without the dependency". The dependency is declared and `arrayMove` was already imported from it in three sibling modules. The two differ on a negative `to` — dnd-kit resolves it against the pre-removal length, native splice against the post-removal one — but neither call site can reach that path, so the swap is behaviour-identical. **Reversed since, and it must stay reversed:** `engine/` is the grid's pure core, and this one runtime import held its `@dnd-kit` / `@floating-ui` clause out of [`engine-purity-boundary.test.ts`](../../src/__tests__/boundary/engine-purity-boundary.test.ts). The private `moveItem` is back for that reason alone. The sibling call sites are React shell files, and they keep `arrayMove`.

- [x] **Grid export walked the wrong row model** (`use-grid-export.ts:51-55`). TanStack groups before it sorts, and `getGroupedRowModel` builds each header row with its first leaf's datum as `original`, so a grouped grid exported one row per group. The selection path failed with it: a group header's id is `${columnId}:${groupingValue}`, never a key in the mirrored selection state, so an active selection read as empty and fell through to the full set. Collapsing to leaves first answers both, through the `deriveLeafRows` and `manualGroupRow` the module already uses for its leaf set. The suite's 30 export cases had no grouping coverage; three new ones fail against the previous behaviour.

- [x] **`useEffectEvent` for two ref-held callbacks** — `useCopyButtonState` assigned its ref inside a dependency-less effect, so the ref held the previous render's callback until effects flushed and a copy resolving in that window called the stale one. `useResizeObserver` held no ref at all: it captured `callback` in the effect's dependencies and pushed the hazard to callers, its own doc comment asking for a stable reference and warning that a fresh one "re-subscribes the observer each render and re-fires its initial callback" — which, since it also invokes the callback on attach, made an inline measure-and-set callback a render loop. Its test pinned re-subscribe-on-identity-change; that pinned the hazard, not a feature.

- [x] **Ambient locale for date labels** — `dateCategoryFormat` built every plain-category date axis label as `MM-DD`, an order no locale writes, while `timeCategory` in the same file already formatted through `DateFormatter`. `DatePicker` derived its trigger label from `Date.prototype.toLocaleDateString` with no argument, which resolves to the runtime locale and can never see `<LocaleProvider>`. `DatePicker` now reads the provider. The chart reads the runtime locale rather than `<LocaleProvider>` — `useChartCartesian` calls both formatters with no locale and the chart module holds no `useLocale`, so the fix there is that the format is a real locale's rather than one no locale writes. Both formatters take a `locale?`, so wiring the provider through the hook is a small follow-up; it is not done here. `LANG` is exported by the `test` scripts so the one assertion that reads an unlocalized `Intl` result is deterministic. It cannot go in `vitest.config.ts` beside `TZ`: Node resolves ICU's default locale at process start and `test.env` is applied inside the worker afterwards, so a pin there reads as set and changes nothing — measured, after a first attempt made exactly that mistake.

- [x] **`DateInput` field order** (`date-input.tsx`) — `format` defaulted to `'MM/DD/YYYY'` and the component read no locale, while the `Calendar` it pairs with inside a `DatePicker` honoured the provider. A British user typing `10/06/2026` for 10 June got 6 October, silently. The default now reads the locale's own order from `DateFormatter.formatToParts`. Order alone is derived, not the separator — de-DE writes `10.06.2026` where this masks `10/06/2026` — since the three supported layouts each pin their own and widening that means reworking the mask's single-separator model.

- [x] **Truncation measured with a `Range`** (`use-is-truncated.ts`) — the hook built a `<span>`, copied the label text into it, and appended it *into the element being measured*, a React-rendered node. That is the classic `removeChild` hazard, and it put a second copy of the text in the accessibility tree, which the file-upload suite worked around with an `ignore: '[aria-hidden="true"]'` option on two queries. The correct measurement already existed one file over in `useTruncation`. An element whose text wraps now reads as not truncated, which is the better answer: no ellipsis is painted, so the reveal tooltip has nothing to reveal.

- [x] **`AbortController` for drag teardown** — `useResizablePanel`, `useHoldButtonGesture`, and the scroll-area scrollbar each listed their `removeEventListener` calls twice, so adding a listener meant remembering every list. `addEventListener(..., { signal })` collapses each set to one `abort()`, and the hold button drops its ref of stable handler identities outright — that ref existed only so add and remove could pair.

- [x] **Sibling-portal dismissal** (`isFloatingOutsidePress`) — the predicate spared a press in any other floating portal that did not contain this panel's reference. "Not an ancestor" is wider than "a descendant", and an unrelated sibling satisfied it, so such a press left the panel open. DOM ancestry cannot separate them: `PresencePortal` passes an explicit `root` under a `<UIProvider>`, so every portal is a sibling `<div>` under one node. Each panel now publishes its reference against its portal node, making the test exact. A portal that publishes nothing — an `Overlay`, which dismisses through `useDismissable` — keeps the ancestor test.

- [x] **Menu keyboard activation** (`menu-trigger.tsx`) — the trigger clones an arbitrary child and opened from `onClick` alone; `handleTriggerKeyDown` only armed the auto-repeat guard and delegated to `rovingKeyDown`, a no-op while the panel is unmounted. A native `<button>` hid the gap because the browser synthesizes the click. `Menu` now composes `useClick`, as `Popover` already did, whose `keyboardHandlers` bail through `isButtonTarget` precisely because native buttons need no help. The auto-repeat guard stays: `useClick` has no `event.repeat` handling anywhere.

## Corrections

Six claims from the first pass were wrong. Recorded rather than deleted, so the same ground is not re-walked.

**`motion` is not unused.** An initial grep for imports reported zero hits and was quoted as a ~100kB dependency carried for nothing. The grep used double quotes; the package formats with single. `motion` is imported in 46 files and is load-bearing — `AnimatePresence` in `presence-portal.tsx` is the mount lifecycle for every floating surface, and the overlay stack, `active-indicator`, grid rows, and the whole chart mark layer follow. The three surfaces named as hand-rolled alternatives are the evidence against: `primitives/reduced-motion` is a 7-line wrapper around motion's own `MotionConfig`, `use-enter-animation` decides *whether* an enter plays rather than animating anything, and the `ugoki` CSS transition tokens are deliberately off the JS path because the Activity audit's `transitionend` landings depend on them.

**`safePolygon` does not replace the submenu corridor.** The pointer-course work was read as a hand-rolled `safePolygon`. They answer different questions: `inCorridor` vetoes a *cursor move* within a level, while `safePolygon` is a `HandleClose` fed to `useHover` whose only lever is `onClose()` — and `MenuSub` never calls `useHover`. Three concrete mismatches, all read from source: `safePolygon` is timer-based under its default `requireIntent: true` (a `40ms` `setTimeout` behind a cursor-speed threshold), which is exactly what that work set out to remove; its polygon is anchored to the reference/floating rect pair and placement-switched, where the corridor anchors to the last accepted arrival point; and its nested-child guard needs a `FloatingTree` the package does not have. `blockPointerEvents` is likewise not the answer to a closed-but-exiting panel still taking input, which `floating-surface.tsx` fixes at the node.

**`markOthers` is not exported by `@floating-ui/react`.** It is internal to `FloatingFocusManager`, and absent from both the main entry and `./utils`. Prose describing it as an import — including in the Activity audit — describes an effect, not a call.

**`useDismiss({ outsidePress })` cannot replace the custom listener.** This is the claim two hooks rest on, so it was traced rather than trusted. `closeOnPressOutside` collects `[data-floating-ui-inert]` markers and spares a press whose root ancestor contains none, treating it as a third-party element injected after the floating element rendered. A panel opening inside a modal Dialog and portalling to the same `<UIProvider>` node is a later-mounted sibling, so it is unmarked and its presses can satisfy that test. An `outsidePress` *function* cannot rescue it either: the predicate runs **before** the marker check, so it can only veto a dismissal, never force one.

**There is no date-math bug in `date-input-utilities.ts`.** Its hand-rolled `daysInMonth` and two-digit-year handling read like a classic defect site. Brute-forced against `endOfMonth(new CalendarDate(y, m, 1)).day` for all 12 months of years 1–9999: zero mismatches. The proleptic Gregorian rule is correct and the range guard fires before the `setFullYear` path can misbehave. It remains duplication — a second date stack inside a component whose sibling already routes through `@internationalized/date` — but it is not a defect, and is recorded at that weight.

**Hoisting `useGrabbingCursor`'s injected style to React's `<style href precedence>` would freeze every cursor in the app.** The types support it and the manual `document.head.append` with a module-level reference count looks like a textbook document-metadata-hoisting win. Rendered and unmounted under `react-dom/client`: React never un-hoists, so the rule — `*{cursor:grabbing !important}`, whose whole purpose is to lift when the drag ends — would persist permanently after the first drag. The manual injection is the correct implementation.

## Open

- [ ] **`useRole`'s reference half is hand-stamped on four triggers** — `menu-trigger.tsx`, `popover-trigger.tsx`, `menu-sub.tsx`, and `combobox-input.tsx` each write `aria-haspopup`/`aria-expanded`/`aria-controls` by hand beside a locally minted `useId()`. The stated reason for `role: null` is sound and was confirmed: `getFloatingProps` is spread onto the positioning wrapper, not the inner panel, so `useRole`'s floating half would nest a duplicate widget around the real one. But that condemns the floating half only, and `useInteractions([{ reference: role.reference }])` takes the trigger wiring alone. The concrete win is `MenuSub`, which hand-writes the nested `role="menuitem"` that `useRole` derives from `useFloatingParentNodeId`. **Blocked on:** that derivation needs a `FloatingTree`, which the package does not have; splitting the return halves is also supported by the type but off the documented path.

- [ ] **`PopoverTrigger`'s hand-rolled ref merge** (`popover-trigger.tsx:29-71`) — `assignRef` plus a `mergeRefs` callback, where `useComposedRef` already wraps floating-ui's `useMergeRefs` and both sibling triggers use it. Only a partial adoption is available: the cleanup deliberately nulls `triggerRef` and `childRef` but **not** `setReference`, because `setReference(null)` during deletion effects can cascade into "Maximum update depth", and `useMergeRefs` nulls uniformly. A correct change merges the two safe refs through `useComposedRef` and keeps `setReference` on a separate non-nulling callback. Small, and ranked low.

- [ ] **The tooltip's bare `safePolygon()`** (`use-tooltip-state.ts:120`) — defaults are `buffer: 0.5`, `requireIntent: true`. With intent required, a slow deliberate traverse under `0.1 px/ms` closes the tooltip, which is the one case an interactive tooltip most wants to survive. Not hand-rolled code, so not a finding; recorded because the default is non-obvious and `safePolygon({ requireIntent: false, buffer: 2 })` is the dial if interactive tooltips ever read as closing under a careful cursor.

- [ ] **`getFacetedMinMaxValues` is imported nowhere** — the query engine has a `between` operator and `filterType: 'number' | 'date'` whose bounds are free-form inputs. Facet-derived `[min, max]` would let the range editor clamp to the column's actual span, and `getFacetedUniqueValues` is already wired for `select`, so the plumbing exists. An addition, not a replacement.

- [ ] **`useVirtualWindow`'s uniform-height assumption costs two features their virtualization** — `resolveGroupingGates` stands virtualization down whenever grouping or master-detail is active, and the wrapper's omission of `measureElement`/`getItemKey` is why. That is a wrapper-level choice, not a library limit: react-virtual supports dynamic measurement. But the collapse animation depends on leaves staying mounted through the `1fr`↔`0fr` transition, `measureElement` on `<tr>` in a fixed-layout table with spacer rows is unverified, and `ROADMAP.md` already lists variable-height virtualization as deliberately deferred. The Activity audit priced the alternative and shipped it. **Fix:** at minimum, say so in the wrapper's TSDoc, which today reads only "Assumes uniform heights".

## Ruled out

**dnd-kit is fully adopted.** `@dnd-kit/modifiers` is not installed and five of its modifiers are transcribed into `grid-reorder-compute.ts` — verified identical against the published tarball, branch for branch. Taking the dependency would delete ~98 lines of pure arithmetic plus a 51-line test, and buy three modifiers nothing here wants, on a package that shares 6.x's maintenance clock. Not worth it; the provenance comments are what keep it honest. Everything else on the checklist came back negative: `CSS.Transform.toString` is used at every site that needs one (the single hand-built transform takes only the x translate, deliberately, because dnd-kit's would emit `scaleX`/`scaleY` and stretch cell content); `activationConstraint`, `sortableKeyboardCoordinates`, and core autoscroll are all configured rather than rebuilt; `useGrabbingCursor` fills a real gap, since `@dnd-kit/core` contains zero occurrences of `cursor`; and `useCombinedRefs` is strictly less capable than the local `useComposedRef` (callback refs only, no object refs, no React 19 cleanup). `useDndMonitor` is unused and there is a structural argument for it — `useSortableList` holds `activeId` above the `DndContext`, so drag start and end re-render the owner's subtree — but rows are memoized and the cost is two renders per gesture, not per pointer move. It wants a bench before anyone acts on it.

**TanStack Table is used correctly, and the places that depart from it were measured.** `nextSort` does re-derive the sort-cycle state machine, and shift-click matches `toggleSorting(undefined, true)` exactly — but plain-click differs in one case (clicking the last-priority sorted column would keep the other sort columns instead of collapsing), `sortDescFirst` would need pinning for numeric columns, and adopting `getToggleSortingHandler` means threading the table instance into every header cell and inverting the ownership of a public controllable binding. 27 lines against that is a poor trade. `makeSmartSortingFn` is a strict superset of every built-in `sortingFn` — none handles `$1,234.50`, accounting negatives, or percentages — and `sortUndefined: 'last'` provably cannot replace the empties-last dance, since it fires only on `undefined` while the grid also treats `null` and `''` as empty. The off-engine sort and the lite-cell body are recorded optimizations (100k sort 162→48.6ms; 100k mount ~450→16ms), not oversights, and `flexRender` is deliberately bypassed there. `grid-aggregate` cannot be `aggregationFns` because the same reducer serves grand-total and per-group-footer rows, which are not group rows. Selection cannot use `getIsAllRowsSelected` because it reads `getPreGroupedRowModel().flatRows` and materializes the model the materialization gate exists to avoid. Column pinning, ordering, visibility, resizing, and filtering are all pure engine consumers already. `fuzzy` is not a built-in `filterFn`; nothing duplicates one.

**`primitives/virtual-options` and `useVirtualWindow` call `useVirtualizer`; they do not reimplement it.** The re-sync guard is genuinely needed — react-virtual re-resolves the scroll element in a layout effect, and refs attach bottom-up, so a child's layout effect can resolve `null` and never recover. The spacer `<tr>` pattern is not replaceable by `paddingStart`/`paddingEnd`, which add fixed end padding rather than tracking `virtualItems[0].start`; and for a `<table>` the spacer form is required, since absolutely positioning `<tr>`s destroys the column grid.

**Most React 19 built-ins are already in place.** `.Provider` has zero occurrences; `forwardRef` has zero in production code (the 13 hits are test mocks and the docs' ts-morph extractor, which must recognize the wrapper to parse code it does not own); `useContext` has one. `useSyncExternalStore`, `useId`, `use(Context)`, and ref-as-a-prop are throughout. `useMediaQuery` was named as the obvious `useSyncExternalStore` candidate and already is one. `useComposedRef` is a two-line delegation to `useMergeRefs`, which React has no equivalent for — ref-as-a-prop removes `forwardRef`, not the need to compose. `useDeferredToggle` is not `useDeferredValue` despite the name: it freezes a selection across an exit animation, released on `onExitComplete`, where `useDeferredValue` defers by priority and cannot be held to a `transitionend`. `<ViewTransition>` does not exist in the installed runtime — absent from `index.d.ts`, present only in `canary.d.ts`, which is not loaded, and `undefined` at runtime.

**The remaining ref-to-latest-callback sites are a real `useEffectEvent` opportunity, ~28 of them, and were left for a separate change.** Assigning a ref during render is an impure render — React may discard the work under `StrictMode`, an interrupted concurrent render, or an `Activity`-hidden subtree re-rendering at low priority, leaving the ref carrying a callback from a render that never committed. Two of the two probed constraints matter: `useEffectEvent` throws if called during render, and the *value* shadows (`use-controllable.ts`'s `valueRef`, `use-form-reducer.ts`'s `valuesRef`) must not be converted — they hold values, not callbacks, and `valueRef` is deliberately advanced eagerly inside `setValue` so batched functional updaters chain. Biome 2.5.3 already exempts `useEffectEvent` results from `useExhaustiveDependencies`, verified against a same-shaped control that is flagged.

**Platform built-ins are largely adopted.** `Intl.NumberFormat` runs through a cached `resolveFormat` seam covering number/currency/percent/compact, with no hand-rolled grouping or `K`/`M` abbreviation anywhere; `Intl.RelativeTimeFormat`, `Intl.Collator`, `AbortSignal.timeout`/`any`, `crypto.randomUUID`, `navigator.clipboard`, `Element.checkVisibility` (correctly guarded for jsdom), `CSS.escape`, native `aspect-ratio`, `field-sizing: content`, `scrollbar-gutter: stable`, `:has()`, `text-wrap: pretty`, and `scrollIntoView({ block: 'nearest' })` are all in use. `Object.groupBy`/`Map.groupBy` have no candidates — the two things that look like groupings are a filtered two-level nest and a first-wins single-value map, neither expressible. `toSorted`/`.at(-1)` are idiom-only under `noUncheckedIndexedAccess`, which gives `.at(-1)` the same `T | undefined` type. `Intl.ListFormat`/`PluralRules` are incoherent while every user-facing string in the package is hardcoded English; they become real the day a string catalogue lands.

**Several platform swaps are blocked, and the blockers are worth recording.** `interpolate-size: allow-keywords` is unsupported in Firefox and Safari, so the `0fr`↔`1fr` grid reveal already in use remains the right auto-height mechanism. Scroll-driven animations (`animation-timeline`) would retire `useScrollOverflow` entirely but are not in stable Firefox. `scrollbar-gutter: stable` cannot replace `useScrollLock`'s measurement, because it only works applied to the consumer's `:root` at all times — a global layout decision a library cannot make for its host. `showModal()`/`popover` do not fit `Overlay`: `OverlayProps.container` scopes an overlay to an arbitrary element where `showModal()` always promotes to the document's top layer, `modal={false}` has no dialog equivalent, and jsdom implements none of `showModal`/`showPopover`/`inert`. Chart text measurement must stay an estimate — jsdom stubs `getContext` to `null` outright, so canvas `TextMetrics` would drop every chart-layout test to a fallback and cost SSR determinism.

**The remaining dependencies are used well.** `card-validator` handles brand detection, Luhn, CVV, and expiry with no hand-rolled duplicate (the formatters exist because it ships none, and consume its `gaps`). `fflate` does the zip; the OOXML part XML is hand-written because fflate ships no OOXML. `marked` is lexed to tokens and walked into React elements, never to an HTML string, so there is nothing to sanitize; its `safeUrl` scheme allowlist is something marked does not provide. `d3-geo`/`topojson-client` are used for bounds, fitting, area, and projection with no hand-rolled math — the two custom pieces, `rewindFeatures` and `decodePolyline`, have no equivalent in either. `tinykeys` is wrapped thinly and correctly, and the modifier-key checks scattered through roving-focus and pointer sensors are per-element rejection guards, not global shortcut matching — the wrong shape for it. `@internationalized/date` is used well everywhere except the two sites fixed above; `chart-time.ts` is exemplary. The charting and grid packages in `devDependencies` (`ag-charts-community`, `echarts`, `highcharts`, `ag-grid-community`, `@mui/x-data-grid`) are competitive baselines for the browser bench suite and never enter a published entry point.

**Dependency hygiene is clean.** Every one of the 21 runtime dependencies resolves to a real import site; nothing used is undeclared. `@types/d3-geo` and `@types/topojson-client` sit in `dependencies` rather than `devDependencies` correctly — the package publishes raw TypeScript source, so consumers type-check against it and need those types at their own install time.

**`CodeBlock` ships the full Shiki bundle to consumers** — `import('shiki')` resolves to `bundle-full`, 692 grammars and a 466 kB wasm, while the curated `createHighlighterCore` build already exists and reaches `CodeBlock` only through a docs-only Vite alias. Not filed as a finding because it is a deliberate, documented choice: `CodeBlockProps` types `lang`/`theme` as the full bundle's unions and `Markdown` casts arbitrary fence info-strings to `BundledLanguage`, so narrowing is a breaking API change. The honest shape is an injectable highlighter, which is a feature.

**`pdf-viewer` renders pages as PNGs and has no text layer**, so the document is unselectable, unsearchable, and reaches a screen reader as `Page 1 … Page N`. `pdfjs-dist` ships `TextLayer` and the module already holds the `viewport` it wants. This is the largest accessibility gap in the package and it is deliberately not filed as a built-in finding: the viewer's architecture is pages-as-immutable-image-`src`es, consumed in that shape by the thumbnail rail, zoom, and rotation, and `releasePdf` destroys the document as soon as rasterization finishes. A text layer is a rendering-core rewrite, and wants its own change and its own decision.
