# Bug Audit — defects across the `ui` surface

**Date:** 2026-09-11 · **Scope:** every `.ts` and `.tsx` file under [`src`](../../src), except the test and the benchmark trees — 1,510 files and 153,159 lines. **Method:** an area sweep reads every line of a disjoint file set and reports a defect only with a concrete trigger; a batched mechanism pass and a reach pass then judge each claim. **Status:** 1 of 28 area segments is complete, and it holds 15 findings; 33 segments stay open. **Living record — resolve rows in place, against the pull request that closed them.**

## Status

This audit is incomplete by design. One sweep of the whole package does not fit in one session. This container holds 4 cores, so the agent harness runs 2 sweeps at a time; a full first pass costs about 5 hours of sweep time, and the verification costs several times more. The segments below divide that cost. Each segment closes a named part of the surface, and each one costs one short session.

Segment `A01` is complete. It covers [`components/date-picker`](../../src/components/date-picker), [`components/menu`](../../src/components/menu), [`components/segment`](../../src/components/segment), and part of [`components/pdf-viewer`](../../src/components/pdf-viewer) — 49 files and 7,172 lines. It raised 15 claims, and all 15 survive verification: 2 high, 5 medium, and 8 low. Three root causes produce eight of them.

Nothing in this audit is fixed yet. Every row is a claim about the tree as of this commit, and the line numbers drift.

## Method

A unit is a disjoint file set of about 4,200 lines. One sweep agent owns each unit and reads every file in it, because a sample hides the defect that a sample misses. A segment holds one or two units.

A sweep reports a defect only when it can name the file, the line, the trigger, and the wrong result. Style, naming, and format stay out of scope, and Biome owns them. A request for a test, for a document, or for a refactor is not a defect. A repository convention is not a defect: [`CONVENTIONS.md`](../../../../CONVENTIONS.md) §3.6, §3.9, §7.2, §7.3, and §11.3 decide intent, and [`REFERENCE.md`](../../REFERENCE.md) §2 decides the tier boundary.

Two verifiers then attack the mechanism of every claim. The first one traces the real control flow, it follows each caller and each guard, and it tries to prove the wrong behaviour cannot happen. The second one reads the conventions, the TSDoc, the surface docs, the open audits, and the tests, and it tries to prove the behaviour is deliberate or already known. Both verifiers refute a claim when they are not certain.

A third pass then tests reach. For each claim it names a call site in the demos, the modules, the layouts, or the apps that reaches the trigger, or it records that no call site exists; that pass sets the severity. Segment `A01` ran without it, and [Method correction](#method-correction) records what that cost.

A claim survives only when a concrete trigger produces a wrong result that the repository neither intends nor already records. The bar separates a wrong result from fragile code, and only the wrong result survives.

Verification runs as one batch for each unit, not as one agent for each claim. The batch costs 2 agents for each unit in place of 2 agents for each claim, and it gives each verifier the context of the neighbouring claims. This choice is what makes a segment affordable.

### R1 — the `input` arm of DatePicker drops what the state hook resolved

`useDatePickerState` resolves `readOnly` and `invalid` for the whole component. The button-trigger arm forwards both. The `input` arm forwards `disabled` only, so each resolved flag dies at the branch. One decision fixes both rows: forward the resolved state to `DateInput` as the trigger arm does.

**R1.1 — `readOnly` never reaches the `DateInput`** · `date-picker.tsx:325` · high. The hook resolves `readOnly` at `use-date-picker-state.ts:63`, and its only reader is the `setOpen` guard at `:87`. The returned bundle never exposes it. `<DatePicker input readOnly value={d} onValueChange={spy} />` therefore renders an editable field with a live clear button, and a keystroke runs `commit` and rewrites the bound form field. The prop's own doccomment at `date-picker.tsx:161` says it blocks a value change. The input arm renders a bare `data-slot="control"` div, not a `Control` provider, so the `Control` half of the cascade is absent too. The one `readOnly` test covers the button trigger only.

**R1.2 — the resolved `invalid` flag never reaches the `DateInput`** · `date-picker.tsx:316` · medium. The hook merges the `Control` severity with the bound field's errors at `use-date-picker-state.ts:267`. `DateInput` re-derives the `Control` half through `useControl()`, so only the form-field half is lost — and that half is the one a resolver sets. Submit a `Form` whose resolver rejects an empty `due`, and the typed field carries no `aria-invalid` and no `data-invalid`. The same tree marks the button trigger invalid. A screen-reader user in `input` mode is never told the control is in error.

### R2 — relative presets have no span identity

A relative preset resolves to a span, and the code treats the preset id and the span as interchangeable. They are not: two presets can resolve to one span, and one span can change which preset it matches as the clock moves. Three findings follow from that single conflation, and R2.3 reaches its trigger only through R2.2.

**R2.1 — multi-select dedupes preset ids, not spans** · `date-picker-relative-utilities.ts:267` · high. The multi branch rebuilds the value as `presets.filter(selected.has(id)).map(resolve)`. Dedupe runs on the id set, and the committed value is a bare span, so two presets that resolve to one span both emit it. The shipped presets collide: `this-month` and `this-year` resolve identically for every day of January, and `today` and `this-month` collide on the first of each month. The value becomes `[span, span]`. `relativeChips` labels both spans through the newest pick, so two chips render with one React key — a duplicate-key error, and an aliased second chip. `selectedPresetIds` collapses both to one id, so the twin row reports `aria-pressed="false"` although it is selected, and a second click re-adds the same pair: the row cannot toggle off. The function's TSDoc at `:239` promises a deduped rebuild. The shipped demo passes `relative={{ multiple: true }}` with the default presets, and the only collision test covers single-select.

**R2.2 — the reference clock sits in a ref that no memo depends on** · `use-date-picker-relative-state.ts:136` · medium. `nowRef` takes `new Date()` during render, and `openPicker` re-stamps it. The two derivations that consume it, `chips` and `selectedIds`, list neither the ref nor any value that changes with it; `presets` resolves to a module constant for every shipped option, so no dep moves. A ref write cannot invalidate a memo, so the re-stamp never reaches the rendered label or the highlight. Hold a page across midnight with `Today` selected and reopen: the trigger still reads `Today` for a span that is now yesterday, and the `Today` row keeps `aria-pressed="true"` while `togglePreset`, which reads the ref directly, resolves at the fresh clock and commits a new span instead of a clear. `Calendar` guards the same hazard by deferring `today` to a mount effect. Hold `now` in state, seed it in an effect, and list it as a dep. The claim also named `customActive` as stale; it is computed inline, so it reads the fresh ref and is sound.

**R2.3 — the custom-range seed reads `value[0]`, not the unmatched span** · `use-date-picker-relative-state.ts:153` · low. `customActive` asks whether any committed span matches no preset, and `customSpan` then takes `value[0]` unconditionally. The committed value is never a mixed array, so a consumer-supplied mixed array is out of contract and is not a trigger. R2.2 supplies the real one: with `multiple: true`, pick two presets and hold the page across midnight. At the re-stamped clock `value[0]` matches a preset and `value[1]` matches nothing, so `Custom range` pre-fills Start and End from the preset span. Both endpoints are present, so the draft reads as a settled range that no user entered. Select the span that matched nothing.

### R3 — a static Menu with a trigger is an unsupported composition

`MenuTrigger`'s own TSDoc scopes it to a dropdown `Menu`, and `MenuContent` documents a static menu as a panel with no trigger to name it. Nothing enforces that, so `<Menu defaultOpen>` with a `MenuTrigger` typechecks and renders — and the repository's own accessibility corpus builds exactly that shape at `__tests__/a11y/cases/overlays.tsx:100`, with a comment that calls it a dropdown. Three findings come from that one seam. [`2026-07-13-PROPS-AUDIT.md`](2026-07-13-PROPS-AUDIT.md) already holds an open row for the seam itself: `Menu` selects its mode by prop presence, and a `StaticMenu` variant would complete the set. That row names the API shape; these three rows name the defects it produces, so they are new. One decision closes R3.2 and R3.3 and makes R3.1 the only real work: make the unsupported composition impossible, or support it.

Static mode has no consumer in the monorepo and no demo. That fact sets the severities below, and the first verification pass did not establish it.

**R3.1 — a static menu seats no tab stop** · `menu-content.tsx:73` · medium. The static branch renders `PopoverPanel` with `autoFocus={false}`. `PopoverPanel` runs `useA11yRoving` without `manageTabIndex`, which defaults to false, so the tab-stop effect returns at its first line. The panel is `tabIndex={-1}` and every row hardcodes `tabIndex={-1}`. Nothing in the subtree is tabbable, and nothing seats focus, so the documented roving focus has no entry point and a pointer hover is the only way in. A keyboard user cannot reach or activate any row (WCAG 2.1.1). Pass `manageTabIndex` through for the static branch, or give the static panel `tabIndex={0}`.

**R3.2 — a static menu's trigger toggles state the panel ignores** · `use-menu-state.ts:158` · low. `useClick(context)` composes into `getReferenceProps` in every mode. `MenuContent` gates the static panel on `isStatic`, not on `open`. A press therefore flips `open` to false and fires `onOpenChange(false)` while the panel stays on screen, so the trigger reports `aria-expanded="false"` over a visible menu and drops `aria-controls`. Only dismissal is suppressed for static mode; the toggle is not. Disable the toggle: `useClick(context, { enabled: !isStatic })`.

**R3.3 — a static panel omits `id`, so `aria-controls` dangles** · `menu-content.tsx:64` · low. The floating branch stamps `id={menuId}`; the static branch does not. `MenuTrigger` emits `aria-controls={open ? menuId : undefined}` in both arms, and a static menu's `open` is true from mount, so the trigger always names an element that never enters the document. axe reports a missing `aria-controls` target as incomplete rather than as a violation, so the accessibility sweep gate does not catch it. Stamp `id={menuId}` on the static panel.

### Independent findings

**F1 — the footer Clear unmounts itself under focus** · `use-date-picker-relative-state.ts:212` · medium. `handleClear` empties the value and keeps the popover open on purpose. An empty value makes `showFooterClear` false, so `DatePickerFooter` returns null at `date-picker-footer.tsx:41` and removes the focused button with no hand-off. No rescue runs: this tree resolves to a patched `@floating-ui/react` 0.27.19 whose patch touches `useFloatingPortalNode` only, `restoreFocus` defaults to false, and `DatePickerContent` never passes it. `useFloatingUI` returns focus on an open-to-closed transition, which `handleClear` avoids. The dialog stays open and modal with `document.activeElement` on `<body>`, and the rest of the page stays `aria-hidden` (WCAG 2.4.3). Only keyboard activation reaches it, because the panel preventDefaults `mousedown`; the one relative consumer in `apps/places` passes `footer={{ clear: false }}`. Move focus inside `handleClear`, as the trigger's clear button does. The claim cited `:247` for the bail; the file holds 86 lines.

**F2 — a rebuilt `pages` array resets every rotation** · `use-pdf-viewer-page-rotation.ts:47` · medium. The document identity is `pagesProp ?? src`, compared by reference against a ref, and a mismatch clears every stored rotation during render. `PdfViewer` hands the prop through with no memo and carries no `React.memo`, so `pages={docs.map(toPage)}` yields a fresh array for each parent render and each one reads as a document swap. Rotate a page, then trigger any unrelated parent render: every rotation is lost. The hook's contract says a page preserves its rotation, and `PdfViewerProps.pages` documents no stability requirement — while the sibling `highlights` prop advertises that its identity need not be stable, so the inline array is the shape the API invites. Key the reset on `src` or on the joined page ids.

**F3 — a clear emits `onOpenChange(false)` on a closed picker** · `use-date-picker-state.ts:157` · low. `handleClear` always calls `closeCalendar`, which calls `setOpen(false)` unconditionally, and `useControllable`'s setter fires the callback with no equality check. Clear from the trigger without opening the picker and the consumer receives a close transition that never happened. The range hook holds the same shape. Guard the close, or let `setOpen` skip a write that matches the current state.

**F4 — `aria-activedescendant` outlives the grid it names** · `use-date-picker-state.ts:285` · low. `inputAria` gates `aria-controls` on `open` and gates `aria-activedescendant` on `active?.zone === 'grid'` alone. `active` clears in `openCalendar` and `closeCalendar` only. A close by a click or a press outside self-heals through the outside-press dismiss, so that is not a trigger; a programmatic close of a controlled `open` prop — an effect, a timer, a route change, or arriving data — leaves the input naming an id that the unmounted grid no longer stamps, and a later programmatic reopen restores the stale highlight. Gate both attributes on `open`, and reset `active` when `open` goes false from any source.

**F5 — a link row does not activate on Space** · `menu-item.tsx:96` · low. The `href` branch composes `onClick` and `onPointerMove` and no `onKeyDown`; the button branch composes the key handler. An anchor activates on Enter natively, so Enter works. Space does not: `handleActivationKey` bails when the mode is not virtual, typeahead excludes the space key, and the navigation helper returns null for it, so nothing consumes the press and the page behind the open menu scrolls. This affects the context menu, a submenu, and a static menu; the dropdown path synthesises a click. No demo and no repository consumer puts an `href` row outside a dropdown, so this is an APG gap on one redundant key, not keyboard inoperability.

**F6 — `data-active` survives the exit animation** · `use-menu-state.ts:151` · low. `clearVirtualActive` forwards an empty item list, so the lookup that strips `data-active` matches nothing and only the owner's `aria-activedescendant` is removed. Its comment assumes the rows unmount, but `PresencePortal` holds the panel through a 150 ms opacity exit. Reopen inside that window and the same DOM nodes reconcile, so a row stays washed with no `aria-activedescendant` that names it, and the first arrow press skips past it. A reduced-motion user is unaffected, which makes the divergence intermittent. Clear from the live rows, or strip the attribute across the panel on open.

**F7 — consumer props spread after the structural wiring** · `menu-trigger.tsx:149` · low. `mergeProps` in the installed floating-ui build assigns every non-`on*` key straight through, so `{...getReferenceProps({ ...rest })}` re-emits each consumer prop — and that spread sits after `type="button"`, `aria-haspopup`, `aria-expanded`, `aria-controls`, and `data-slot`. A consumer prop therefore wins over the structural wiring, which inverts [`CONVENTIONS.md`](../../../../CONVENTIONS.md) §3.9. `MenuTriggerProps` accepts `type`, so `<MenuTrigger type="submit">` inside a form typechecks, and a press both opens the menu and submits the form. This component's own cloned-child branch applies the wiring after the spread, and `menu-item.tsx` is the convention's cited precedent. Move the five attributes below the spread.

## Ruled out

No claim fell. The first pass refuted none of the 15, and the red team overturned none. That outcome is unusual for this repository, and [Method correction](#method-correction) treats it as a fact about the method rather than as a result.

Six claims changed instead of falling. The red team restated two and downgraded four, and each adjustment names ground that the next audit does not need to walk again.

`R2.3` — the claim's trigger was a consumer-supplied mixed array of preset spans and custom spans. The documented mutual-exclusivity contract excludes that value, and the committed value is never mixed. The finding survives on a different trigger, which R2.2 supplies.

`F4` — the claim's trigger was a `Done` button outside the picker. A click or a press anywhere outside routes through the outside-press dismiss, which clears `active` and erases the state the claim depends on. Only a non-pointer programmatic close reaches the defect.

`R3.1` — downgraded from high. Static mode has no consumer in the monorepo and no demo, so no shipped surface is keyboard-unreachable today.

`R3.2`, `F5`, `F6` — downgraded from medium. `R3.2` needs the unsupported trigger composition, which no demo builds and which the trigger's own TSDoc excludes. `F5` costs one redundant key, and Enter still activates the row. `F6` holds for 150 ms and self-heals on the next arrow press or pointer move.

One citation in `F1` was wrong and the sweep caught it itself: the footer bail is `date-picker-footer.tsx:41`, and the claim named `:247` on an 86-line file. Neither verifier opened the file, which is the first piece of evidence in the section below.

## Method correction

The first verification pass kept all 15 claims. This repository's audits kill a large share of theirs: 19 of 54 in the events audit, 35 of 57 in the August simplification audit, 8 of 26 in the test-suite audit. A zero rate is therefore a fact about the verification, not a result, so a red team re-judged all 15 with a mandate to overturn.

It overturned none. On mechanism the sweep was disciplined: the red team opened every cited file, reproduced all 15 traces, and found no claim whose cited line says something other than what the claim says. The zero rate is partly earned.

The verification was weak on reach, and in four specific ways.

First, neither verifier attacked the trigger. Both attacked the mechanism, found it, and stopped. A claim whose mechanism is real but whose stated trigger cannot reach it passed twice — `F4` and `R2.3` are the two proofs.

Second, neither verifier weighed blast radius. Two greps settle who reaches each path, and they move four of the fifteen severities. The reachability verifier read its remit as "can this code path execute" in place of "does anything execute it".

Third, the batch did not cross-reference its own claims. `R3.1`, `R3.2`, and `R3.3` are one unsupported composition, and a row in the July props audit already records the seam. Judged one at a time each confirms; judged together they are one decision.

Fourth, the two verifiers were not independent enough. They ran in parallel and neither read the other's output, so the anchor is the claim itself: both read the sweep's own `evidence` text and walked the same citations in the same order, including the wrong line number for the footer bail. Both also cited `node_modules` line numbers without checking `patches/`, where this tree patches `@floating-ui/react`. The patch touches an unrelated export, so `F1` survives — by luck, not by verification.

These five changes apply from segment `A02`:

1. Keep the batched mechanism pass. It earns its cost, and it is what holds the verification affordable.

2. Add a separate reach pass. For each claim it must name a call site in `src/docs/demos`, `src/modules`, `layouts`, or `apps` that reaches the trigger, or record that no call site exists. That pass sets the severity, not the sweep. Expect it to move severities rather than kill claims.

3. Require a verifier to quote each line from the file it opened. The wrong citation in `F1` would not have survived one quote.

4. Require a check of `patches/` before a verifier cites a `node_modules` line.

5. Require the batch to group its claims by root cause, and to search the open audits for a row that already records the seam, before it reports.

The cost of segment `A01` sets the budget for the rest. Two sweeps raised 15 claims. The verification spent 643,106 subagent tokens across 4 agents, and the red team spent 346,960 across 2. Judgement therefore cost about one million tokens for 15 claims, and it cost more than the sweep that found them.

## Lens segments

An area sweep reads one file set, so it cannot see a defect that spans the package. A lens sweep reads across the package for one defect class. The lens segments run after the area segments, because a lens needs the confirmed list to avoid a repeat.

|---|---|---|
| `B01` | react-hook-correctness · lifecycle-teardown · form-binding-cascade | open |
| `B02` | aria-semantics · focus-and-keyboard · error-handling | open |

Each lens hunts one class. **react-hook-correctness** reads dependency arrays against the bodies, and it hunts a stale closure, a state write in render, and a ref that the render body mutates. **lifecycle-teardown** hunts a listener, an observer, a timer, or an animation frame with no matching teardown. **form-binding-cascade** tests each bindable control against [`CONVENTIONS.md`](../../../../CONVENTIONS.md) §7.2 and §7.3. **aria-semantics** hunts a role or a state that breaks assistive technology, and an `id` reference that points at nothing. **focus-and-keyboard** hunts focus that escapes to `document.body`, a roving set with no tab stop, and arrow arithmetic that overruns. **error-handling** hunts a swallowed error and a state that stays in load forever. **async-races** hunts a state write after a newer request resolves, and a missing guard. **numeric-and-geometry** hunts a zero divisor, and `NaN` in a style or an SVG attribute. **date-time-locale** hunts a time-zone assumption and a locale-sensitive parse of a machine string; the suite pins `LANG=en-US`, so CI hides this class. **unsound-types** hunts a cast that a caller can break. **composition-and-boundaries** tests spread order against §3.9, and the barrel against §3.5. **browser-floor** tests each platform call against [`.browserslistrc`](../../../../.browserslistrc) and §11.3. **render-cost-and-leaks** hunts an unstable context value and a cache with no eviction. **test-soundness** hunts a test that cannot fail. **build-and-config-surface** reads what the area sweeps exclude: `tsup.config.ts`, `vite.docs.config.ts`, the five Vitest configs, the three `tsconfig` files, the `exports` map in `package.json`, and the three CSS files under [`src/docs`](../../src/docs).
